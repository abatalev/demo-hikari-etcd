# Hikari-пул, который настраивается через etcd, на масштабируемом флоте

Прототип: размер пула соединений каждого инстанса к PostgreSQL 16 меняется **на лету** правкой
ключа в etcd. Compose-стенд: etcd, инстансы сервиса (Spring Boot 3 + HikariCP) четырёх групп,
число реплик которых задаётся `make up --scale` (по умолчанию 8), **своя база PostgreSQL 16 на
каждый сервис**, балансировщик Traefik на docker-метках с двумя точками входа (граница — по
сервису), два провизора
конфигурации (лидер выбирается по каждому сервису через etcd), Prometheus с правилами, Grafana,
по сборщику метрик на каждую базу, две точки нагрузки (по одной на сервис) и образ с etcdctl.

```
   etcdctl put (бюджет активного флота)   провизёр делит бюджет между активными инстансами
   /config/services/{service}/activeMaxConnections = 100   →   .../hikari/maximumPoolSize = 25
            │  неактивные группы (маркер {root}/groups/{group}/active=false) держат резерв R
            │  столько путей, сколько развёрнуто реплик (имя инстанса — hex-ID контейнера)
            ▼
  ┌───────────────── etcd (watch, jetcd, revision-aware) ─────────────────┐
  │                                                                        │
  ▼      ▼      ▼      ▼      ▼      ▼      ▼      ▼                       ▼
 service-a × 4 реплики (group-1, group-2)   service-b × 4 реплики (group-1, group-2)
   (имя узла регистрации = hex-ID контейнера = application_name пула)
       \       |        /     Traefik     \       |        /
        service-a ←── web-a :8080 ──┐        service-b ←──── web-b :8081
   нагрузка → web-a ─────────────────► service-a (только service-a)  ──► PostgreSQL 16 «postgres-a»
   нагрузка → web-b ───────────────────────────────► service-b (только service-b) ──► PostgreSQL 16 «postgres-b»
             │ JDBC (application_name = имя инстанса), своя база на сервис
             ▼
     у каждой базы max_connections=120 при бюджете флота 100 (запас 20)
```

Ключ из etcd доезжает до нового числа коннектов — [docs/mechanism.md](docs/mechanism.md).
Инстанс не принимает трафик, пока не получил конфигурацию из etcd (гейт готовности, 503 на
`/api/work`) — подробности в [docs/operations.md](docs/operations.md#готовность-к-трафику).
Размер пула задаётся только через etcd: локальный дефолт жёстко 0, пул появляется с первым
конфигом из провизора.

## Быстрый старт

```bash
cp .env.example .env   # один раз; масштабы групп A_G1..B_G2 там же
make up                # собрать, поднять 8 инстансов (4 группы × 2 реплики) + 2 базы + lb + 2 провизора,
                       #   дождаться готовности; состав объявляет docker compose ps (make instances)
make load-logs         # смотреть, как нагрузка давит на пул (loadgen-a; LOAD_S=service-b — второй)
make leader            # кто ведёт каждый сервис (лидер выборов провизора)
make set-active-max-connections SIZE=100 S=service-a  # ← вот тут etcd меняет пул на живых инстансах
make set-group-active G=group-2 ACTIVE=false          # неактивный флот: узлы группы сжимаются до R
make budget S=service-a           # доли по сервису и их сумма (сумма долей + резерв = бюджет)
make fleet-sessions S=service-a   # сколько флот держит в базе сервиса против его бюджета
make pool              # сводка: ready/max/total/active/idle по всем инстансам из метрик
make down              # остановить; make clean — вместе с данными (в т.ч. ключи etcd)
```

Число реплик группы задаётся в `.env` (`A_G1=2 A_G2=2 B_G1=2 B_G2=2`); правка требует
`make up` — реплики пересоздаются там, где число изменилось. Списка инстансов в конфигурации нет:
что развёрнуто, объявляет сам compose, а имя инстанса приходит из окружения
(`ETCD_INSTANCE → POD_NAME → HOSTNAME`; в контейнере `HOSTNAME` — короткий ID, он же имя узла
регистрации и `POOL_NAME`).

Наблюдение поднимается тем же `make up` и устроено **одной дверью**: приложения сами отдают
метрики, трассы и свой журнал в otel-collector, тот раскладывает их по хранилищам, а сборщик
метрик берёт у него только метрики. Порты из `.env`:

| что | адрес | что там смотреть |
|---|---|---|
| витрина Grafana | `localhost:3000` | три панели, анонимный просмотр без логина |
| Prometheus | `localhost:9090` | `/targets` — состояние целей, `/alerts` — сработавшие правила, `/graph` — запросы |
| дверь сигналов (otel-collector) | `localhost:4318` | приём OTLP от приложений; `:9464` — её же метрики в prometheus-формате (единственный источник метрик приложений) |
| хранилище трасс (Tempo) | `localhost:3200` | трассы инстансов и события механизма |
| хранилище журналов (Loki) | `localhost:3100` | журналы инстансов и провизёров по признакам |
| сборщик метрик базы a | `localhost:9187` | сессии postgres сервиса `service-a` (нужна витрине, руками обычно не смотрят) |
| сборщик метрик базы b | `localhost:9188` | сессии postgres сервиса `service-b` |

Панели витрины (слева в списке, в этом порядке):

- **Бюджет флота** — `N`, `R`, `m`, сумма приказанных размеров против бюджета, оценка занятого
  места и её максимум, неосвобождённое сжатие, решения провизёра, **факт: сессии пулов в базе
  против бюджета**. Переменные `service`/`group` сверху.
- **Пулы и конфигурация** — потолок против применённой конфигурации по каждому инстансу,
  соединения (занятые/idle/ожидающие), перцентили ожидания выдачи и удержания, состояние
  конфигурации, гейт трафика и причина неготовности, расхождение «процесс ↔ база».
- **Провизёр и etcd** — кто ведёт каждый сервис (обе реплики), устарел ли снимок дерева,
  пересчёты и приказы, зависшее сжатие, число сработавших правил, состояние целей сбора.

У величин инстанса на панелях есть переходы: у точки на графике — «Журнал» и «Трассы», они
открывают журнал и трассы **того же инстанса за выбранный момент** (признаки берутся из самой
точки, вручную ничего вводить не надо). Так разбор события идёт величина → журнал → трасса.

Панели поставляются **только на чтение**: правка в интерфейсе перезаписывается при рестарте
витрины. Правила живут в сборщике и **ничего не доставляют** (alertmanager не подключён) —
сработавшие видно на панели «Провизёр и etcd» и запросом
`localhost:9090/api/v1/query?query=ALERTS{alertstate="firing"}`. Состояние целей печатается в
конце `make up` и по требованию — `make targets`; «молчание инстанса» объявлено правилом из
живого состава (`make silence-rules`), а узнать, у кого именно нет рядов, — `make check-instances`.
Подробности, в том числе разбор сбоев и что означает каждая величина, —
[docs/operations.md](docs/operations.md#наблюдение).

Лог инстанса в момент правки:

```
[etcd@4 [maximumPoolSize=put]] eager fill: пул расширен с 10 до 25 коннектов одним изменением
[etcd@4 [maximumPoolSize=put]] конфигурация по пути /config/services/service-a/groups/group-1/instances/a1b2c3d4e5f6/hikari/ получена, открываем трафик
```

**Что нужно на машине:** Docker + `make` + `curl` + `python3` (и `make up` зовёт `python3`).
Maven нужен только для `make test`. Локальный запуск без compose и режим `ETCD_ENABLED=false`
(единственный способ подняться без etcd — тогда гейта нет; но и пула нет: размер задаётся только
через etcd) — [docs/operations.md](docs/operations.md).

## Ключи конфигурации в etcd

Путь конфигурации инстанса:

```
{ETCD_ROOT}/services/{service}/groups/{group}/instances/{instance}/hikari/<ключ>
/config/services/service-a/groups/group-1/instances/a1b2c3d4e5f6/hikari/maximumPoolSize
```

Сегменты: `service` — имя сервиса (`SERVICE_NAME`, фолбэк `spring.application.name`); `group` —
`sгруппа из окружения` (`ETCD_GROUP` → `POD_NAMESPACE`); `instance` — имя инстанса из окружения
(`ETCD_INSTANCE` → `POD_NAME` → `HOSTNAME`). При `ETCD_ENABLED=true` `group` и `instance`
**обязательны**: пустой сегмент — отказ на старте с указанием, какой сегмент не заполнен. Путь
собирается сервисом сам, и провизор собирает его по тем же правилам, поэтому расхождение
«провижер пишет в другой префикс, чем читает сервис» исключено по построению.

| ключ | пример | меняется на лету | комментарий |
|---|---|---|---|
| `maximumPoolSize` | `25` | да | **доля бюджета сервиса** (активный флот); неактивному узлу — ровно резерв R; 0 закрывает пул; ключ управляемый — провизёр перезаписывает его при пересчёте |
| `minimumIdle` | `5` | да | не задан = держится равным `maximumPoolSize`; если меньше — в пуле появятся «спящие» коннекты, которые уходят по `idleTimeout` |
| что угодно ещё | | | игнорируется с предупреждением (ловим опечатки) |

Из etcd приходит только размер. Цель соединения (адрес базы, учётные данные, имя пула) и
таймауты — локальная конфигурация процесса (`DB_URL`, `DB_USER`, `DB_PASSWORD`, `POOL_NAME`,
`POOL_CONNECTION_TIMEOUT_MS` и прочие `POOL_*`): их правка требует перезапуска инстанса. Пароль
подключения в etcd не хранится вовсе, и такой ключ считается неизвестным.

Второй уровень дерева — **бюджет соединений сервиса и активность групп**. Эти ключи читает и
пишет только провизёр, инстанс их не видит:

| ключ | пример | комментарий |
|---|---|---|
| `{ETCD_ROOT}/services/{service}/activeMaxConnections` | `100` | бюджет активного флота N: сумма активных долей + резерв неактивных; делится между активными поровну, 1.. |
| `{ETCD_ROOT}/services/{service}/activeMinConnections` | `1` | минимальная активная доля m: обслуживаются только `floor((N − R×k)/m)` активных инстансов |
| `{ETCD_ROOT}/services/{service}/inactiveMaxConnections` | `1` | резерв неактивного флота R: неактивный узел держит пул ровно R; `0` = холод (конфигурации нет, 503) |
| `{ETCD_ROOT}/groups/{group}/active` | `true` | маркер активности группы — **глобальный флот** (общий для всех сервисов); отсутствие/мусор ≠ «false» = активна |

Диапазоны значений и что бывает за их нарушение — [docs/mechanism.md](docs/mechanism.md#валидация).
Локальные дефолты (`pool.db.*`) — фолбэк: ключ в etcd всегда выигрывает.

## Регистрация инстанса в etcd

Каждый инстанс при включённом источнике на старте создаёт в etcd **узел со своим именем** — на
уровень выше ключей конфигурации:

```
{ETCD_ROOT}/services/{service}/groups/{group}/instances/{instance}
```

Узел держится через аренду etcd (TTL по умолчанию 15с, keepalive каждые 5с) и исчезает при
остановке: штатной — немедленно (аренда отзывается), при падении процесса — по истечении TTL.
После обрыва etcd регистрация восстанавливается сама. `make registrations` показывает живые узлы,
`make instances` — развёрнутый состав из `docker compose ps`.

Узел лежит **вне** префикса `hikari/`, поэтому конфиг-воркер его не читает: на готовность и гейт
трафика регистрация не влияет — «зарегистрирован, но не готов» это нормальное состояние (трафик
открывается только после распознанных ключей `hikari/`). При `ETCD_ENABLED=false` регистрации нет.
Подробности — [docs/mechanism.md](docs/mechanism.md#регистрация-инстанса-в-etcd).

## Провижирование конфигурации

Конфигурацию раскладывает не разовый сидер, а отдельный сервис **провижер**, запускаемый
**двумя репликами** (`config-provisioner-1`, `config-provisioner-2`), который следит за деревом
`{root}/services/` и держит инвариант: **ключи конфигурации инстанса существуют тогда и только
тогда, когда существует его узел регистрации и узел получил долю сервисного бюджета**.

- Работает ровно одна реплика на сервис: лидер выбирается через etcd узлами
  `{root}/provisioner/leader/{service}/` (лидер — ключ с наименьшим `create_revision`, значение —
  имя реплики). Упал лидер → второй перехватывает сервис в пределах `PROV_LEADER_TTL` (10с) и
  делает полную сверку. Кто ведёт: `make leader`. Подробности — [docs/mechanism.md](docs/mechanism.md#выборы-лидера).
- **Размер пула — доля сервисного бюджета, делённая между активными.** Бюджет лежит в etcd:
  `{root}/services/{service}/activeMaxConnections` (N), `.../activeMinConnections` (минимальная
  активная доля m) и `.../inactiveMaxConnections` (резерв неактивного флота R). Активные инстансы
  делят `N − R×k` (k — число неактивных) поровну, неактивные держат пул ровно R (при `R=0` —
  конфигурации нет, холод). Сумма активных долей + резерв = N. Ключи создаются при первом узле
  сервиса дефолтами провизера (`PROV_ACTIVE_MAX_CONNECTIONS` = 100,
  `PROV_ACTIVE_MIN_CONNECTIONS` = 1, `PROV_INACTIVE_MAX_CONNECTIONS` = 1) только если их ещё нет,
  и переживают опустение сервиса — этого требует rolling update.
- **Группа — глобальный флот.** Маркер `{root}/groups/{group}/active` (true|false) общий для всех
  сервисов: выключенная группа сжимает узлы во всех сервисах, но бюджет каждого сервиса
  пересчитывается свой. Маркеры читаются поллингом ~1с; обрыв etcd держит последнее состояние.
  Управление: `make set-group-active G=group-2 ACTIVE=false`.
- `maximumPoolSize` — **управляемый** ключ: лидер приводит его к доле при каждом пересчёте, то
  есть при изменении бюджета, появлении или исчезновении инстанса, а также на старте и после
  обрыва etcd. `minimumIdle` — обычный put-if-absent: ручная правка переживает всё, пока жив узел
  регистрации.
- Инстанс, которому доля не досталась (активный бюджет не тянет минимум, либо неактивная группа
  при `R=0` — холод), остаётся без конфигурации и не обслуживает трафик: `/api/work` отвечает 503,
  `readiness` DOWN, пула нет вовсе (локальный размер 0). При `N < m`, `R` вне диапазона или
  `R×k > N` провижёр не меняет ничего и пишет WARN с числами (fail-closed — опечатка в etcd не
  должна обнулить живой сервис).
- Инстанс исчез (штатная остановка, краш, истекла аренда по TTL) → лидер **удаляет весь**
  префикс `.../{instance}/hikari/`, включая ключи, добавленные вручную.
- События ключей `hikari/*`, кроме `maximumPoolSize`, провижёр игнорирует — петель нет. Записи
  лидера идемпотентны, поэтому окно перехвата безопасно.
- **Сумма долей = N не означает, что флот держит N прямо сейчас.** В переходе сжатый инстанс ещё
  держит соединения, поэтому инстанс публикует рядом с конфигурацией
  `{root}/services/{service}/groups/{group}/instances/{instance}/unreleasedConnections` —
  сколько соединений он держит **сверх** своего потолка, и провижёр выдаёт растущим только то, что
  освободилось фактически, одному узлу за раз. Пока место не освободилось, флот работает меньше
  бюджета — это размен превышения на недобор. Проверка: `make fleet-sessions`, непрерывный замер
  перехода — `scripts/measure-fleet.sh`. Подробности —
  [docs/mechanism.md](docs/mechanism.md#переходы-бюджета-почему-рост-ждёт-освобождения).

Порядок старта в compose не важен: инстансы больше не ждут сидера — провижёр нагоняет
конфигурацию по факту регистрации (сверка + watch с `revision+1`). Окно «зарегистрирован, но ещё
не провижен» — нормальное состояние, гейт трафика закрывает его до первого ключа.

Следствие для ручных правок: `maximumPoolSize` живёт **до ближайшего пересчёта** (`make set-size` —
временный оверайд), остальные значения — **пока жив узел инстанса**. Подробности —
[docs/mechanism.md](docs/mechanism.md#распределение-сервисного-бюджета).

## Команды

Адресация инстансов: `I=имя` — один инстанс (hex-ID контейнера, он же имя узла регистрации),
`S=сервис` — все инстансы сервиса, `G=группа` — все инстансы группы. Фактический расклад:
`make instances` (состав из `docker compose ps`), живые сервисы — `make services` (узлы регистрации).

| команда | что делает |
|---|---|
| `make up` / `make down` / `make clean` | поднять (ждёт готовности всех с таймаутом) / остановить / остановить с томами |
| `make build` | пересобрать образы |
| `make ps` | состояние контейнеров |
| `make instances` | расклад из `docker compose ps`: инстанс (hex-ID), сервис/группа, путь конфигурации |
| `make services` | живые сервисы по узлам регистрации etcd |
| `make pool` | сводка по всем инстансам: готовность из метрик, пул, путь и ключи в etcd |
| `make targets` | состояние целей сбора метрик (нужен поднятый Prometheus) |
| `make check-instances` | живая сверка: у каждого инстанса из `docker compose ps` есть ряды в наблюдении, расхождение называется поимённо и даёт ненулевой код возврата |
| `make silence-rules` | перегенерировать правила молчания инстансов из состава `docker compose ps` (оба файла: `instances.yml` и `instances.test.yml`) |
| `make check-silence` | зафиксированные правила молчания совпадают с составом (входит в `make test`) |
| `make door-config` | проверить конфигурацию двери сигналов (входит в `make test`) |
| `make config I=…` | ключи инстанса в etcd (I — hex-ID; неизвестный I — отказ) |
| `make registrations` | узлы регистрации инстансов в etcd (кто сейчас жив) |
| `make leader` | кто ведёт каждый сервис (лидер выборов провизора) |
| `make budget [S=сервис]` | бюджет сервиса: N, m, R, маркеры групп, доли по инстансам и их сумма |
| `make fleet-sessions S=сервис` | флот **одного** сервиса по сессиям его базы: потолки, публикации освобождения, «худший случай» и OK/ПРЕВЫШЕНИЕ против N |
| `make set-active-max-connections SIZE=100 S=service-a` | **бюджет активного флота N** (делится между активными инстансами) |
| `make set-active-min-connections SIZE=15 S=service-a` | **минимальная активная доля инстанса m** |
| `make set-inactive-max-connections SIZE=1 S=service-a` | **резерв неактивного флота R** (`0` = холод: неактивным конфигурации нет) |
| `make set-group-active G=group-2 ACTIVE=false` | **маркер активности группы** (глобальный флот, true/false) |
| `make set-size SIZE=25 I=…` | оверайд `maximumPoolSize` одного инстанса (живёт до пересчёта) |
| `make set-service-size SIZE=25 S=service-a` | оверайд `maximumPoolSize` всех провиженных инстансов сервиса |
| `make set-group-size SIZE=25 G=group-1` | оверайд `maximumPoolSize` всех провиженных инстансов группы |
| `make set-min-idle SIZE=3 I=…` | зафиксировать `minimumIdle` |
| `make unset-min-idle I=…` | снова follow за `maximumPoolSize` |
| `make work [LOAD_S=сервис]` | один запрос через балансировщик сервиса (round-robin по нему) |
| `make sessions S=сервис` | сессии базы сервиса по `application_name` всех его пулов |
| `make psql S=сервис` | консоль базы сервиса |
| `make stress [LOAD_S=сервис]` | разовый прогон нагрузки на сервис (по умолчанию 20с) |
| `make logs P=…` | логи инстанса (hex-ID или имя сервиса compose) |
| `make load-logs [LOAD_S=сервис]` | логи нагрузчика сервиса |
| `make service-restart P=…` | перезапустить инстанс |
| `make test` | юнит-тесты (нужен maven) + проверки на живом стенде: сверка правил молчания и состава (check-silence, check-instances), конфигурация двери, `promtool check config/rules` и `promtool test rules` |

`make stress` без явного `DURATION_S` больше не зависает: для разового прогона он по умолчанию
20 секунд (для постоянной нагрузки работают `loadgen-a`/`loadgen-b` — например, `docker compose
restart loadgen-a` или пусть крутятся как есть).

Команды, работающие с базой (`sessions`, `psql`, `fleet-sessions`), требуют `S=` и **отказывают
без него**: баз две, а сводка «флот 100» из обеих сразу читалась бы как «флот 200 в одной базе».
Проверка `S=` идёт по живым узлам регистрации (`make services`): неизвестный сервис — отказ с
перечислением живых. Нагрузка адресуется отдельной переменной `LOAD_S=` (по умолчанию `service-a`),
потому что `S=` в командах etcd обязателен по существу и молчаливый выбор там опасен.

## Топология и балансировка

- Состав: 4 группы (`service-a-group-1`, `service-a-group-2`, `service-b-group-1`,
  `service-b-group-2`), число реплик каждой задаётся `make up --scale` из `A_G1`/`A_G2`/`B_G1`/
  `B_G2` (`.env`, по умолчанию 2 → 8 инстансов). Хост-портов у инстансов нет: наружу флот отдаёт
  балансировщик, и у инстанса нет ни имени, ни порта, которые можно было бы зафиксировать.
  Реплики идентифицируют себя сами, из окружения (имя инстанса — hex-ID контейнера).
- **Своя база на сервис**: `postgres-a` обслуживает `service-a`, `postgres-b` — `service-b`
  (порты хоста 5432/5433, потолок соединений 120 каждый, свой том и свой сборщик метрик). Границы
  проходят по сервису, как и точки входа балансировщика. Механизму база безразлична: бюджет и доли
  живут в etcd, адрес базы приходит локально в `DB_URL`. Потолок 120 = бюджет 100 + запас 20: запас
  меньше доли одного инстанса (25), поэтому превышение сверх потолка отказывает база, и больше
  того, что занимает стенд сам (7–9 соединений), поэтому `psql` и сборщик проходят при полном
  флоте — роль стенда суперпользователь, зарезервированные слоты флотом не занимаются.
- Один балансировщик **Traefik** с двумя точками входа: `:8080` → инстансы `service-a`,
  `:8081` → инстансы `service-b` (граница по сервису держится привязкой маршрута к точке входа).
  Состав балансировщик читает из docker-провайдера: роутер и сервис (`fleet-service-a`/
  `fleet-service-b`) заданы метками на контейнерах инстансов, что развёрнуто — то и балансируется,
  и правка состава (scale up/down, пересоздание реплик) подхватывается по событиям docker без
  перезапуска распределителя и без правки его настройки. Отдельных процессов два не было смысла
  делать: составы бэкендов не пересекались, поэтому они и не подстраховывали друг друга.
- Балансировка: round-robin с активным опросом признака готовности каждого экземпляра. Неготовый
  инстанс уходит из ротации сам — до того, как отдаст хоть один `503`, — за время не длиннее периода
  опроса (1с) плюс подтверждение; замер на стенде — 0.93с от `readiness: DOWN` до исчезновения
  имени в ответах. Опрос идёт по `/actuator/health/readiness`, тому же признаку, на котором держится
  гейт трафика, поэтому «не готов» для распределителя и «не обслуживает» для клиента — один и тот же
  факт. Повторов запроса у другого экземпляра нет: за неготовым не идёт уже сам, а на пересоздании
  экземпляров (новые адреса) распределитель подхватывает новое состояние сам, без перезапуска.
- Наблюдение: дверь сигналов `otel-collector :4318` (её метрики `:9464`), хранилище трасс
  `tempo :3200`, хранилище журналов `loki :3100`, `prometheus :9090`, `grafana :3000`,
  `postgres-exporter-a :9187`, `postgres-exporter-b :9188` (порты из `OTLP_PORT`/
  `OTEL_METRICS_PORT`/`TEMPO_PORT`/`LOKI_PORT`/`PROM_PORT`/`GRAFANA_PORT`/`EXPORTER_PORT_A`/
  `EXPORTER_PORT_B` в `.env`). Приложения отдают метрики, трассы и журнал **сами** (OTLP), сборщик
  метрик приложений не опрашивает — только дверь, etcd и сборщики баз. Ни один компонент
  наблюдения не входит в цепочки `depends_on`: недоступность наблюдения не мешает подъёму стенда и
  обслуживанию трафика.
- Перечней в конфигурации нет: состав инстансов — `docker compose ps` (`make instances`), узлы
  регистрации — etcd (`make registrations`), сервисы — живые узлы регистрации (`make services`).
  Из живого состава выводятся правила молчания инстансов (`make silence-rules`, сверка
  `make check-silence`) и ведётся живая сверка состава с наблюдением (`make check-instances`); оба
  входят в `make test`. Имя базы выводится из имени сервиса (`service-a` → `postgres-a`), второй
  копии списка в репозитории не появляется.

## Готовность к трафику (гейт конфигурации)

Инстанс **не принимает трафик, пока не получил конфигурацию из etcd** (снимок с хотя бы одним
распознанным ключом). Пока гейт закрыт:

- `/api/work` отвечает **503** (фильтр), а наблюдение работает — неготовый инстанс виден:
  метрики (`pool_traffic_gate_open`, `pool_not_ready_reason`, `pool_config_state`) и
  `/actuator/prometheus`; текстовая точка отдаётся всегда, независимо от гейта;
- `/actuator/health/readiness` = DOWN (с причиной), `/actuator/health/liveness` = UP — живость
  от etcd не зависит, crashloop из-за etcd исключён;
- причина неготовности — в деталях `readiness` (`details.poolEtcd.reason`), в метрике
  `pool_not_ready_reason` и в теле 503 самого `/api/work`.

Гейт закрывается, когда распознанных ключей не осталось (провижер снял конфигурацию — инстанс
потерял долю бюджета или стал частью холодного флота `R=0`), и открывается снова при возврате
ключей. Закрытие происходит только по реальным событиям удаления и снимкам при живом etcd: обрыв
etcd трафик не останавливает. Неактивные группы при `R ≥ 1` конфигурацию **получают** (пул ровно
R) и продолжают обслуживать трафик. Отклонённая при проверке конфигурация (мусор или 0 в
`maximumPoolSize` из etcd) гейт не удерживает: значение получено, пул остаётся на последних
рабочих значениях. `ETCD_PREFIX` больше нет: есть `ETCD_ROOT` + сегменты. Старые ключи из старого
префикса не читаются и удаляются вместе с томом (`make clean`).

## Что умеет и чего не умеет

**Меняется на живом пуле, без пересоздания** — `maximumPoolSize` и `minimumIdle`. Единственный
источник этих двух величин — etcd. Запросы в полёте не страдают.

**Не меняется на живом пуле вовсе** — цель соединения (`jdbcUrl`, `username`, `password`,
`poolName`) и таймауты. Они приходят из локальной конфигурации процесса и меняются только
перезапуском инстанса: MBean такие параметры не принимает, а смены цели из etcd больше нет.
Перед закрытием пула (нулевой размер, остановка процесса) ждём до `drain-on-recreate-timeout`
(3 c), пока доработают активные соединения.

Плохой конфиг не роняет сервис:

| что положили в etcd | что будет |
|---|---|
| `maximumPoolSize=0` | конфиг отклонён целиком (REJECTED, отдельная проверка до нормализации: пулом управляет провизор), пул остался на последних рабочих значениях, трафик не блокируется, причина в логе |
| `maximumPoolSize=banana` | только этот ключ отброшен, соседние ключи применились, проблема в журнале инстанса и в метрике `pool_etcd_problems`. Локальный дефолт максимума — 0, поэтому пул на эти ~20 мс закрывается; провижёр возвращает долю и пул поднимается заново |
| `maxPoolSize=8` (опечатка) | предупреждение «неизвестный ключ» один раз, на конфиг не влияет |
| `jdbcUrl`, `password`, `connectionTimeoutMs` и прочие снятые ключи | то же самое: неизвестный ключ, значение не применяется, пул продолжает работать на локально заданной цели |
| удалили ключ | значение возвращается к локальному дефолту (`maximumPoolSize` → 0: пул закрывается; инстанс без доли — холод) |
| etcd лежит после применения | пул работает на последнем конфиге, готовность не сбрасывается, watch докатывается с backoff'ом |
| etcd лежит до первого применения | инстанс жив, готовность DOWN, /api/work=503; когда etcd вернётся — сам становится готовым |

## Демо, которое стоит пройти

```bash
make up
make pool                        # все 8 готовы, total=25 у каждого (имена — hex-ID контейнеров)

make set-active-max-connections SIZE=120 S=service-a   # бюджет активного флота 120 на 4 инстанса service-a
make budget S=service-a                                # доли 30/30/30/30, сумма 120
make pool                                              # у всех инстансов service-a maximumPoolSize=30

make set-active-max-connections SIZE=60 S=service-a    # 60 / 4 = по 15 у каждого
make set-active-min-connections SIZE=40 S=service-a    # 60 / 40 = 1 -> трое без доли и 503
make budget S=service-a
make set-active-min-connections SIZE=1 S=service-a     # вернуть всех в обслуживание

# неактивный флот: глобальный маркер группы сжимает её во всех сервисах
make set-group-active G=group-2 ACTIVE=false           # узлы group-2 (оба сервиса) -> пул 1, активным + по доле
make budget                                            # group-2: 1 (НЕАКТИВНАЯ группа), активные пересчитаны, сумма = N
make set-inactive-max-connections SIZE=0 S=service-a   # холод: group-2 в service-a без конфигурации, 503, readiness DOWN
make set-inactive-max-connections SIZE=1 S=service-a   # снова тёплый резерв
make set-group-active G=group-2 ACTIVE=true            # вернуть флот: все снова по 25

make registrations               # 8 живых узлов регистрации (hex-ID)

# провижирование: инстантные ключи живут, пока жив узел (I=... из make instances)
docker stop <hex-a>              # узел исчез -> провизор удалил весь префикс hikari/*
make registrations               # 7 узлов
make budget S=service-a          # 3 инстанса делят 100: 34/33/33
make config I=<hex-a>            # пусто — вместе с ручными правками стёрлись все ключи
docker start <hex-a>             # узел вернулся -> провижёр прислал долю бюджета
make config I=<hex-a>            # maximumPoolSize=34 — и больше ничего

# увод трафика: инстанс не готов, балансировщик его пропускает
docker stop <hex-b>
make work                        # {'ok':true} — round-robin по остальным service-a
make pool                        # <hex-b> помечен как не готовый (причина в метриках)
docker start <hex-b>

# состав меняется масштабированием — без правки конфигурации
# (голый --scale одной группы сбросит остальные к 1 — compose-семантика, масштабируй полным набором)
docker compose up -d --scale service-a-group-1=3 --scale service-a-group-2=2 \
  --scale service-b-group-1=2 --scale service-b-group-2=2     # третий инстанс группы-1
make instances                   # 9 инстансов, шестой service-a уже провижен
docker compose up -d --scale service-a-group-1=2 --scale service-a-group-2=2 \
  --scale service-b-group-1=2 --scale service-b-group-2=2     # и снова 8
```

То же самое глазами, без чтения вывода команд. Откройте `localhost:3000`, панель **Бюджет флота**,
переменная `service` = `service-a`, и пройдите переходы `set-active-max-connections` /
`set-group-active` заново:

- «Потолок бюджета» — бюджет, сумма приказанных размеров и оценка занятости; расходятся они в
  переходе, и это норма (место освобождается не сразу);
- «Факт: сессии пулов в базе против бюджета» — правда от postgres: сессии `application_name`
  инстансов сервиса против `N`. Потолок не пробивается даже в момент перехода;
- панель **Провизёр и etcd** — кто ведёт сервис и сработавшие правила (их быть не должно).

Под нагрузкой (`make load-logs`) на панели **Пулы и конфигурация** видно, как расширение пула
одним изменением поднимает `total` и срезает перцентиль ожидания выдачи соединения.

```bash
make targets                     # 4 цели сбора: дверь сигналов, etcd, 2 сборщика баз
make check-instances             # у каждого из 8 инстансов есть ряды в наблюдении
```

Сессии пулов приходят из двух сборщиков (по одному на базу) в одну задачу `postgres`. Ряды не
склеиваются и не дублируются, потому что суммирование идёт по `application_name`, а имя пула
(`POOL_NAME` = имя инстанса = hex-ID) уникально на весь стенд: каждая реплика существует ровно в
одной базе, второму сборщику склеивать нечего. Имена приходят из окружения, поэтому отбор сессий
пулов на панелях и в правиле потолка ведётся **join'ом с метриками пула**, а не шаблоном имён:
сессия, у которой нет пула с таким именем (psql оператора, сборщик базы), в сумму флота не
попадает. Проверка «сумма флота равна бюджету» не держится на формате имени вообще. Ловится это
глазами: `make sessions S=<сервис>` в исправной базе показывает только инстансы своего сервиса.

Как устроен нагрузчик (`loadgen/`, Maven + Spring Boot; логика в `LoadGen.java` тронута только в
отчёте): `WORKERS` виртуальных потоков,
`WORK_MS` — сколько держать коннект в `pg_sleep`, `REPORT_MS` — период отчёта, `DURATION_S=0` —
крутится до `docker compose stop loadgen-a loadgen-b`. Каждая строка отчёта: rps, p50/p95/max,
inflight, ошибки. Состояние пула и сессии postgres в отчёт не входят: они снимаются в наблюдении
(метрики инстанса и сборщика базы, `make pool`), поэтому отчёт одинаков при любом состоянии пула.
`TARGET` — куда долбить (`lb:80` у `loadgen-a`,
`lb:81` у `loadgen-b` — порт выбирает точку входа, то есть сервис). Две точки нагрузки вместо
списка целей в одной — намеренно: у каждой своя гистограмма задержек, и отчёты двух прогонов не
смешивают две базы.

## API

| эндпоинт | что делает |
|---|---|
| `GET /api/work?ms=20` | взять коннект, сделать запрос, поспать в БД; **503**, пока гейт закрыт |
| `GET /actuator/health/readiness` | готовность: гейт конфигурации (`readinessState` + `poolEtcd`) и база |
| `GET /actuator/health/liveness` | живость: только `ping`, от etcd и базы не зависит |
| `GET /actuator/prometheus` | метрики инстанса в текстовом формате prometheus (те же имена, что на витрине) |

С примерами ответа и разбором полей — [docs/api.md](docs/api.md). Состояния пула, конфигурации и
источника отдельной точки API нет: оно в метриках инстанса, трассах и журнале, сводка по флоту —
`make pool`. В `pool_sessions` пулы различаются по `application_name` (равен `POOL_NAME` = имени
инстанса) — view показывает каждый пул отдельной строкой, а число сессий берёт сборщик метрик базы.

## Разработка: spec-driven через OpenSpec

Изменения проектируются до того, как пишется код. Спецификации и планы лежат в `openspec/`,
код — в `service/`.

```bash
openspec list --json                     # состояние спецификаций
openspec new change <kebab-case-name>    # завести изменение
openspec status --change <name> --json   # какие артефакты готовы
openspec validate <name>                 # проверить артефакты
```

Изменение проходит четыре артефакта: `proposal.md` (зачем) → `specs/<capability>/spec.md`
(контракт поведения, дельта к основной спеке) → `design.md` (как) → `tasks.md` (шаги).
В OpenCode это доступно как слэш-команды `/opsx-propose`, `/opsx-apply`, `/opsx-archive`,
`/opsx-explore`, `/opsx-sync`, `/opsx-update`. Артефакты на русском; структурные заголовки и
`SHALL`/`MUST` — английские. Планирование и реализация разнесены: `/opsx-propose` создаёт только
артефакты, код трогается после отдельного запроса на `/opsx-apply`.

проверяются на живом стенде (Testcontainers в проекте нет).

## Решения, которые стоит знать

- **Состав — живые источники, а не перечень.** Списка инстансов в конфигурации нет: число реплик
  группы задаёт `make up --scale`, развёрнутый состав объявляет `docker compose ps`, имя инстанса
  приходит из окружения (`ETCD_INSTANCE → POD_NAME → HOSTNAME`), группа — из `ETCD_GROUP →
  POD_NAMESPACE`. Из живого состава выводятся правила молчания и сверки (`make silence-rules`,
  `make check-instances`, `make check-silence`), поэтому правка состава не требует правки
  наблюдения; единственное место, где число реплик задаётся, — `A_G1..B_G2` в `.env`.
- **Путь собирается из сегментов, а не берётся строкой.** `ETCD_PREFIX` удалён: сервис сам
  строит `{root}/services/{service}/groups/{group}/instances/{instance}/hikari/`, поэтому «сервис
  смотрит в другой префикс, чем провизор» невозможно по построению. Плата: пустые `group`/`instance`
  при включённом etcd — отказ на старте.
- **Балансировщик на метках.** Файлового списка бэкендов нет: Traefik читает состав из
  docker-провайдера, роутер и сервис на каждую точку входа заданы метками на контейнерах.
  Дедупликация идентичных меток реплик — штатное поведение Traefik: реплики группы обслуживаются
  одним роутером. Границу по сервису держит привязка маршрута к точке входа (web-a / web-b).
- **Провижёр пишет по жизни инстанса в etcd ровно один ключ — долю бюджета.** Появление узла
  регистрации → приходит своя доля в `maximumPoolSize`, исчезновение узла → весь префикс `hikari/`
  удаляется вместе с ручными правками. События самих ключей конфигурации провизор игнорирует —
  петель нет. Стартовых ключей, кладённых put-if-absent, больше нет: из etcd читается только
  размер, а цель соединения и таймауты приходят из локальной конфигурации процесса.
- **Провижер — это две реплики с выборами лидера по сервису** (`{root}/provisioner/leader/{service}/`),
  а не один процесс: набор сервисов выводится из живых узлов дерева (списка в конфигурации нет),
  роли симметричны, перехват краха лидера — в пределах TTL аренды. Записи идемпотентны, поэтому
  окно «двух писателей» при перехвате безопасно.
- **Гейт трафика живёт в источнике конфигурации**: открывается первым распознанным ключом и
  закрывается, когда распознанных ключей не осталось (провижер снял конфигурацию). Живость
  процесса от etcd не зависит (`liveness` = `ping`).
- **Пул создаётся из первой принятой конфигурации etcd.** Локальный размер жёстко 0 — до
  конфигурации пула нет, с первым снимком он создаётся на своей доле, целевой ноль (инстанс без
  доли, холодный флот) закрывает его с дренажом. `ManagedPool` реализует `DataSource` и
  делегирует вызовы живому `HikariDataSource`: `JdbcTemplate` и менеджер транзакций следуют за
  подменой пула сами, без пересоздания.
- **Группы — глобальный флот: маркер в корне выключает их во всех сервисах.** У каждого сервиса
  свои N, m и R; неактивная группа держит пул ровно R (тёплый флот) или не имеет конфигурации
  вовсе при `R=0` (холодный). Маркер читается поллингом ~1с, обрыв etcd держит последнее
  состояние.
- **`minimumIdle` по умолчанию следует за `maximumPoolSize`** (как в HikariCP). Иначе сжатие пула
  падало бы с `minimumIdle > maximumPoolSize`.
- **Снимок + watch с `revision + 1`.** Разрыва между чтением и подпиской нет; любой обрыв
  приводит к новому снимку.
- **`eager-fill-on-resize=true`** (дефолт стенда) — коннекты после увеличения добиваются сразу.
  В проде обычно `false`.
- **`initialization-fail-timeout=-1`** — сервис поднимается, даже если БД ещё не готова.
- **`mem_limit: 512m` на инстанс** — 8 JVM без лимитов разнесли бы хост.
- **Пароль подключения в etcd не хранится**: ключ `password` не входит в перечень распознаваемых,
  то есть считается опечаткой и не применяется. Пароль приходит из `DB_PASSWORD` (окружение
  инстанса); в наблюдаемом состоянии источника значение `password` всё равно маскируется как `***`
  на случай, если такой ключ всё же появится.
