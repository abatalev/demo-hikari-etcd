# AGENTS.md

Инструкции для агентов, работающих в этом репозитории. Читать до того, как что-либо менять.

## Что это

Прототип сервиса, у которого размер пула соединений HikariCP к PostgreSQL 16 настраивается
на лету правкой ключа в etcd. Compose-стенд: postgres, etcd, сервис, провизор конфигурации,
нагрузчик, образ с etcdctl.

Стек: Spring Boot 3.5.16, HikariCP 6.3.3, jetcd 0.8.7, Java 21, Maven, PostgreSQL 16, etcd 3.6.15.
Сервис (пул, конфиг-источник, API) — `service/`, провизор конфигурации — `provisioner/`.
Нагрузчик — `loadgen/LoadGen.java`, один файл на голом JDK, без зависимостей.

Схема и обзор — [README.md](README.md), подробности — в [docs/](docs/):
[mechanism.md](docs/mechanism.md) (путь `put` → resize), [api.md](docs/api.md),
[experiments.md](docs/experiments.md) (замеры), [operations.md](docs/operations.md) (troubleshooting).

## Спецификация: OpenSpec

Работа идёт spec-driven. Планирующих артефактов в `openspec/`, а кода — в `service/`.

```bash
openspec list --json          # есть ли openspec-корень
openspec new change <kebab-case-name>
openspec status --change <name> --json      # что готово, что заблокировано
openspec validate <name>                    # проверка артефактов
```

Внутри OpenCode доступны слэш-команды: `/opsx-propose`, `/opsx-apply`, `/opsx-archive`,
`/opsx-explore`, `/opsx-sync`, `/opsx-update`.

Основные спеки в `openspec/specs/` описывают текущее поведение системы. Прежде чем предлагать
изменение, найди нужную capability и прочитай её требования — новое требование не должно
противоречить существующему, а расхождение поведения и спеки само по себе повод на изменение.

| capability | о чём |
|---|---|
| `pool-lifecycle` | создание, ресайз без пересоздания, сжатие, добивка, recreate с дренажем |
| `etcd-config-source` | путь `{root}/services/{service}/groups/{group}/instances/{instance}/hikari/`, валидация сегментов, снимок+watch, обрывы, статус источника |
| `config-validation` | приоритет источников, диапазоны, поведение при ошибочных значениях |
| `pool-observability` | HTTP-контракт наблюдения, гейт готовности, нагрузочная точка |
| `traffic-readiness` | инстанс не принимает трафик до конфигурации из etcd; 503; liveness свободна от etcd |
| `demo-stand` | compose-стенд из 8 инстансов, балансировщики, реактивное провижинирование, нагрузчик |
| `instance-registration` | узел `.../instances/{instance}` в etcd: создаётся при старте на аренде, исчезает при остановке (revoke/TTL), переживает обрывы, на готовность и конфиг-воркер не влияет |
| `config-provisioner` | провизор: бюджет активного флота делится между активными инстансами сервиса, неактивные (по глобальному маркеру `{root}/groups/{group}/active`) держат резерв R (0 = холод); ключи конфигурации ⟺ живой узел регистрации, получивший долю; DELETE/TTL → весь префикс `hikari/` удаляется; сверка на старте и после обрывов |
| | две реплики, лидер выбирается по сервису через `{root}/provisioner/leader/{service}/` |

Правила, которые нельзя нарушать:

- **Артефакты планирования пишутся на русском** (`openspec/config.yaml`), но структурные
  заголовки (`## Purpose`, `### Requirement:`, `#### Scenario:`) и ключевые слова SHALL/MUST
  остаются английскими. Сценарии — строго `####` (четыре решётки), иначе валидация падает тихо.
- **Спека — это контракт поведения, а не план реализации.** В `spec.md` не указывать имена
  классов, выбор библиотек и пошаговость. Если реализацию можно поменять, не меняя внешнего
  поведения, этого в спеке быть не должно.
- **Каждое требование обязано иметь хотя бы один сценарий.** Требование без сценария — ошибка.
- **Планирование и реализация разнесены.** `/opsx-propose` только создаёт артефакты; код
  трогается лишь после отдельного запроса на `/opsx-apply`.
- **Изменение без изменения поведения** (рефакторинг, тулинги, документация) обязано ставить
  `skip_specs: true` в `.openspec.yaml` изменения. Не выдумывать требование ради прохождения
  валидации.
- **Изменение существующего требования** оформляется как `## MODIFIED Requirements` с полным
  текстом требования, а не только правкой. Путь capability берётся из `openspec list --specs`.

## Сборка и запуск

```bash
make up        # весь стенд (нужны docker, make, curl, python3)
make test      # юнит-тесты, нужен maven
make down      # остановить; make clean — вместе с томами
make pool      # состояние пула + конфиг + сессии postgres
make leader    # кто ведёт каждый сервис (лидер выборов провизора)
make budget    # бюджет сервиса: N, m, R, маркеры групп, доли по инстансам и их сумма
make targets   # состояние целей сбора метрик (Prometheus на :9090, Grafana на :3000)
make test      # + сверка списка целей с ETCD_INSTANCES и promtool check config/rules
```

Размер пула задаётся бюджетом активного флота: `make set-active-max-connections SIZE=100 S=service-a`
(N) и `make set-active-min-connections SIZE=15 S=service-a` (минимальная активная доля m); резерв
неактивного флота — `make set-inactive-max-connections SIZE=1 S=service-a` (R, `0` = холод),
активность группы — `make set-group-active G=group-2 ACTIVE=false` (глобальный флот). Остальные
правки: `make set-min-idle SIZE=3`, `make unset-min-idle`, `make set-conn-timeout SIZE=1000`,
`make config`. `make set-size`, `set-service-size`, `set-group-size` — оверайды
`maximumPoolSize` в обход бюджета, живут до ближайшего пересчёта.

Перед тем как объявлять работу готовой, проверь на живом стенде, а не по коду.

## Инварианты, которые нельзя нарушать

Это ошибки, которые уже находили и чинили. Ломать их — регрессия.

**`ManagedPool` реализует `DataSource` сам и никогда не отдаёт наружу `HikariDataSource`.**
Отдадите — `JdbcTemplate` и менеджер транзакций захватят конкретный пул и перестанут следовать
за подменой при пересоздании. Переключение пула идёт через `AtomicReference`.

**`apply()` синхронизирован.** Два события etcd не должны применяться одновременно.

**При уменьшении пула `minimumIdle` ставится первым, потом `maximumPoolSize`.** Иначе
`setMaximumPoolSize` упадёт на `minimumIdle > maximumPoolSize` и не применится весь конфиг,
включая валидные таймауты. Обратный порядок — при увеличении.

**После сжатия вызывается `softEvictConnections()`.** Новый лимит применяется сразу, а лишние
idle-соединения иначе висят до HouseKeeper (~30с), и `total` в API показывает неверное число.

**`eagerFill` обязан удерживать соединения одновременно.** Если взять коннект и сразу вернуть,
HikariCP отдаст то же idle-соединение и `total` не вырастет. Собирать в список, возвращать
разом в `finally`. Дедлайн обязателен, иначе насыщенный пул задержит watch-поток.

**Перед закрытием старого пула — дренаж.** `HikariDataSource.close()` убивает активные соединения
и запросы в полёте падают с 08006. Сначала `softEvictConnections()`, потом ожидание до
`drain-on-recreate-timeout`. Без этого пересоздание ломает трафик.

**Watch стартует с `revision + 1` ответа снимка.** Иначе появляется окно потерянного обновления
между `get` и подпиской.

**Обрыв etcd не должен влиять на пул.** Пул живёт на последнем применённом конфиге, watch
докатывается с backoff'ом. Сервис не падает ни на старте без etcd, ни при его падении.

**`minimumIdle` по умолчанию следует за `maximumPoolSize`.** Иначе сжатие пула падает.

**Гейт трафика: без распознанных ключей `/api/work` отвечает 503, а `/actuator/health/readiness` —
DOWN; `/api/pool` и `/api/config` при этом работают.** Гейт открывается первым распознанным
ключом и закрывается, когда распознанных ключей не осталось (провижер снял конфигурацию — инстанс
потерял долю бюджета или стал частью холодного флота `R=0`); при возврате ключей трафик открывается
снова. Тёплый флот (`R ≥ 1`) конфигурацию получает и обслуживает трафик на резервном размере —
гейт для него открыт. Закрытие происходит только по
реальным событиям удаления и снимкам при живом etcd: обрыв etcd ни трафик, ни готовность не
сбрасывает — недоступное хранилище событий не шлёт вовсе. Отклонённый конфиг (REJECTED) гейт не
удерживает.

**Живость от etcd не зависит.** `liveness` — только `ping`; `readiness` = `readinessState,db,poolEtcd`.
Compose-healthcheck и `make up` смотрят в `/actuator/health/readiness`, а не в общий `/health`.

**Валидация сегментов пути — только при `pool.etcd.enabled=true`.** Пустые `group`/`instance`
при включённом источнике валят старт с именем сегмента; при выключенном (`ETCD_ENABLED=false`)
путь не собирается и ничего не проверяется. Правила — в чистой функции `EtcdKeyPath`.

**`POOL_NAME` каждого инстанса уникален (= имени инстанса).** Иначе `application_name` у всех пулов
одинаковый и view `pool_sessions` склеит восемь пулов в одну строку.

**Регистрация инстанса не трогает конфиг-воркер и готовность.** Узел `.../instances/{instance}`
лежит вне префикса `hikari/` — снимок и watch его не видят, «неизвестный ключ» не логируется,
гейт не дёргается. Keepalive идёт в отдельном потоке `etcd-registration`, а не в
`etcd-config-watch`; при штатной остановке аренда отзывается в `stop()` до закрытия клиента
(revoke — узел исчезает сразу), при падении — по TTL. `ETCD_ENABLED=false` — регистрации нет.

**Провижер добавляет ключи только атомарным txn «ключа нет → put» (`create_revision == 0`).**
Никаких слепых `put`: существующее значение (в том числе ручная правка оператора) никогда не
перезаписывается, пока жив узел. События и ключи `hikari/*` провизор игнорирует — свои записи не
порождают петель. Узел — единственный автор ключей конфигурации.

**Размер пула — доля сервисного бюджета, и делит его провижёр.** Ключи
`{root}/services/{service}/activeMaxConnections` (N) и `.../activeMinConnections` (m) создаются
put-if-absent дефолтами `PROV_ACTIVE_MAX_CONNECTIONS`/`PROV_ACTIVE_MIN_CONNECTIONS`, резерв
неактивного флота `.../inactiveMaxConnections` (R) — дефолтом `PROV_INACTIVE_MAX_CONNECTIONS`, и все
три **переживают опустение сервиса** — иначе rolling update с окном без живых узлов сбросил бы
бюджет оператора на дефолт. Группы разделяются на активные и неактивные по глобальному маркеру
`{root}/groups/{group}/active` (чистый `GroupFleetKey`: «false» в любом регистре = неактивна,
отсутствие/мусор = активна). Формула (чистый `PoolSizeDistribution` — **он не менялся**):
`k` неактивных получают ровно R, активные делят `N' = N − R×k`: `serve = min(n_акт, N' div m)`,
`доля = N' div serve` и `+1` первым по сортировке полного ключа, усечение до `PROV_MAX_SHARE`.
`n_акт × m ≤ N'` ⇒ равномерный сплит сам даёт каждому ≥ m, отдельной ветки нет. Сумма долей
активных + резерв неактивных = N — потолок защищает `max_connections` postgres. Отказ fail-closed
(`N < m`, `m > PROV_MAX_SHARE`, `R` вне `{0} ∪ [1..200]`, `R×k > N`, активные есть и `N' < m`,
не-число): ничего не менять, WARN с числами. Инстанс без доли теряет конфигурацию целиком →
503 и `readiness: DOWN`. Снятие конфигурации закрывает гейт трафика (по удалению ключей —
см. инвариант «Гейт трафика»), поэтому инстанс без доли действительно не обслуживает.

**`maximumPoolSize` перезаписывается при расхождении с долей, при равенстве записи нет.**
Условие txn инвертировано: `If(значение == доля)` → обходная ветка пуста (записи нет), `Else` —
put. Так ловится и отсутствующий ключ: сравнение значения с несуществующим ключом в etcd никогда
не проходит, поэтому `Else` создаёт ключ (`NOT_EQUAL` для этого не годился). Один поход в etcd, две
реплики в окне перехвата лидерства пишут одно и то же — записи идемпотентны. Остальные ключи
инстанса остаются put-if-absent, ручные правки переживают. Значение 0 провизор узлу не напишет
(неактивный холодный узел теряет ключи целиком — инвариант «Провижер удаляет …»), а вручную
записанный 0 сервис отклоняет до нормализации: пулом управляет провизор.

**Провижер удаляет весь префикс `hikari/` у узла, который исчез или выпал из состава, и
осиротевшие префиксы при сверке.** `DELETE` узла (стоп/краш/TTL) → `del --prefix` по
`.../{instance}/hikari/`, ключи, добавленные вручную, тоже удаляются. Инстанс без доли
бюджета и неактивный узел при `R=0` (холодный флот) — тот же случай: конфигурация снимается
намеренно, иначе он обслуживал бы трафик вопреки потолку. Сверка (снимок `{root}/services/`) на
старте и после каждого обрыва: живым узлам доли и стартовые ключи, лишним префиксам — очистка.
Обрыв etcd пул/конфиг инстанса не ломает — это домен провизора.

**Переходы бюджета: рост ждёт освобождения, и место раздаётся один раз.** Инстанс публикует
`{instance}/unreleasedConnections` = `max(0, held − maximumPoolSize)` — неотрицательный, поэтому
завышенная оценка лишь придерживает рост. Публикация по изменению, **терминальный ноль проходит
безусловно** (на нём держится разблокировка роста), а после **любого** применённого изменения
конфигурации значение переписывается заново, даже если не изменилось: etcd поднимает
`mod_revision`, и только так отчёт перестаёт быть «от прежнего потолка». Проверка
`mod_revision(отчёт) > mod_revision(maximumPoolSize)`; иначе — худший случай, инстанс держит
свой потолок. Провижёр: `занято = потолок + долг`, `рост = max(0, N − сумма занято)`,
`приказ = min(доля, потолок + рост)` — и **рост уменьшается на выданное в порядке сортировки
полного ключа**. Не уменьшать — флот занимает `N + рост×(число растущих)`, при этом сумма команд
остаётся ≤ N, и проверка «сумма команд ≤ N» это пропускает; проверять надо «что флот будет держать
сразу после прохода» (растущий добирает приказанное сразу, сжимаемый держит своё до нуля долга) —
именно на ней падает юнит-тест на случайных снимках. Пока долг ненулевой, инстанс вытесняет
всё, что оказалось сверх потолка: иначе лишнее соединение ждёт запроса, который может не
прийти, и место занято навсегда. **При остановке сначала дренаж, потом revoke** — иначе место
освобождается повторно, пока останавливающийся ещё держит соединения. Превышение воспроизводится
только под нагрузкой (без неё сжимающие успевают отпустить раньше, чем растущие добирают), мерять
надо непрерывно на 10 Гц по сессиям postgres: `scripts/measure-fleet.sh`.

**Маркеры групп — глобальный флот, читается поллингом, а не событиями.** Ключ
`{root}/groups/{group}/active` общий для всех сервисов: «false» (в любом регистре) выключает
группу во всех сервисах, отсутствие/мусор/«true» — активна. Читается отдельным потоком воркера
~1с (`GROUP_POLL_MS`), старт/стоп вместе с воркером; изменение маркера пересчитывает **только**
сервисы, содержащие узлы группы. Обрыв etcd держит последнее известное состояние маркеров:
недоступное хранилище не порождает новых состояний активности. Маркер лежит вне `{root}/services/` —
в снимок и watch воркера не попадает, «неизвестный ключ» не логируется. R=0 → неактивные узлы не
получают конфигурации вовсе; `R ≥ 1` → пул ровно R и трафик продолжает обслуживаться.

**Провизор — тоже снимок + watch с `revision + 1`.** Окна между снимком и подпиской нет
(тот же аргумент, что у конфиг-источника). Backoff 1→30с, сервис не падает ни на старте без
etcd, ни при его падении. Сверка/события провизора юнит-тестами не покрыты — проверять на стенде.

**На каждый сервис активна ровно одна реплика провизора, и её выбирают выборы, а не конфигурация.**
Лидер — ключ с наименьшим `create_revision` в префиксе `{root}/provisioner/leader/{service}/`
(ключ = `prefix/<hex аренды>`, значение = `PROV_NAME`); набор сервисов выводится из живых узлов
дерева (чистая `InstanceKey.liveServices`), списка в конфигурации нет. Ключи выборов лежат **вне**
`{root}/services/` — в снимок и watch воркера не попадают, «неизвестный ключ» не логируется.
Воркер на поддерево сервиса стартует и останавливается лидерством (один watch-поток на сервис);
потеря аренды (keepalive-сторож) останавливает все воркеры немедленно. Записи идемпотентны
(txn «ключа нет → put»), поэтому окно «двух писателей» при перехвате безопасно, fencing не нужен.
Смотреть: `make leader`.

**Метрики снимает сам процесс, а состояние пула — из `runtime()`, а не из SPI.**
`/actuator/prometheus` есть и у сервиса, и у провизёра (`micrometer-registry-prometheus` из BOM).
Через SPI HikariCP (`HikariEventMetrics`) идут **только события**: создание соединения, ожидание
выдачи, удержание, таймаут. Всё состояние (размер, соединения, поколение, неосвобождённое сжатие,
конфиг, гейт, признаки etcd) берётся из `runtime()` и живёт без пула — пул `null` отдаёт нули.
Гейджи состояния в SPI публиковать нельзя: `PoolStats`, который приходит в
`create(poolName, poolStats)`, — снимок **первого** поколения, поэтому штатный Micrometer-трекер
HikariCP после recreate или снятия конфигурации навсегда показывает ноль (стенд именно это и
делает, переходя холодной группой туда и обратно).

**Общие признаки задаёт окружение, метка `instance` — неприкосновенна.** У сервиса это `service`,
`group`, `node` (`SERVICE_NAME`/`ETCD_GROUP`/`ETCD_INSTANCE`) через `management.metrics.tags`, у
провизёра — `replica` (`PROV_NAME`, то же значение, что в ключе выборов). Метку `instance` не
заводить: Prometheus использует её для адреса цели, и ряд с признаком `instance` всегда получит
`exported_instance`. Метку `pool` на приборах событий тоже не заводить: пул в процессе один, его
уже называет `node`, а приборы событий переиспользуются по имени, чтобы после recreate история
не распалась на два ряда.

**Значения конфигурации метриками не публикуются.** Пароль в etcd лежит открытым текстом, и
признаки-значения ещё и размножили бы кардинальность. Вместо них: числовые гейджи применённых
величин, состояние из закрытого набора (`pool_config_state{state=none|applied|rejected}`) и
счётчики. Причина неготовности — тоже закрытый набор
(`pool_not_ready_reason{reason=none|no_config_keys|etcd_unavailable}`), причём `none` = 1, когда
причины нет (гейт открыт или источник выключен): иначе «нет причины» и «причина неизвестна»
неразличимы. Текст для человека выводится из того же кода состояния (`NotReadyCause.describe`),
а не хранится рядом.

**Ряды провизёра — на сервис, не на узел.** `provision_fleet_*` несут признак `service`, метрик на
инстанс нет намеренно: узлы появляются и исчезают, а признаки в реестре метрик живут до явного
снятия. Подробности по узлам остаются в журнале, в etcd и в `make budget`/`make fleet-sessions`.
Провал чтения ряда в сборщике — это ноль и запись в лог, а не оборванный весь остальной сбор.

**Признаки лидерства и устаревания снимаются на неуспешном пути, а не только ставятся на успешном.**
`provision_leader` и `provision_tree_stale` нельзя публиковать только после выигранных выборов и
полученного снимка: при обрыве etcd провизёр теряет аренду и останавливает воркеры, величины
флота застывают — а признаки молчали, и наблюдение утверждало «ведёт, снимок свежий» у процесса,
который не делает ни того, ни другого. `stopAllWorkers()` гасит `provision_leader` у всех сервисов
разом, `ProvisioningWorker.stop()` ставит `tree_stale = 0→1`. Величины при этом **не обнуляются**:
конфигурация и пул живут на последнем применённом состоянии. Правил на staleness нет и это
осознанно — обрыв etcd не должен превращаться в крик.

**Публикация неосвобождённого сжатия обязана повторяться при смене аренды.** Ключ публикации
живёт на аренде узла регистрации и умирает вместе с ней. После обрыва etcd аренда истекает, ключ
исчезает, инстанс при переподключении получает новую. Если считать прежний ноль опубликованным
(«значение не изменилось → не публикуем»), он больше не повторится, провижёр вечно увидит худший
случай (потолок) — и место флота не перераспределится **никогда**: сценарий «выключить группу и
включить обратно» оставлял флот на 75 из 100 с узлом без доли и без гейта. Поводов к публикации
три, все в `DrainDebtPolicy` (чистая функция, тестируется без etcd): изменение величины, применение
новой команды, смена аренды.

**Максимум оценки занятости живёт в провизёре и обнуляется пересчётом состава.**
`provision_fleet_sum_held_peak_since_reset` копится с максимумом при пересчёте по публикации и
сбрасывается на текущую оценку при **полном** пересчёте состава (`provision(c, tree, true)`).
Оценка занятости — верхняя оценка и законно выше бюджета, пока инстанс не подтвердил освобождение
публикацией: до подтверждения долг узла равен его потолку (`ConnectionGrowth.debt`). **Алертить на
`provision_fleet_sum_held_estimate` и на её максимум нельзя** — на штатном перезапуске флота максимум
доходит до `N + одна доля`, и это ложное срабатывание, а не нарушение (проверено на стенде).
**Зависшее сжатие считается только по подтверждённым публикациям**: узел без такой публикации не
входит в `provision_fleet_stuck_shrink_nodes`, иначе правило о зависшем сжатии кричало бы на каждом
штатном перезапуске флота, где публикаций нет ни у кого. Правило использует текущее число узлов
(гейдж), а не счётчик предупреждений — только так оно снимается сразу после устранения причины.

**Потолок проверяется по факту, а не по оценке провизёра.** Нарушение — это когда флот держит в базе
больше N: `FleetConnectionsExceedBudget` считает сессии пулов сервиса в postgres
(`pg_stat_activity_count` по `application_name`, равному имени инстанса) и сравнивает с бюджетом;
`FleetCommandsExceedBudget` ловит ошибку учёта (`provision_fleet_sum_ceilings > N`). Признак
`service` для сессий берётся из метрик самого инстанса (`group_left` по `node`), а не разбирается из
имени: иначе правило молчало бы вхолостую при смене соглашения об именах. Отбор сессий идёт по
шаблону `application_name=~"service-.+"` — он и переменная `$pool_app` на панели правятся вместе.

**Правила проверяются promtool дважды, а не только на синтаксис.** `check config`, `check rules` и
`test rules` (`prometheus/rules/stand.test.yml`) в составе `make test`: последнее требует, чтобы
правило **молчало на норме и срабатывало на нарушении**. Про «молчит всегда» проверка не узнаёт —
это тихая дырка, а не ошибка. Учесть, что `rule_files` в `prometheus.yml` указывает на `stand.yml`
явно: рядом лежит `stand.test.yml`, и сборщик не отличил бы его от правил (промолчал бы).

**Наблюдение не входит ни в одну цепочку `depends_on`.** Prometheus, `postgres-exporter` и Grafana
не условие готовности инстансов: недоступность наблюдения не должна ронять подъём стенда и
обслуживание трафика. `scripts/wait-ready.sh` ждёт их отдельно и коротко, сообщает состояние и на
код возврата не влияет. Плата: «метрики есть» не защищает подъём, поэтому список целей проверяется
явно — `make check-targets` (в `make test`) и `make targets`.

**Список целей сбора выводится из `ETCD_INSTANCES`, а не живёт отдельно.** `prometheus/targets.json`
генерируется `make prometheus-targets` (`scripts/targets.py`) и зафиксирован в репозитории, чтобы
сборщик поднимался и без make; расхождение с `.env` ловит `make check-targets`. Признаки
`service`/`group`/`node` целям не задаются: их и так отдаёт сам инстанс, а переопределение метки
создало бы ряд `exported_*` при расхождении.

**Панели витрины только на чтение.** Поставщик запрещает сохранение (`allowUiUpdates: false`),
поэтому правка в интерфейсе перезаписывается при рестарте — это осознанно и описано в
`docs/operations.md`, иначе стенд тихо разъезжается с репозиторием.

**Порядок старта в compose не важен.** У инстансов нет `depends_on` на провизор: конфигурация
нагоняется по факту регистрации узла. Окно «зарегистрирован, но ещё не провижен» — нормальное
состояние, закрывается гейтом трафика.

## Подводные камни

- **`ETCD_INSTANCES` — канонический список инстансов, живёт в `.env`** (`service|group|instance|port`).
  Его читают compose (напрямую) и Makefile (`-include .env`). Фолбэк-дефолт
  продублирован в `docker-compose.yml` и `Makefile` на случай отсутствующего `.env` — **не правь
  его**, правится `.env`. Провижеру список не нужен — он адресуется по сегментам пути узла
  регистрации. Расхождение между кортежами и блоками `service-*` в compose видно через
  `make instances`; менять порты инстансов в `ETCD_INSTANCES` нужно синхронно с `docker-compose.yml`.
- **Штатный Micrometer-трекер HikariCP (`com.zaxxer.hikari.metrics.micrometer`) в поставке 6.3.3
  есть и даёт неверные значения после recreate.** Он вешает гейджи на `PoolStats` первого
  поколения: после пересоздания пула или снятия конфигурации они читают закрытый пул и показывают
  ноль навсегда. Поэтому SPI-адаптер публикует только события, а состояние идёт из `runtime()`.
- **Micrometer молча склеивает регистрации с одинаковым id.** Три регистрации `Gauge.builder` с
  одним именем и одним набором признаков дают один ряд с последним значением — ошибка выглядит
  как «значение прыгает». Для рядов из закрытого набора (`pool_config_state`,
  `pool_not_ready_reason`) набор признаков должен быть полным, иначе теряется половина рядов.
- **Таймер SPI без заданных границ уходит в summary, и панель перцентилей молчит без ошибки.**
  `Timer.builder(name).register(...)` даёт `_count`/`_sum`/`_max`, `histogram_quantile` по
  `_bucket` возвращает пусто, и это выглядит как «нагрузки нет». Нужен
  `publishPercentileHistogram()` + `serviceLevelObjectives(Duration[])` (в Micrometer 1.15 только
  `Duration[]`, `double[]` не подходит) и `register()`, а не `registry.timer()`: конфигурация
  гистограммы действует только при первой регистрации. Micrometer достраивает границы геометрически
  между заданными — их выходит около 80 на прибор, это нормально, ряды с одним признаком `le`.
- **Точка метрик приложения — `/actuator/prometheus`, а не `/metrics`.** Без `metrics_path` в
  задаче сборщика все цели отдают 404 и выглядят как «наблюдение не работает».
- **`Timer.totalTime(TimeUnit)`**, а не `Duration`; лямбда-поставщик гейджа принимает
  `Supplier<? extends Number>` — тернарник `long`/`int` с автоупаковкой в `Number` не подходит.
- **Прибор, созданный в инициализаторе поля через `registry`, не компилируется** (поле
  инициализируется раньше конструктора) — создавать приборы в конструкторе.
- **`docker compose run … prometheus promtool …` не сработает**: у образа сборщика `ENTRYPOINT
  ["/bin/prometheus"]`, нужен `--entrypoint promtool`.
- **Поставщик файлов Grafana читает `/etc/grafana/dashboards`, а не `/var/lib/grafana/dashboards`** —
  путь в `grafana/provisioning/dashboards/stand.yml` и точка привязки в compose должны совпадать.
- **Панель с несколькими целями в формате таблицы схлопывается**, если у запросов разные наборы
  признаков: ряды `provision_fleet_*` у ведущей и ведомой реплики надо брать как
  `max by (service)`, иначе в таблице будут лишние строки с нулями.
- **`ALERTS{alertstate="firing"}` без alertmanager никуда не уходит** — правила молчат, и это
  правильно; состояние смотрится в панели правил витрины. Удалённое правило ещё до 5 минут видно в
  `ALERTS`: сборщик не дописывает новые точки, а запрос отдаёт последнюю в пределах lookback.
- **Прометеус не принимает скобки вокруг `and`/`or`**: `sum by (service) (a and on(x) b)` — ошибка
  разбора «no grouping allowed for and operation». Признаки переносят арифметикой:
  `a * on(node) group_left(service) count by (node, service) (pool_maximum_pool_size)`.
- **YAML не любит двоеточие в некавыченном значении**, в том числе в `name` теста правил:
  `- name: потолок в норме: …` не парсится — имя надо брать в кавычки.
- **`make stress` без явного `DURATION_S` ограничен 20 секундами** (см. `Makefile`), бесконечный
  прогон — это loadgen-сервис (`docker compose stop loadgen`). Раньше `make stress` молча висел:
  `DURATION_S ?= 0` всегда непустой, и `$(or $(DURATION_S),20)` был мёртв.
- **Превышение бюджета воспроизводится только под нагрузкой.** Без неё сжимающие успевают отпустить
  соединения раньше, чем растущие добирают своё (выигрывает задержка JVM и eager fill), и переход
  проходит даже на сборке без ограничения роста. Проверять надо под нагрузкой и непрерывно: 4 Гц
  пропускает короткий пик, нужен 10 Гц (`scripts/measure-fleet.sh`).
- **`max_connections` на стенде поднят до 300** (`docker-compose.yml`): сумма флота ровно 200, и
  без запаса пик перехода упирался в базу — соединения не создавались, превышение не измерялось.
- **`etcd.problems` не очищается** при исправлении значения — работает как журнал за всё время
  процесса, а не «что сломано сейчас». Текущее состояние смотреть в `pool`/`config`.
- **В образе etcd нет `/bin/sh`**, поэтому ручные правки идут через отдельный образ `etcd/` на
  alpine с `etcd-ctl` (`docker compose run --rm --no-deps etcdctl put …`). Стартовые ключи
  провизёр кладёт через txn «ключа нет → put», а `maximumPoolSize` — управляемый: перезаписывается
  долей бюджета.
- **`etcdctl del <key> [range_end]`** — второй аргумент это *конец диапазона*, а не список
  ключей.
- **`EtcdKeysTest`, `EtcdKeyPathTest` и `HikariSettingsTest` покрывают только чистые функции.**
  `ManagedPool` и watch-цикл (сервис и провизор) тестами не покрыты; для них нужен Testcontainers.
  Не выдавай отсутствие теста за доказательство, что путь не сломан, — проверяй на стенде.
- **Выборы — это поллинг, а не событийный механизм.** Каждая реплика каждую ~1с делает снимок
  дерева сервисов и кампанию по каждому живому сервису + keepalive аренды раз в TTL/3 — при
  N сервисах и M репликах это O(N·M) txn/JSON-снимков в секунду. На восьми инстансах незаметно,
  на сотнях сервисов надо поднимать период поллинга.
- **Лидер выбирается по `create_revision`, а не по алфавиту.** Ключ кампании — `prefix/<hex
  аренды>`, лидер — старейший живой. Строковый порядок ключей ничего не говорит о лидере:
  `make leader` читает `create_revision` из `-w json`.
- **Рестарт реплики разворачивает роли, и это норма.** Новый ключ получает бо́льший
  `create_revision` и стартует фолловером; предпочтительного лидера нет. Не диагностируй
  «перемещение лидерства» как перехват.
- **Окно перехвата при крахе лидера — TTL + ~1с поллинга фолловера.** В этом окне формально
  могут «писать двое» (записи идемпотентны — безопасно). Штатная остановка перехватывается
  сразу (revoke до закрытия клиента). Обрыв etcd дольше TTL/3 убирает лидера раньше — keepalive-
  сторож останавливает воркеры немедленно.
- **`maximumPoolSize` — управляемый ключ, ручная правка держится недолго.** Провизёр приводит
  его к доле при каждом пересчёте: смена бюджета или маркера группы, появление или исчезновение
  инстанса, рестарт провизёра, обрыв etcd. Правка остальных ключей (например `minimumIdle`)
  держится, пока жив узел, — её сносит только GC по узлу регистрации. `make set-size` и его
  варианты — оверайд для показа, а не способ задать размер пула; задавать нужно
  `make set-active-max-connections`.
- **Инстанс без доли пула не имеет вовсе.** Локальный дефолт размера жёстко 0
  (`maximum-pool-size: 0`, env `POOL_MAX_SIZE` нет): пул появляется только из конфигурации etcd,
  а целевой ноль (инстанс без доли, холодный флот `R=0`) закрывает его с дренажом. Гейт трафика
  закрыт (503, `readiness: DOWN`), соединения к базе открыть нечем — потолок защищён полностью.
- **Кто обслуживает в дефиците — лексикографический порядок ключа узла, а не возраст.** При
  `n_акт × m > N'` (N' = N − R×k) долю получают первые `floor(N'/m)` активных узлов в порядке
  сортировки полного ключа; кто именно выпадет при rolling — не «самый старый», а «первым по имени».
- **Сервисные ключи бюджета удаляются только руками.** `activeMaxConnections`/`activeMinConnections`/
  `inactiveMaxConnections` провизёр не чистит никогда, поэтому бюджет может пережить все инстансы
  сервиса и вернуться к старому значению при следующем развёртывании — это осознанно (rolling), но
  сбивает с толку: проверяй `make budget`, а не инстантные ключи.

## Стиль

- Комментарии, логи и сообщения об ошибках в коде — на русском, как сейчас. Идентификаторы —
  английские.
- Пароль не должен попадать в логи и в API: `HikariSettings.redacted()` для ответов,
  `EtcdStatus` маскирует значение ключа `password` в `***`.
- Валидация настроек — в одном месте (`HikariSettings.normalize()`), жёсткие нарушения бросают
  `InvalidSettingsException`, мягкие дают warning и чинят значение. Не размазывай проверки
  по вызывающему коду.
- Не-число в etcd игнорируется только для своего ключа, остальные применяются — не ломай это:
  одна опечатка не должна блокировать правку соседнего ключа.
- Неизвестные ключи в пути логируются один раз как опечатка, молча игнорировать их нельзя.

## Чего в проекте нет

Не выдавай это за работающие возможности: нет TLS и аутентификации к etcd, пароль лежит в etcd
открытым текстом, нет ACL на путь (конфиг под каждый инстанс пишется отдельно; `S=`/`G=` в
Makefile — ручная группировка, а не репликация), нет доставки алертов (alertmanager не подключён:
правила срабатывают и видны в панели витрины, но уходить им некуда), нет долговременного хранения
метрик (retention 2ч, тома нет), watch-поток один и блокируется на eager fill и дренаже.
Метрики в prometheus-формате, Prometheus с правилами и витрина в стенде **есть** — не выдавай их
за отсутствующие, но и не выдавай за наблюдение с доставкой уведомлений.
Полный список — [docs/operations.md](docs/operations.md).
