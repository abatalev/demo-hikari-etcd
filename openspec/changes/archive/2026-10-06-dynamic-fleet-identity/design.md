# Design

## Context

Состав стенда, идентичность инстансов и бэкенды балансировщика заданы статическим перечнем
`ETCD_INSTANCES` в `.env` (восемь кортежей «сервис|группа|инстанс|порт»), из которого выводятся
блоки compose, порты, `fleet.yml` и правила молчания; отбор сессий флота в правиле по потолку и
в панелях опирается на соглашение об именах `service-.+`. Мотивация — `proposal.md`. Требования —
дельты `demo-stand` и `instance-registration`. Модель: service — статичное имя, group — namespace,
инстанс — имя пода/хоста, число — масштабирование группы. Механизм (провизор, ключи, пул, гейт
трафика) не меняется: провизор уже определяет состав по живым узлам регистрации.

## Goals / Non-Goals

**Goals:**
- Идентичность инстанса и группы — из окружения развёртывания (K8s-first), с docker-фолбэком.
- Состав стенда — масштабирование четырёх сервисов-групп; ни одного статического перечня инстансов.
- Балансировщик — docker-провайдер с метками; состав бэкендов живёт в развёрнутых контейнерах.
- Наблюдение и команды стенда не опираются на соглашение об именах и не ходят HTTP в инстансы.
- Перечни для команд и проверок — из живых источников: развёрнутые контейнеры, узлы регистрации,
  метрики.

**Non-Goals:**
- Механизм бюджета/долей/резерва/маркеров групп/публикации неосвобождённого сжатия не меняется.
- Стенд остаётся docker-compose; переноса в Kubernetes нет — воспроизводится модель его поведения.
- Имена метрик и набор признаков (`service`/`group`/`node`) не меняются — меняются значения.
- Нет TLS/ACL etcd и прочих отсутствующих в проекте возможностей.

## Decisions

### D1. Идентичность — цепочка дефолтов в `application.yml`

```yaml
pool:
  etcd:
    instance: ${ETCD_INSTANCE:${POD_NAME:${HOSTNAME:}}}
    group:    ${ETCD_GROUP:${POD_NAMESPACE:}}
  db:
    pool-name: ${POOL_NAME:${pool.etcd.instance:}}
```

`POOL_NAME` следует за именем инстанса — сохраняется инвариант уникальности имён сессий пула.
На docker `HOSTNAME` = container ID (hex), группа задаётся блоком группы (`ETCD_GROUP`); на k8s —
`POD_NAME`/`POD_NAMESPACE`. Альтернатива «префикc `service-` в имени» отклонена: это снова соглашение
об именах, от которого уходим. Валидация непустых сегментов (`EtcdKeyPath`) работает как есть.

### D2. Состав — четыре сервиса-группы и масштабирование

`service-a-group-1`, `service-a-group-2`, `service-b-group-1`, `service-b-group-2` наследуют
`x-service-a`/`x-service-b` и добавляют только `ETCD_GROUP`; `ETCD_INSTANCE`, `POOL_NAME` и
хост-порты из блоков удаляются. `make up`:

```bash
docker compose up -d --scale service-a-group-1=${A_G1} --scale service-a-group-2=${A_G2} \
                   --scale service-b-group-1=${B_G1} --scale service-b-group-2=${B_G2}
```

Дефолты чисел — в `.env` (`A_G1=2 A_G2=2 B_G1=2 B_G2=2`), фолбэк — в Makefile. Проверка готовности
инстансов в `make up`/`wait-ready.sh`: точки входа `web-a`/`web-b` + docker-здоровье контейнеров
(`docker compose ps`), без хост-портов. Нагрузчик — `depends_on` на группу
(`condition: service_healthy`); если поведение на масштабируемом сервисе неоднозначно — упростить
до `depends_on` на etcd+postgres и самостоятельного ожидания ответа точки входа (см. Risks).

### D3. Балансировщик — docker-провайдер с метками и ro-сокетом

Метки на базовом блоке экземпляра (одинаковы для всех реплик группы):

```yaml
- traefik.enable=true
- traefik.http.routers.fleet-<service>.rule=PathPrefix(`/`)
- traefik.http.routers.fleet-<service>.entrypoints=web-<a|b>
- traefik.http.services.fleet-<service>.loadbalancer.server.port=8080
```

Ожидание: идентичные определения роутера в репликах дедуплицируются, определения сервиса
агрегируют адреса реплик; нездоровые контейнеры docker-провайдер исключает по событиям (здоровье =
существующий healthcheck `/actuator/health/readiness`). `traefik/dynamic/fleet.yml`,
`scripts/balancers.py`, цели `balancers`/`check-balancers` и монтирование `traefik/dynamic`
удаляются. Окно после потери готовности = период docker-healthcheck, от числа реплик не зависит.

### D4. Наблюдение без соглашения об именах — join по метрикам пула

Правило по потолку: вместо `application_name=~"service-.+"` — оставить только имена, живущие как
пул в наблюдении (тот же разворот `application_name ↔ node`, что уже есть в правиле):

```promql
sum by (application_name) (pg_stat_activity_count)
  * on(application_name) group_left()
    label_replace(count by (node) (pool_maximum_pool_size),
                  "application_name", "$1", "node", "(.+)")
```

`$pool_app` в панелях — той же заменой (шаблонная переменная принимает произвольное выражение;
`allValue` без шаблона имён). `fleet-sessions` строит IN-список из узлов регистрации etcd, а не из
кортежей. В `stand.test.yml` добавляется кейс с именами без префикса сервиса.

### D5. Перечни и проверки — из живого состава

- **Правила молчания**: `scripts/silence.py` переписывается на перечень `docker compose ps`
  (развёрнутые контейнеры проекта, включая упавшие — правило обязано жить для упавшего) и пишет
  оба файла — `prometheus/rules/instances.yml` и `instances.test.yml` (тест ссылается на правило
  через `rule_files`, имена обязаны совпадать). Файлы остаются зафиксированными в репозитории
  (прежний паттерн «сгенерировать + закоммитить + сверять»). `make up` перегенерирует и делает
  reload Prometheus (SIGHUP; `--web.enable-lifecycle`), `check-silence` сверяет перегенерацией во
  временный файл за пределами `prometheus/rules/`.
- **`check-instances`**: перечень из `docker compose ps` × мгновенный запрос рядов
  `pool_maximum_pool_size{node=…}` — расхождения поимённо.
- **`make pool` (`pool-all.py`)**: перечень — объединение узлов регистрации (etcd) и состава
  `docker compose ps`; размер/соединения из метрик, готовность из `pool_not_ready_reason`/гейта,
  ключи из etcd; HTTP к инстансам не используется.
- **`make budget`/`sessions`**: перечни из etcd-дерева (для budget — уже так);
  `make sessions`/`fleet-sessions` — IN-список из узлов регистрации (сводка считает по живым узлам).
- **`make test`**: юнит-тесты maven автономны; проверки состава (check-silence, check-instances,
  promtool по сгенерированным файлам) требуют поднятого стенда — при пустом составе отказ с
  внятным сообщением «стенд не поднят», а не молчаливый успех.

Альтернативы, отклонённые в D5: перечень из etcd-дерева (не видит контейнеры без регистрации и
требует живого etcd), снимок перечня при `make up` (вторая копия состава, от которой уходим).

### D6. Команды стенда против живого состава

Из Makefile/скриптов убираются кортежи `TUPLES` и их производные; `require-S` проверяет сервис по
живым узлам регистрации (`{root}/services/`), `I=` принимается по желанию (`make config I=<имя>`);
перечень инстансов — `make instances`/`make registrations` из узлов регистрации и `docker compose
ps`. Адресация нагрузки — `LOAD_S=` как раньше.

### D7. Удаления

`ETCD_INSTANCES` и фолбэк-дефолты из `.env`/compose/Makefile; кортежные цели; хост-порты и
`ETCD_INSTANCE`/`POOL_NAME` в блоках инстансов; `traefik/dynamic/fleet.yml`, `scripts/balancers.py`,
`check-balancers`.

## Risks / Trade-offs

- [Одинаковые router-метки в репликах могут конфликтовать у docker-провайдера] → проверить на
  стенде сразу после перехода; ожидание — дедупликация идентичных определений; фолбэк — роутер
  объявляется один раз на группу (service-only labels на репликах + один роутер в статике).
- [`depends_on` на масштабируемый сервис ведёт себя неоднозначно] → упростить loadgen до
  `depends_on` на etcd+postgres и самостоятельного ожидания ответа точки входа.
- [`make test` частично требует живой стенд] → документируется; пустой состав — отказ с
  сообщением. Проверки состава по своей природе живые (правила молчания знают имена только
  развёрнутых контейнеров).
- [Правила молчания на старте Prometheus могут быть от предыдущего прогона] → `make up`
  перегенерирует и делает reload; `check-silence` ловит расхождение.
- [Имена на стенде станут hex (container ID)] → группировка в выводах идёт по признакам
  service/group, а не по имени; `docs/experiments.md` переснимается.
- [IN-список сессий из узлов регистрации не видит ещё не зарегистрировавшийся инстанс] → окно
  закрыто гейтом трафика; сводка считает по живым узлам.

## Migration Plan

1. Сначала service: дефолты идентичности (`application.yml`) + юнит-тесты — старый compose
   продолжает работать (в блоках явные `ETCD_INSTANCE`/`POOL_NAME` перекрывают дефолты).
2. Затем одним коммитом: удаление перечня/портов и переход на scale (compose + Makefile/scripts) и
   балансировщик на метках вместе с наблюдением (join в правиле/панелях, генерация молчания из
   `docker compose ps`).
3. `docs/README/experiments` — последним.
4. Откат: вернуть `.env`-кортежи и файловый провайдер балансировщика — обе ветки самодостаточны и
   затрагивают только обвязку стенда, не механизм.
