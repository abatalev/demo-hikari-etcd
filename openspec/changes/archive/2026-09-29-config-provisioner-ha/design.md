# Design

## Context

Текущий провизор — один экземпляр (`ConfigProvisioner`, SmartLifecycle, один поток
`config-provisioner-watch`): сверка (`reconcile`) → watch с revision+1 на `{root}/services/`,
при обрыве — backoff 1→30с. Провижин — атомарный txn «ключа нет → put», очистка — `del --prefix`
(идемпотентны). Мотивация и обзор — в proposal.md; набор поведенческих требований — в specs.

Ограничения среды: jetcd 0.8.7 уже содержит `io.etcd.jetcd.Election` (grpc `V3Election`);
ключи выборов обязаны лежать вне `{root}/services/`, чтобы не попадать в сверку, watch и
известный-ключ-проверку; сервис (`service/`) и его готовность не меняются.

Базовые свойства, на которые опираемся: записи провизора идемпотентны и коммутативны —
краткое окно «двух писателей» безопасно и сходится; лидерство определяется состоянием etcd,
а не мнением процессоа; перехват всегда начинается со свежей сверки (догоняет пропущенное).

## Goals / Non-Goals

**Goals:**
- Ровно один активный провизор на сервис `{root}/services/{service}`; остальные бездействуют.
- Набор сервисов выводится из дерева, а не из конфигурации; новые сервисы подхватываются без рестарта.
- Перехват лидера: крах → по TTL аренды; штатная остановка → сразу (resign).
- Механизм безразличен к числу реплик (N ≥ 1); при N=1 поведение совпадает с текущим.

**Non-Goals:**
- Выборы ниже уровня сервиса (`group`/`instance`) — не делаем.
- Фиксированный «предпочтительный лидер» — роли симметричны, преемник определяется возрастом ключа.
- Fencing-токены и ACL: записи идемпотентны, взаимного исключения через etcd не требуется.
- Изменения в `service/` (инстансы, их готовность) — вне объёма.

## Decisions

### D1. Механизм выборов — чистые KV-примитивы на префиксе лидерства

Кампания — атомарный txn «ключа нет → put» своего ключа
`{root}/provisioner/leader/{service}/{hex аренды}` (значение — `PROV_NAME`, ключ привязан к
аренде реплики); лидер — ключ с наименьшим `create_revision` в префиксе (get с сортировкой по
create); резинь — delete своего ключа.
Почему не серверный `V3Election` (`campaign`): в etcd 3.6 `Election/Campaign` реализован поверх
`concurrency.Election.Campaign`, который после записи своего ключа ждёт (`waitDeletes`), пока все
более старые ключи префикса не исчезнут, — т.е. блокируется, пока кампания не выиграет выборы.
Лидер проходит мгновенно, а фолловер висит до таймаута вызова, и его цикл выборов рвётся
(наблюдалось на стенде как `TimeoutException` каждые ~TTL). Обычные KV-примитивы дают ту же
семантику «лидер — старейший живой ключ, перехват по TTL», но без блокирующего ожидания — это
тот же путь txn put_if_absent, что уже используется в провижининге и проверен на стенде.

### D2. Follower-цикл — поллинг ~1с, не observe

Каждый цикл реплика сканирует дерево сервисов (D3), обеспечивает свои ключи кампании по
живым сервисам (D1; txn идемпотентен, ранг не сбрасывается переполлингами), затем определяет
лидера каждого префикса и владеет воркером, только будучи лидером. Преимущества: детерминизм
и простота проверки на стенде; нет стримов, которые надо переживать/обслуживать; при росте
числа реплик деградации нет. Серверные `campaign`/`observe` отклонены: первый блокируется до
победы (см. D1), семантика пушей второго в jetcd 0.8.7 мутновата и требует няньчить обрывы
стрима.

### D3. Набор сервисов — из дерева, поллинг-скан `{root}/services/`

Регулярный маленький `get {root}/services/` (в том же поллинг-стиле) → множество сегментов
`{service}` → кампании по живому сервису, `resign` кампании ушедшего. Не статический список:
сохраняется свойство «провижеру список не нужен». Светлый watch на `services/` отвергнут как
избыточный стрим.

### D4. Один lease на реплику

Все кампании реплики живут на одной аренде: один keepalive (дешевле), `resign` одного ключа
не трогает остальные, штатная остановка — resign всех ключей + revoke аренды до закрытия клиента
(зеркало отзыва узла регистрации в сервисе).

### D5. Лидерство управляет воркером провижининга

Воркер = текущие reconcile+watch с префиксом поддерева `{root}/services/{service}/` (вместо
полного `{root}/services/`). Лидерство получено → воркер стартует с полной сверки поддерева;
лидерство потеряно или сбой keepalive → воркер останавливается, возврат к выборам.
Структурно: резолвер набора сервисов + цикл выборов с владением воркерами + воркер поддерева.
Точные имена классов — деталь реализации, в спеках не фиксируется.

### D6. TTL выборов — 10с, keepalive ~3с (TTL/3)

Бюджет перехвата ≈ TTL + ~1с поллинг + сверка. 10с сбалансировано: быстрее регистрации
инстансов (15с), достаточно для исключения флапа на стенде.

### D7. Симметрия ролей

`restart` разворачивает роли: новый ключ вернувшейся реплики имеет больший `create_revision` →
она становится follower'ом. При N>2 преемник — старейший живой ключ, а не назначенный.
Принимается как свойство (симметричные реплики); «предпочтительный лидер» не вводим.

### D8. Наблюдаемость и конфигурация

`PROV_NAME` (имя реплики — значение лидер-ключа и в логах), `PROV_LEADER_TTL` (дефолт 10s).
Логи: «стал лидером сервиса X», «потерял лидерство», «проиграл выборы». `make leader` —
etcdctl: первый ключ префикса `{root}/provisioner/leader/{service}/` по каждому сервису.
Actuator-индикатор «я лидер» не добавляем (источник истины — etcd, смотрят через `make leader`).

## Risks / Trade-offs

- [Окно между крахом лидера и перехватом (до TTL): провижининг сервиса стоит, инстанс может ждать
  конфигурацию] → окно документируем; гейт трафика не пускает трафик на непровиженный инстанс;
  преемник начинает со сверки.
- [Застрявший лидер: потерял аренду (разрыв с etcd), но продолжает писать после возврата]
  → keepalive-сторож останавливает воркер на сбое аренды; записи идемпотентны — два писателя
  сходятся, ничего не портят.
- [Поллинг создаёт фоновую нагрузку ~1 запрос/с на реплику] → для прототипа (8 инстансов,
  одиночный etcd) некритично; при росте числа сервисов — переход на `observe` как эволюция.
- [Ключи выборов исчезнувшего сервиса могут лингеровать при крахе реплики] → уходят по TTL
  аренды; при живой реплике — resign по D3.
- [Случайный порядок преемника при N>2] → принимаем по D7.
- [Серверный `V3Election.Campaign` блокирует фолловера до победы (`waitDeletes` в
  go-конкеренси-реализации etcd)] → выборы реализованы чистыми KV-примитивами (txn put_if_absent
  + get лидера по create_revision) — тот же путь, что провижининг; проверено на стенде: два
  провизора, перехват по TTL и по resign, обрыв etcd (сценарии в tasks).

## Migration Plan

Обратная совместимость по построению: стенд с одним `config-provisioner` остаётся работать как
сейчас (N=1 → лидер всех сервисов). Развёртывание — добавление второго контейнера в compose
через якорь; rollback — вернуть один контейнер, код менять не нужно. Старые ключи `hikari/*`
и узлы провизор не трогает до смены лидера (сверка на старте лидерства).

## Open Questions

Нет: решения по TTL, поллингу, симметрии и наблюдаемости зафиксированы; проверки на живом
стенде вынесены в tasks (перехват, SIGKILL, обрыв etcd, ETCD_ENABLED=false не применим).
