# Proposal

## Why

Обе флота стенда делят одну базу с `max_connections=300` при сумме флота 200, поэтому база не
может помешать ничему. Утверждение «бюджет флота защищает потолок базы» проверяется только тем,
что правило по метрике молчит, — а молчание правила ничего не говорит о защите. Разделение базы по
сервисам делает потолок настоящим: он становится меньше суммы, которую механизм способен
приказать, и тогда превышение отказывает сама база. Раздельные базы дополнительно дают свойство,
недостижимое на одной общей: отказ базы одного сервиса не затрагивает остальные.

## What Changes

- Стенд поднимает отдельный экземпляр базы данных для каждого сервиса, инстансы каждого сервиса
  подключаются к своей базе, готовность инстанса ждёт готовности именно своей базы.
- Потолок соединений каждой базы задаётся с запасом меньше доли, выдаваемой одному инстансу:
  сумма флота помещается, а превышение сверх неё отказывается базой, а не остаётся незамеченным.
- Появляется сборщик метрик для каждой базы данных; показатели сессий пулов сводятся по имени
  приложения, которое уникально на весь стенд.
- Стенд получает вторую точку нагрузки на второй балансировщик, чтобы нагрузка обслуживала обе
  базы, а не одну.
- Команды стенда, работающие с базой (интерактивный `psql`, сводка флота, непрерывный замер
  флота, замер пулов), получают адресацию базы по имени сервиса и показывают, из какой базы
  получены данные.
- В наблюдении появляется вторая цель сбора, и число целей растёт.

Механизм распределения бюджета не затрагивается: бюджет остаётся числом в etcd, доля остаётся
значением `maximumPoolSize` в ключах узла, а адрес базы остаётся локальной настройкой инстанса.
Ни провизёр, ни пул, ни источник конфигурации не получают нового поведения.

## Capabilities

### New Capabilities

- Нет: разделение базы по сервисам — это свойство стенда, а не новый механизм. Оно описывается
  в существующей capability `demo-stand`.

### Modified Capabilities

- `demo-stand`:
  - требование «Стенд собирает метрики и показывает их» меняет состав компонентов наблюдения:
    сборщик метрик базы становится одним на каждую базу, а не один на стенд;
  - добавляется требование «Каждый сервис стенда работает со своей базой данных»;
  - добавляется требование «Потолок базы ограничивает флот своего сервиса».

## Impact

- `docker-compose.yml`: два экземпляра базы данных, два тома, два сборщика метрик базы, вторая
  точка нагрузки; якорь общей части инстанса разделяется по сервису, потому что адрес базы и
  условие готовности у сервисов различаются; новые публикуемые порты.
- `Makefile`, `scripts/measure-fleet.sh`, `scripts/measure-pools.sh`: адресация базы по сервису в
  командах, работающих напрямую с базой; вывод сводки флота дополняется указанием базы.
- `prometheus/prometheus.yml`: вторая цель в существующей задаче сбора метрик баз.
- `prometheus/rules/stand.yml`: правила не меняются; правило потолка остаётся корректным, и это
  фиксируется комментарием, потому что корректность держится на соглашении об именах инстансов,
  а не на самом запросе.
- `prometheus/targets.json` не меняется: канонический список инстансов не меняется, цели
  инстансов по-прежнему выводятся из него.
- `scripts/targets.py`: правится расхождение докстринга с фактическим путём файла целей.
- `.env`, `.env.example`: порты второй базы и второго сборщика.
- `db/init`: подготовка данных едет в оба экземпляра, идемпотентность сохраняется.
- Документация: `README.md`, `docs/api.md`, `docs/experiments.md`, `docs/operations.md`,
  `AGENTS.md` — состав стенда, порты, число целей, порядок работы с базой.
