# Design

## Маркер активности группы

- Ключ `{root}/groups/{group}/active`, значение `true|false`. Отсутствие ключа или нечитаемое
  значение → группа активна + WARN (fail-safe к обслуживанию). Значение `false` → неактивна.
- Маркер лежит **вне** `{root}/services/` — в снимок и watch воркера не попадает, «неизвестный
  ключ» по нему не логируется, гейт трафика не дёргается (тот же аргумент, что у выборов).
- Читается чистым разбором `GroupFleetKey` (по аналогии с `InstanceKey`/`EtcdKeyPath`):
  `{root}/groups/{group}/active` (пустой group → неверный ключ). Мусор в префиксе групп
  логируется один раз как опечатка.

## Кто и как применяет маркер

- Сам воркер провижининга сервиса поллит префикс `{root}/groups/` раз в секунду (отдельный
  поток, как keepalive у регистрации; на каждой реплике лидера — свой). При изменении маркера
  **своей** группы (фильтр: группа из деревьев последнего скана) воркер делает `recompute()` —
  перечитывает и своё поддерево, и маркеры, и применяет. Меж-сервисной маршрутизации через
  владельца не требуется: группа глобальна, но каждый сервис делит свой бюджет, а воркер и так
  видит все свои узлы.
- `recompute()` и события watch сериализованы общим `sync`/семафором провижининга `apply()`.
- Обрыв etcd: поллинг молча пропускает тики (последнее известное состояние маркеров
  сохраняется), сервис/пул не ломаются. Fail-closed: новых неактивных групп нет.

## Бюджет и формула

Сервисные ключи (корень `{root}/services/{service}/`):

| ключ | смысл | дефолт провизора |
|---|---|---|
| `activeMaxConnections` | бюджет активного флота (N) | `PROV_ACTIVE_MAX_CONNECTIONS` |
| `activeMinConnections` | минимум активной доли (m) | `PROV_ACTIVE_MIN_CONNECTIONS` |
| `inactiveMaxConnections` | размер неактивного узла (R) | `PROV_INACTIVE_MAX_CONNECTIONS` (тёплый, 1) |

Формула (вся логика — в `PoolSizeDistribution` как чистая функция + партиционирование в воркере):

1. `k` = число узлов сервиса в неактивных группах. Неактивным узлам — размер ровно R.
2. Активным узлам — `distribute(N − R×k, m, maxShare, активные)` (прежний алгоритм: равные доли
   `floor/floor+1`, усечение до границы). Сумма долей по сервису = N; резерв неактивных
   перетекает активным, освобождение слотов — только когда неактивны все группы (R×n).
3. R = 0 → неактивные узлы не получают конфигурацию вовсе (существующая протирка «узел без
   доли» их сносит). Cold. R ∈ [1, maxShare] → тёплый пул ровно R (`minimumIdle` следует —
   инвариант).
4. Fail-closed на сервис (WARN с числами, конфигурация не меняется): R вне
   `{0} ∪ [1, maxShare]` или не-число; `R×k > N`; есть активные узлы и `N − R×k < m`.

Сервисные ключи создаются put-if-absent на первом живом узле сервиса (как сейчас) и переживают
опустение сервиса. `activeMaxConnections`/`activeMinConnections`/`inactiveMaxConnections` —
равноправные сервисные настройки; `maximumPoolSize` остаётся единственным управляемым ключом
инстанса.

## Сервис: пул только из etcd

- `application.yml` сервиса: `maximum-pool-size: 0` (литерал). `POOL_MAX_SIZE` удаляется из
  compose и `.env.example`. Остальные локальные дефолты (`POOL_CONNECTION_TIMEOUT_MS`,
  `POOL_EAGER_FILL`, `POOL_DRAIN_TIMEOUT`) остаются.
- `HikariSettings.normalize()`: диапазон максимума `[0, POOL_SIZE_MAX]`; при максимуме 0 минимум
  следует → 0; предупреждения о сочетаниях при максимуме 0 не выдаются.
- `ManagedPool`: конструктор не создаёт пул, когда стартовый максимум 0 (`applied` пуст).
  `apply()`: целевой максимум 0 → если пул есть, дренаж (`softEvictConnections` + ожидание
  `drain-on-recreate-timeout`) и закрытие, результат `CLOSED`; пула уже нет → `UNCHANGED`.
  Целевой максимум > 0 при пустом `applied` → создание с нуля (отдельный исход `CREATED`).
  `settings()`/`runtime()` null-safe. `runtime()` возвращает «пула нет» (total 0, замокнут).
- `PoolController`: `/api/pool` и `/api/config` работают и без пула (`settings: null` при
  `include_non_null`), `/api/work` — через гейт.
- **Отказ 0 из etcd сохраняется**: проверка в `EtcdPoolConfigSource` до `resolve`
  (`maximumPoolSize() == 0` → `InvalidSettingsException` → REJECTED, причина в статусе).
  Гейт по этому пути не закрывается (распознанные ключи есть). Полная протирка ключей (R=0)
  происходит удалением ключей — это «Конфигурация снята»: гейт закрывается, а дальше локальные
  дефолты (максимум 0) дают честное «пула нет».

## Открытые состояния и краевые

- Частичный конфиг без `maximumPoolSize` → `resolve(defaults)` даёт 0 → пул временно закрыт до
  восстановления управляемого ключа провизором. Осознанно; описывается в документации.
- Старт без etcd: пула нет, гейт закрыт (нет распознанных ключей), liveness жива. При возврате
  etcd пул создаётся из первой конфигурации без перезапуска.
- Миграция ключей: старые `maxConnections`/`minConnections` после рестарта стенда становятся
  «неизвестными ключами» уровнем выше (`{root}/services/{service}/...`), поэтому `make clean &&
  make up` обязателен один раз.

## Команды стенда

- `make set-active-max-connections SIZE=N S=s`, `make set-active-min-connections SIZE=m S=s`
  (валидация: положительное число, m ≤ N — как сейчас, ключи новые).
- `make set-inactive-max-connections SIZE=R S=s` (R ≥ 0; 0 — холод).
- `make set-group-active G=g ACTIVE=false|true` — маркер `{root}/groups/{g}/active`.
- `make budget`, `scripts/budget.py` — новые имена ключей, R, маркеры групп.
- `make config` — ручная правка (неизменна).
