# Design

## Context

Сейчас стартовый конфиг раскладывается разовым сидером для статичного списка `ETCD_INSTANCES`
до старта инстансов. Инстанс с прошлого изменения регистрирует собственный узел
`{root}/services/{s}/groups/{g}/instances/{i}/` на аренде (пустое значение, TTL 15с, keepalive) —
появление/исчезновение узла это готовые события для реактивного провижининга. Гейт трафика
открывается первым распознанным ключом, окно «зарегистрирован, но не готов» — нормальное
состояние, поэтому сам сервис менять не нужно (см. proposal.md — Why).

Стек сервиса: Spring Boot 3.5.16, Java 21, jetcd 0.8.7. В `EtcdPoolConfigSource` уже написаны
паттерны, которые провизор повторяет: снимок → watch с `revision + 1`, backoff 1→30с, один
клиент на жизненный цикл.

## Goals / Non-Goals

**Goals:**
- Отдельный сервис-провижер (модуль `provisioner/`), который держит инвариант «ключи
  конфигурации инстанса существуют ⟺ существует его узел регистрации».
- Реактивность: появление узла → провижин, исчезновение → удаление.
- Идемпотентность и отсутствие петель: существующие ключи живого инстанса никогда не
  перезаписываются; события `hikari/*` игнорируются.
- Замена разового сидера в стенде без изменения самого сервиса и его готовности.

**Non-Goals:**
- Заполнение значения узла регистрации (остаётся пустым; поинстансные параметры провижена не
  поддерживаются — дефолты глобальные, тюнинг — ручными правками).
- Наблюдаемость провизора через HTTP API (логи и ключи etcd достаточно; liveness — для
  compose-healthcheck).
- Репликация/лидер-выбор провизора (в стенде один экземпляр; идемпотентность делает запуск
  второго безвредным).

## Decisions

**1. Форма: отдельный Spring Boot 3.5-модуль `provisioner/` с jetcd.**
Тот же стек, что и сервис; паттерны снимка, watch и backoff уже написаны в `EtcdPoolConfigSource`
и повторяются один в один.
Альтернативы: (а) один файл на голом JDK через HTTP/gRPC-gateway — технически работает (gateway
в etcd 3.6 включён по умолчанию), но JSON-парсер без библиотек и стрим watch добавляют хрупкости
ради «ноль зависимостей»; (б) bash + etcdctl — событийный watch в bash не различает PUT пустого
узла и DELETE (значение узла пустое), пришлось бы опрашивать, что ломает «при появлении».
Выбор пользователя и консистентность со стеком — Spring Boot.

**2. Цикл провижера = сверка + watch (как у конфиг-источника).**
Старт: `get --prefix {root}/services/` → построить (а) множество живых узлов, (б) множество
префиксов `hikari/` → reconcile → подписка watch с `revision + 1`. Обрыв (compaction, рестарт
etcd, недоступность) → backoff 1→30с, повторный снимок, повторная подписка. Events, случившиеся
во время обрыва, не доставляются, но сверка на переподключении восстанавливает инвариант —
это и есть механизм без потери.

**3. Фильтр событий — чистая функция.**
Ключ считается узлом, если он равен `{root}/services/{s}/groups/{g}/instances/{i}/` при валидных
непустых сегментах без `/` и без дополнительных сегментов после имени инстанса. Всё внутри
`.../{i}/hikari/` игнорируется. Функция разбора/фильтрации выносится отдельно и покрывается
юнит-тестами без etcd (по образцу `EtcdKeyPathTest`).

**4. Провижин — атомарный `put_if_absent` через txn jetcd.**
На каждый стартовый ключ: если `create_revision == 0` (ключа нет) — `put`; иначе — ничего.
Атомарность нужна, чтобы две записи (провижер + ручная правка или два провизора) не
соревновались. Стартовый набор: `maximumPoolSize` (`PROV_MAX_POOL_SIZE`, дефолт 10),
`connectionTimeoutMs` (`PROV_CONNECTION_TIMEOUT_MS`, дефолт 3000). `minimumIdle` не пишем —
следует за `maximumPoolSize` (как было у сидера).

**5. Очистка — `del` всего префикса.**
При DELETE узла и при осиротевшем `hikari/`-префиксе (в сверке) удаляется весь префикс
`.../{i}/hikari/`, включая ключи, добавленные вручную — такова выбранная семантика «при
исчезновении инстанса все ключи удаляются».

**6. Reconcile — по инстансам, без общих блокировок.**
Для каждого живого узла — провижин стартовых ключей; для каждого осиротевшего префикса —
очистка. Каждая операция — отдельный запрос; сбой одной не останавливает остальные (ошибка
логируется, повтор при следующем событии/сверке).

**7. Порядок старта в compose не критичен.**
Инстансы больше не ждут сидера (`depends_on` снимается). Провизор стартует после healthy etcd.
Корректность обеспечивает сверка: зарегистрировавшихся до старта провизора догоняет снимок,
зарегистрировавшихся между снимком и подпиской — watch с `revision + 1`.

**8. Дублирование чистой логики пути вместо общего модуля.**
Провизору нужны свои ~40 строк разбора пути (узел/префикс). Общий модуль ради них раздувал бы
репозиторий; дублирование с тестами — осознанный компромисс прототипа.

**9. Liveness провизора — только ping.**
Как у сервиса: живость от etcd не зависит, композ-healthcheck смотрит в
`/actuator/health/liveness`. Отдельный readiness («соединён с etcd») не нужен — в стенде это
видно по логам и времени провижининга.

## Risks / Trade-offs

- **Watch-цикл и сверка не покрыты юнит-тестами** (Testcontainers в проекте нет, как и для
  `ManagedPool`/watch конфиг-источника) → обязательная проверка на живом стенде: чистый старт 8
  инстансов, стоп/старт одного, краш (SIGKILL), обрыв etcd, `ETCD_ENABLED=false`-инстанс.
- **Удаление всего префикса при остановке** теряет ручную настройку остановленного инстанса —
  зафиксировано в спеке `demo-stand` (сознательный выбор пользователя).
- **Осиротевший конфиг после перехода со сидера**: первый запуск провизора вычистит ключи,
  оставшиеся без узлов (старый сидинг) — желаемая миграция; на чистом стенде этого нет.
- **Гонка во время сверки**: инстанс зарегистрировался, но ещё не провижен —
  «зарегистрирован, но не готов», гейт закроет окно, когда ключи появятся; петель нет, потому
  что события `hikari/*` не обрабатываются.
- **Два провизора** запустят одинаковые записи/удаления — идемпотентно (txn/`del`), без вреда;
  в стенде провизор один.

## Migration Plan

1. Добавить в `docker-compose.yml` сервис `config-provisioner` (сборка модуля `provisioner/`,
   `depends_on: etcd healthy`), удалить `etcd-seed`, снять `depends_on` сидера у инстансов.
2. `.env(.example)`: `SEED_*` → `PROV_*`; `Makefile`: убрать `make seed`.
3. Документация: README (схема, команды), docs/mechanism.md (раздел провижининга),
   docs/operations.md (переменные, troubleshooting), AGENTS.md (capability-таблица, инварианты).
4. Откат: вернуть сидер и зависимость инстансов; идемпотентный сидинг не конфликтует с ключами,
   созданными провизором.

## Open Questions

- Хочется ли для провизора отдельный readiness-индикатор «соединён с etcd» сверх liveness — не
  меняет спеки, подход и задачи; можно добавить позже отдельным изменением.
- Появятся ли поинстансные стартовые параметры через значение узла регистрации — остаётся
  отложенным (узел пустой), провижин использует глобальные дефолты.
