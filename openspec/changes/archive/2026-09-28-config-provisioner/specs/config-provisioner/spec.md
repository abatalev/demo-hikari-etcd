# Spec Delta

## Purpose

Провижинирование конфигурации пула по факту жизни инстанса: появление узла регистрации порождает
стартовые ключи конфигурации, исчезновение узла удаляет их, сверка на старте и после обрывов
удерживает инвариант «ключи существуют тогда и только тогда, когда инстанс жив».

## ADDED Requirements

### Requirement: Появление узла порождает стартовые ключи

При появлении в хранилище узла регистрации инстанса провижер SHALL добавить в путь этого
инстанса стартовый набор ключей конфигурации (`maximumPoolSize`, `connectionTimeoutMs`).
Существующие ключи этого пути SHALL NOT перезаписываться.

#### Scenario: Новый инстанс зарегистрировался

- **WHEN** в хранилище появляется узел регистрации инстанса, в пути которого ещё нет ключей
  конфигурации
- **THEN** в его пути появляются стартовые значения `maximumPoolSize` и `connectionTimeoutMs`

#### Scenario: Повторная регистрация уже настроенного инстанса

- **WHEN** инстанс перезапускается, его узел регистрации создаётся повторно, а ключи конфигурации
  уже есть в пути
- **THEN** существующие значения ключей (в том числе изменённые оператором вручную) сохраняются
  без изменений

### Requirement: Исчезновение узла удаляет конфигурацию

Когда узел регистрации инстанса исчезает из хранилища, провижер SHALL удалить все ключи
конфигурации этого инстанса из его пути.

#### Scenario: Штатная остановка инстанса

- **WHEN** инстанс останавливается штатно и его узел регистрации исчезает немедленно
- **THEN** все ключи конфигурации этого инстанса удаляются из хранилища

#### Scenario: Падение инстанса

- **WHEN** процесс инстанса завершается без штатной остановки и его узел исчезает по истечении
  срока аренды
- **THEN** после исчезновения узла ключи конфигурации этого инстанса удаляются из хранилища

### Requirement: Сверка на старте и после обрыва

При запуске и после каждого обрыва связи с хранилищем провижер SHALL восстановить инвариант:
ключи конфигурации инстанса существуют в хранилище тогда и только тогда, когда существует его
узел регистрации. Живые узлы без конфигурации SHALL получить стартовые ключи; ключи конфигурации
без живого узла SHALL быть удалены.

#### Scenario: Старт при уже зарегистрированных инстансах

- **WHEN** провижер запускается, а инстансы уже зарегистрировали свои узлы
- **THEN** все живые узлы получают стартовые ключи конфигурации

#### Scenario: Осиротевшие ключи конфигурации

- **WHEN** в хранилище есть ключи конфигурации, для которых не существует узла регистрации
- **THEN** после сверки такие ключи удаляются

#### Scenario: Регистрация сразу после старта провижера

- **WHEN** инстанс регистрирует узел сразу после запуска провижера
- **THEN** конфигурация для него появляется без потери события

### Requirement: События конфигурации игнорируются

Изменения ключей конфигурации (префикс `{instance}/hikari/`) — выполненные как провижером, так и
оператором вручную — SHALL NOT приводить к действиям провижера: существующие ключи не
перезаписываются, не удаляются и не порождают повторных записей.

#### Scenario: Ручная правка размера пула

- **WHEN** оператор изменяет значение ключа `hikari/` работающего инстанса
- **THEN** провижер не трогает ни этот ключ, ни соседние

#### Scenario: Собственные записи провижера

- **WHEN** провижер записывает стартовые ключи инстанса
- **THEN** эти записи не вызывают у провижера дальнейших действий (повторных записей)

### Requirement: Переживание обрывов хранилища

При недоступности хранилища провижер SHALL продолжать работу, периодически повторяя попытки
соединения; при возврате хранилища провижер SHALL восстановить инвариант без перезапуска и без
потери событий, произошедших во время обрыва.

#### Scenario: Хранилище недоступно на старте

- **WHEN** провижер запускается при недоступном etcd
- **THEN** процесс продолжает работать и начинает провижинирование, когда хранилище возвращается

#### Scenario: Обрыв во время работы

- **WHEN** etcd был недоступен во время работы провижера, а затем снова ответил
- **THEN** провижер восстанавливает инвариант «ключи ⟺ живой узел» без перезапуска процесса
