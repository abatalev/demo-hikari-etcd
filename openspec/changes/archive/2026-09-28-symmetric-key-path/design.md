# Design

## Context

См. proposal.md — Why. Форма пути материализована в трёх независимых «строителях» (Java-билдер,
bash-сидер, Makefile), которые обязаны собирать дословно одинаковый путь: расхождение тихо даёт
«инстанс никогда не получает конфигурацию». Кортежи `ETCD_INSTANCES` остаются каноническим
описанием инстансов без изменений — маркеры это статический «клей» в сборке, а не данные.

## Goals / Non-Goals

**Goals**
- Единая симметричная форма пути `/config/services/{service}/groups/{group}/instances/{instance}/hikari/` во всех трёх строителях и в документации.
- Минимальный разлёт правки: маркеры живут константами в `EtcdKeyPath`, валидация сегментов не трогается.
- Изменение формы не меняет контрактов: гейт, изоляция инстансов, порядок применения, watch — без изменений.

**Non-Goals**
- Миграция существующих ключей etcd (нет — по образцу предыдущего изменения схемы).
- Конфигурируемость маркеров через env — это статические константы, а не настройка.
- Изменение кортежей `ETCD_INSTANCES`, диапазонов настроек, HTTP-контрактов.

## Decisions

**1. Маркеры — константы в `EtcdKeyPath` рядом с `HIKARI`.**
`SERVICES = "services"`, `GROUPS = "groups"`, `INSTANCES = "instances"`. Позволяет покрыть форму
тестами как чистую функцию и держать маркеры в одном месте на Java-стороне.
*Альтернатива:* прокидывать маркеры через свойства — избыточно, маркеры не меняются между
инстансами и без причины расходятся с правилом «путь собирается в одном месте».

**2. Форма добавляется только в `build()`; валидация сегментов не меняется.**
Маркеры статичны и не проходят `requireSegment` (это не пользовательский ввод). Service/group/
instance по-прежнему проверяются на непустоту и отсутствие `/`. Структура:
`trimmedRoot + "/" + SERVICES + "/" + service + "/" + GROUPS + "/" + group + "/" + INSTANCES + "/" + instance + "/" + HIKARI + "/"`.
*Альтернатива:* валидировать и маркеры — лишняя логика без пользовательского ввода.

**3. Сидер и Makefile меняются одним выражением каждая.**
`seed-config.sh`: `PREFIX="$ROOT/services/$svc/groups/$grp/instances/$inst/hikari/"`.
`Makefile` `tuple_path`: `$(ETCD_ROOT)/services/$(service)/groups/$(group)/instances/$(instance)/hikari/`.
Это единственные точки в bash/make — остальные команды (`set-size`, `set-min-idle`, `config`,
`instances`) наследуют форму через них. Допустимые значения сегментов (`service|group|instance`
без `/`) не меняются, поэтому кортежи не трогаются.

**4. Тесты чистых функций обновляются на новый образец пути.**
`EtcdKeyPathTest` — ожидаемый путь во всех кейсах (3 построения). Покрыты только чистые функции:
правильность сборки формы верифицируется на живом стенде (`make instances` показывает пути,
`make up` ждёт readiness всех 8 инстансов — если сидер и сервис разойдутся, readiness не настанет).

## Risks / Trade-offs

- **Расхождение формы между тремя строителями** (правка прошла в одном месте) → маркеры одинаково
  выглядят в трёх местах; проверка на стенде: `make instances` (пути из Makefile) + `make pool`
  (путь из /api/config инстанса) + readiness всех 8 в `make up` (сидер ⇄ сервис).
- **Старые ключи остаются мусором в etcd** после `make up` без чистки → `make clean && make up`
  обязательно, документируется в tasks/применении.
- **Опечатка «hikari» при переносе** (маркеры копируются в текстовые строители bash/make) →
  маркеры вводятся дословно из proposal; опасность та же, что у самого `hikari`, покрыта ожиданием
  readiness на стенде.

## Migration Plan

1. Правка кода и тестов (`EtcdKeyPath`, `EtcdKeyPathTest`, сидер, Makefile).
2. Правка примеров путей в javadoc/комментариях/docs.
3. `make clean && make up` — стенд чистится и поднимается на новой схеме (8 инстансов готовы).
4. Проверка: `make instances` (новые пути), `make pool` (путь из API совпадает), правка размера
   одной командой (`make set-size`) применяется к нужному инстансу.
Откат: возврат формы пути в трёх строителях + `make clean && make up` (миграция ключей не
предусмотрена в обе стороны).

Нет. Форма пути, точки правки и порядок проверки определены; решение `skip_specs: true`
обосновано в proposal (спеки не фиксируют литеральную форму).
