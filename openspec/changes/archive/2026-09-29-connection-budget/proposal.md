# Proposal

## Why

Сейчас каждый инстанс провижинируется фиксированным стартовым `maximumPoolSize` (по умолчанию 10), и
изменение суммарной ёмкости сервиса требует ручной правки ключа каждого инстанса. Нужен сервисный
бюджет: общее число коннектов на сервис задаётся одним ключом, провизор делит его равномерно между
живыми инстансами (с полом на инстанс), а сумма долей не превышает бюджета — это защищает базу
(`max_connections=200`) от суммарного перерасхода.

## What Changes

- Сервисный ключ бюджета `{root}/services/{service}/maxConnections`: провизор при появлении первого
  узла сервиса создаёт его put-if-absent со значением по умолчанию из своей конфигурации; ключ
  переживает опустение сервиса (окно `n=0` в rolling не сбрасывает его).
- Ключ минимума `{root}/services/{service}/minConnections` (тот же жизненный цикл): пол на инстанс,
  «если выделяем, то не меньше установленного значения».
- `maximumPoolSize` становится **управляемым ключом**: провизор распределяет бюджет N равномерно
  между живыми инстансами сервиса (доля `N div n`, остаток раздаётся первым по порядку, сумма
  ровно N) и перезаписывает ключ при расхождении с вычисленной долей. `connectionTimeoutMs`
  остаётся стартовым put-if-absent. **BREAKING**: ручные правки `maximumPoolSize` переживают только
  до ближайшего пересчёта; команды вида `make set-size` становятся временными оверайдами.
- Минимум: если `n×m > N`, служат ровно `floor(N/m)` инстансов (по установленному порядку), избыток
  не провижинируется — гейт трафика держит его в 503, сумма долей остаётся ≤ N. При `N < m` провизор
  ничего не меняет (последнее применённое состояние сохраняется) и фиксирует причину. Доли выше 200
  усекаются до 200.
- Пересчёт распределения по событиям: узел появился/исчез, изменение `maxConnections`/
  `minConnections`, сверка на старте и после обрыва. Падение/появление одного инстанса меняет доли
  всех живых инстансов сервиса.
- Стенд: вместо per-инстансных команд — `make set-max-connections N=… S=…` и
  `make set-min-connections M=… S=…`; кейс «rolling update» (новые инстансы → готовы → вывод старых)
  отрабатывается на живом стенде дополнительными контейнерами.
- Известное ограничение (документируется): непровижинённый избыток держит локальный дефолт пула на
  старте — гейт не пускает трафик, но соединения к базе такой инстанс может открывать.

## Capabilities

### New Capabilities

_(нет новых capability: распределение бюджета — поведение провижининга и ложится в существующий
`config-provisioner`)_

### Modified Capabilities

- `config-provisioner`: алгоритм провижининга меняется — `maximumPoolSize` становится управляемым
  ключом (раньше существующие ключи не перезаписывались никогда); добавляются сервисные ключи
  бюджета с собственным жизненным циклом, равномерное распределение, пол на инстанс, избыток без
  конфигурации; сверка и классификация событий переформулируются.
- `demo-stand`: семантика «повторные прогоны не перезаписывают ручные правки» сужается до
  не-размерных ключей; команда изменения размера пула становится сервисным бюджетом (+команда
  минимума); добавляется сценарий смены состава сервиса (rolling).

## Impact

- `provisioner/` — основной удар: `InstanceKey` (новый тип ключа сервиса), чистая функция
  распределения `PoolSizeDistribution` (покрывается юнит-тестами), `ProvisioningWorker`
  (пересчёт всего сервиса по событиям узлов и бюджета, обеспечение сервисных ключей),
  `ProvisionerProperties`/`application.yml` (`PROV_MAX_CONNECTIONS`, `PROV_MIN_CONNECTIONS`;
  `PROV_MAX_POOL_SIZE` устаревает).
- `service/` — **не меняется** (инстанс по-прежнему видит только свой путь и применяет
  `maximumPoolSize` как раньше).
- `Makefile`, `docker-compose.yml`, `.env.example` — команды бюджета, дефолты переменных.
- Документация: `docs/mechanism.md`, `docs/operations.md`, `README.md`, `AGENTS.md` (инвариант
  «управляемый ключ», подводные камни, ограничение про локальный дефолт избытка).
- Спеки `config-validation`, `pool-lifecycle`, `traffic-readiness`, `instance-registration` — без
  изменений (проверено: поведение инстанса не меняется).
