# Proposal

## Why

Нагрузчик стенда — единственный артефакт, который собирается не так же, как остальные. `service/`
и `provisioner/` это Maven-проекты на `spring-boot-starter-parent`, а `loadgen/` — один файл,
который компилируется `javac` внутри Dockerfile. Отсюда два последствия, оба чисто инструментальные:

- нагрузчик нельзя собрать и запустить обычной командой проекта: нет `mvn package`, нет запуска вне
  Docker. Правка нагрузчика проверяется только через `docker compose build`, то есть медленно и
  неотличимо от проверки стенда целиком;
- образ нагрузчика собирается из исходника в две стадии (`javac` → `jre`), а два других образа
  Maven-сборкой. Три способа сборки в одном стенде.

Перевод нагрузчика на Spring Boot и Maven снимает это рассогласование: все три образа стенда
собираются одним инструментом, а нагрузчик запускается и без Docker.

Побочная выгода та же, что у остальных двух модулей: конфигурация из окружения читается
одинаковым способом, и в проекте появляется единый способ собрать любой артефакт.

Оговорка честности: функциональной потребности в Spring Boot у нагрузчика нет. Это процесс с
одним HTTP-клиентом, виртуальными потоками и печатью отчёта в stdout; ни DI, ни web, ни
персистентность в нём не используются. Поэтому переменная этого изменения — **единообразие
инструментария и удобство локальной сборки**, а не функциональность. Плата за это: фреймворк в
процессе, который сам по себе фреймворка не требует. Размена обоснована в `design.md`.

## What Changes

- `loadgen/` становится самостоятельным Maven-проектом на `spring-boot-starter-parent`
  версии 3.5.16 — той же, что у `service/` и `provisioner/`. Это **не** модуль агрегатора:
  корневого `pom.xml` в проекте нет, все три артефакта собираются независимо, и loadgen
  следует тому же соглашению.
- Появляется `loadgen/pom.xml` и точка входа, запускающая существующий нагрузчик. Сам
  `LoadGen.java` переносится в `src/main/java/ru/hikari/loadgen/` и меняется ровно на одну
  строку — `package`-декларацию: она обязательна, потому что `@SpringBootApplication` в default
  package не работает, а класс из default package невидим из named package. Тело нагрузчика —
  логика, тайминги, формат отчёта — не тронуто ни на строку.
- Тип приложения — `none`: веб-сервер не поднимается, порт не занимается.
- Вывод отчёта остаётся в stdout и остаётся построчным. Логи и баннер Spring Boot на stdout
  не попадают — иначе они смешаются с отчётом, который читает `make load-logs`.
- Dockerfile нагрузчика переходит с `javac`/`-cp` на `mvn package` + `java -jar`.
- `docker-compose.yml`, `Makefile` и набор переменных окружения не меняются: `TARGET`,
  `STATUS_TARGET`, `WORKERS`, `WORK_MS`, `THINK_MS`, `REPORT_MS`, `DURATION_S`,
  `REQUEST_TIMEOUT_S` работают как раньше, `make stress`, `make load-logs`, `make build` —
  без правок вызова.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

Нет. Поведение нагрузчика не меняется: те же переменные, тот же формат отчёта, та же семантика
`DURATION_S=0` (висит до остановки контейнера), тот же итог по `SIGTERM`. Изменение относится к
способу сборки и запуска, а не к поведению, поэтому дельты спек не заводятся — это тулинг без
изменения контракта (`skip_specs: true`).

## Impact

- **Код**: `loadgen/LoadGen.java` (только перенос пути), `loadgen/pom.xml` (новый),
  `loadgen/src/main/java/.../LoadGenApp.java` (новый), `loadgen/Dockerfile` (сборка через Maven).
- **Не меняется**: `docker-compose.yml`, `Makefile`, `.env`, `.env.example`, переменные
  окружения нагрузчика, формат вывода, поведение точек нагрузки `loadgen-a`/`loadgen-b`.
- **Документация**: `README.md` (описание «один файл на JDK» → Maven + Spring Boot),
  `AGENTS.md` (состав и инварианты), `docs/operations.md` (переменные и раздел про нагрузчик),
  `docs/experiments.md` (команда сборки нагрузчика в «Как повторить»).
- **Артефакты в репозитории**: `LoadGen.class` и `LoadGen$Latencies.class` в `loadgen/` — это
  результат локальной компиляции, в git они не должны попадать.
