# Design

## Context

Нагрузчик устроен так, что почти всё в нём — статика: чтение переменных окружения в статические
поля, создание `HttpClient` в `main`, виртуальные потоки через
`Executors.newVirtualThreadPerTaskExecutor()`, отчёт в `System.out.printf`. `main` не возвращается:
при `DURATION_S > 0` он спит заданное время, при `DURATION_S = 0` висит на `CountDownLatch` до
остановки контейнера, а итог печатает shutdown-hook, зарегистрированный в `main`.

```
текущий loadgen/
  LoadGen.java      13.5 КБ, только JDK
  Dockerfile        javac -d out LoadGen.java -> jre -> java -cp /app LoadGen
  .dockerignore
```

При этом образ собирается `docker compose build`, то есть правку нагрузчика нельзя проверить ничем,
кроме полной пересборки образа.

Смежные факты, определившие решение:

- корневого `pom.xml` в проекте нет; `service/pom.xml` и `provisioner/pom.xml` — два
  самостоятельных проекта, каждый со своим `spring-boot-starter-parent` 3.5.16. Следовательно,
  loadgen должен стать **третьим самостоятельным проектом**, а не модулем агрегатора: вводить
  агрегатор ради одного модуля означало бы перестроение сборки всех трёх артефактов, что выходит
  за пределы изменения нагрузчика;
- отчёт нагрузчика — не просто лог, а интерфейс: его читает `make load-logs`, и человек смотрит
  в него при разборе переходов бюджета. Строки отчёта парсятся глазами, формат колонок зафиксирован
  в `README.md` и `docs/operations.md`.

## Goals / Non-Goals

**Goals:**

- нагрузчик собирается и запускается обычными для проекта средствами (`mvn package`, `java -jar`),
  в том числе без Docker;
- все три образа стенда собираются одним инструментом;
- поведение нагрузчика, набор переменных окружения, формат отчёта и семантика остановки
  не меняются ни в чём;
- тело `LoadGen` не меняется ни на строку — чтобы правка таймингов нагрузки была невозможна
  по недосмотру, а единственная добавленная строка `package` проверяется diff'ом.

**Non-Goals:**

- переписывать логику нагрузки на `RestClient`/`WebClient` и не менять тайминги;
- добавлять нагрузчику web-сервер, actuator, метрики или health — он не наблюдаемый объект
  стенда, он инструмент;
- вводить корневой агрегатор `pom.xml` для трёх модулей;
- переводить `service/` и `provisioner/` на общий агрегатор (это отдельное изменение).

## Decisions

### Тело `LoadGen` не меняется; добавлена только `package`-декларация

Изначально предполагалось перенести файл байт-в-байт. Это оказалось невозможно, и причину
проверяли экспериментом, а не догадкой: `@SpringBootApplication` в default package не
работает — component scan оттуда сканирует весь classpath, включая вложенные jar'ы, и
поднимает `BeanDefinitionStoreException`. Класс же из default package невидим из named
package, поэтому типизированный вызов `LoadGen.main` из точки входа не собирается.

Значит `LoadGen` получает package-декларацию и живёт в `ru.hikari.loadgen` рядом с
`LoadGenApp` и `LoadGenRunner`. Это единственное отличие файла, и оно проверяемо:

```
$ git show HEAD:loadgen/LoadGen.java | diff - loadgen/src/main/java/ru/hikari/loadgen/LoadGen.java
0a1,2
> package ru.hikari.loadgen;
>
```

Декларация package не меняет ни одного наблюдаемого свойства: класс ссылается только на JDK
и на себя. Альтернативы рассматривались и отклонены — вызов по рефлексии
(`Class.forName("LoadGen")`) сохранил бы файл нетронутым, но спрятал бы вызов и оставил
класс навсегда в default package; отказ от аннотаций оставил бы «Spring Boot» только по
имени.

Почему `LoadGen` не переписывается на компонент или на `RestClient`: любая правка его тела —
это изменение таймингов нагрузки, а тайминги нагрузки на стенде и есть измеряемая величина.
Алгоритм остаётся нетронутым. Обратная сторона — «Spring» тут только оболочка, и это надо
назвать прямо, а не выдавать за переход на фреймворк.

### Приложение типа `none`, вывод не смешивается с отчётом

Настройки задаются в самом `main` до `SpringApplication.run`, а не через переменные окружения —
чтобы стенд не зависел от того, что кто-то правит compose:

```java
SpringApplication app = new SpringApplication(LoadGenApp.class);
app.setWebApplicationType(WebApplicationType.NONE);
app.setBannerMode(Banner.Mode.OFF);
app.setLogStartupInfo(false);
```

Дополнительно глушится логирование (`logging.level.root=OFF` системным свойством). Это не
косметика: баннер и сообщения инициализации Spring печатаются в stdout, а `make load-logs`
показывает этот stdout человеку. Один лишний баннер в потоке отчёта — это визуальный мусор в
самом нужном месте, а `LoggingSystem` без настройки ещё и поднимает свой поток.

Веб-сервер не поднимается принципиально: нагрузчик — HTTP-клиент, а свободный порт в контейнере
на стенде не нужен, и наличие сервера только создало бы лишний порт в наблюдении.

### `CommandLineRunner` вместо вызова из `main`

Работа запускается `CommandLineRunner`, который вызывает `LoadGen.main(args)`. Контекст при этом
поднят, а `run` блокирующий — приложение живёт ровно столько, сколько работает нагрузчик, и
завершается вместе с ней.

Остановка: JVM выполняет все зарегистрированные shutdown-hook'и до выхода, поэтому hook с итогом
из `LoadGen` печатает итог независимо от порядка, в котором Boot закроет свой контекст. Порядок
не влияет на результат, и вывод не пересекается, потому что логи выключены.

### Dockerfile: Maven-сборка, запуск jar'ом

```
FROM maven:3.9-eclipse-temurin-21 AS build     # копируем pom.xml и src/, mvn -q package
FROM eclipse-temurin:21-jre                     # копируем target/*.jar
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar /app/loadgen.jar"]
```

`sh -c` остаётся намеренно: `JAVA_OPTS` (`-XX:+UseSerialGC -XX:MaxRAMPercentage=50`) навешивается
через окружение и подставляется в строку запуска — в exec-форме массива подстановки не будет.
Виртуальные потоки создаёт сам `LoadGen` (`newVirtualThreadPerTaskExecutor`), поэтому
`Loom`-настройки Spring Boot на них не влияют.

Слой Maven копируется по `pom.xml` до `src/`: правка исходников не пересобирает зависимости, и
образ слоями короче, как у двух других артефактов.

### `.class` в `loadgen/` — мусор от локальной компиляции

`LoadGen.class` и `LoadGen$Latencies.class` лежат в рабочем дереве как результат ручного `javac`.
Они удаляются, а `target/` добавляется в `.gitignore` (как у `service/` и `provisioner/`).

## Risks / Trade-offs

- **Фреймворк в процессе, которому он не нужен.** Нагрузчик поднимает контекст Spring, чтобы
  вызвать одну функцию. Плата — старт порядка секунды и ~20 МБ fat-jar; на фоне прогона нагрузки
  это неразличимо. Размена — единообразие сборки и возможность запустить нагрузчик без Docker;
  осознанный размен, а не вынужденный.
- **Регрессия в выводе отчёта.** Главный риск: Boot напечатает в stdout что-то лишнее и формат
  сломается. Закрывается двумя мерами — отключение баннера и логов, и проверкой на стенде с
  сравнением отчёта до и после. Формат колонок не переписывается.
- **Тайминги.** Перенос в пакет по умолчанию и вызов из `CommandLineRunner` добавляют к старту
  единицы миллисекунд; на `rps` и перцентили это не влияет, но сравнение прогонов «до/после»
  делается по одному и тому же сценарию, а не по разным.
- **`Skip_specs`.** Контракт не меняется, поэтому дельт нет: требований о способе сборки
  нагрузчика в спеках проекта не существует и не должно появляться — это не поведение стенда.

## Migration Plan

Один шаг: перенос исходников, добавление `pom.xml`, замена сборочной части Dockerfile. Откат —
возврат Dockerfile к `javac` и `LoadGen.java` в корень `loadgen/`. Данные и состояние стенда не
затрагиваются: бюджеты в etcd, настройки провизёра и панели не меняются, пересборка образа
нагрузчика не трогает ни один инстанс.
