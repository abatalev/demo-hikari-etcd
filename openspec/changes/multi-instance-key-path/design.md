# Design

## Context

Мотивация и объём — в `proposal.md`. Кратко про текущее состояние: ключи конфигурации лежат под
единым плоским префиксом `pool.etcd.prefix` (`/config/pool-service/hikari/`), который задаётся в
трёх местах (`.env`, compose, `Makefile`) и одинаков для всех копий сервиса. `EtcdPoolConfigSource`
работает по схеме «снимок + watch с revision+1», сервис поднимается на локальных дефолтах и не
падает без etcd. `EtcdKeys` — чистая функция разбора ключей; `ManagedPool.poolName` уходит в
`application_name` postgres и группируется view `pool_sessions`.

Планируемые требования: `openspec/changes/multi-instance-key-path/specs/` (четыре capability).

## Goals / Non-Goals

Цели:
- Путь ключей `/config/{service}/{group}/{instance}/hikari/` строится сервисом из своих
  сегментов, а не приходит строкой извне; поэтому расхождение префикса между точками
  становится невозможным по построению.
- Гейт трафика: инстанс не принимает запросы, пока не получил конфигурацию; живость процесса
  при этом не зависит от etcd; гейт не откатывается после открытия.
- Стенд из 8 инстансов и 2 балансировщиков, раздельные конфигурации, подъём с таймаутом.

Не-цели:
- Никакой миграции данных: старые ключи в старом префиксе «ломаем» (документируется, станд
  пересоздаётся через `make clean && make up`).
- Никаких активных health-чеков в nginx (в open-source nginx их нет) — только
  `proxy_next_upstream` и `max_fails`.
- Никаких изменений в разборе значений и в самом `ManagedPool`: пул как не менялся, так и не
  меняется.
- Репликация конфигурации на группу инстансов не вводится: «один путь = один инстанс» остаётся
  ограничением.

## Decisions

### 1. `EtcdKeyPath` — чистая функция сборки и проверки пути

Новый класс `com.example.poolsvc.etcd.EtcdKeyPath` строит путь
`{root}/{service}/{group}/{instance}/hikari/` и проверяет сегменты: не пустые и без `/`.
Проверка выполняется только при `pool.etcd.enabled=true` (при выключенном источнике путь не
нужен). Чистая функция — под юнит-тест без etcd, как `EtcdKeys`.

Почему отдельный класс, а не метод в `EtcdPoolConfigSource`: тот же принцип, что в `EtcdKeys` —
правила адресации можно проверить тестами; источник конфигурации остаётся тонким.

### 2. `EtcdProperties`: `prefix` распадается на `root`/`service`/`group`/`instance`

`prefix` удаляется. Четыре сегмента складываются конфигурацией:
- `root` из `ETCD_ROOT` (дефолт `/config`);
- `service` из `SERVICE_NAME` с фолбэком на `spring.application.name`;
- `group` из `ETCD_GROUP` с фолбэком на `POD_NAMESPACE`;
- `instance` из `ETCD_INSTANCE` с фолбэком на `POD_NAME`.

`group` и `instance` без значения при включённом источнике = пустые сегменты → падение на старте
с именем сегмента. Это осознанное поведение: локально без кубовских переменных нужно либо задать
`ETCD_GROUP`/`ETCD_INSTANCE`, либо выключить источник (`ETCD_ENABLED=false`) — единственный режим,
где вполне допустимо отсутствие пути.

Почему не держать `prefix` строкой: именно строка во `docker-compose.yml`/`.env`/`Makefile` и
была источником расхождений (известная ловушка из AGENTS.md). Собираемый путь исключает класс
ошибок «сервис смотрит в другой префикс, чем сидер».

### 3. Гейт готовности живёт в источнике конфигурации

`EtcdPoolConfigSource` держит `AtomicBoolean trafficAllowed`. Гейт открывается, когда после
применения (снимок или событие watch) в текущем наборе ключей есть хотя бы один распознанный
ключ (`EtcdKeys.ALL`), и никогда не закрывается. Открытие публикуется через
`AvailabilityChangeEvent<ReadinessState> ACCEPTING_TRAFFIC` — именно он управляет дефолтной
готовностью Spring Boot. Зачем условие «распознанный ключ», а не «снимок пришёл»: снимок из
одних опечаток — это ещё не конфигурация, и открывать трафик по нему нельзя.

Отклонённый при проверке конфиг (например, `maximumPoolSize` мусором) гейт НЕ закрывает и НЕ
удерживает: значение из хранилища получено, пул остаётся на последних рабочих значениях, причина
видна в `problems`/`lastError`. Это зафиксировано в спеке `traffic-readiness` и отмечено как
сознательное решение.

Пустой префикс: при снимке без единого ключа до открытия гейта логируется предупреждение с путём
(один раз за прогон, чтобы reconnect-цикл не спамил), а в статус пишется причина неготовности.
После открытия гейта пустой снимок не вредит: трафик идёт на последней применённой конфигурации.

### 4. Блокировка трафика — фильтр на `/api/work`, не на контроллер

Новый `TrafficGateFilter` (Spring `Filter`) отвечает 503 `WorkResponse{ok:false, error:...}` на
`/api/work`, пока гейт закрыт и источник включён. `/api/pool` и `/api/config` не блокируются —
наблюдение обязано работать для неготового инстанса. Почему фильтр: гейт не должен растекаться
по бизнес-логике контроллера, и фильтр срабатывает до входа в метод.

### 5. Health: группы readiness/liveness + отдельный индикатор причины

- `management.endpoint.health.group.readiness.include`: `readinessState,db,poolEtcd`;
- `management.endpoint.health.group.liveness.include`: `ping` — живость ни от чего внешнего не
  зависит (и от etcd в первую очередь);
- бин `poolEtcd` (`HealthIndicator`) отражает состояние гейта со связным сообщением (например,
  «конфигурация не получена, путь /config/…»), чтобы причина была видна и в `/actuator/health`.

Compose-healthcheck и `make up` смотрят в `/actuator/health/readiness`, а не в общий `/health`:
общий статус — агрегат групп, и живость (всегда UP) не должна маскировать неготовность.

### 6. Стенд: 8 экземпляров через YAML-anchor, канонический список в `.env`

Канонический список инстансов — переменная `ETCD_INSTANCES` в `.env` (8 кортежей
`service|group|instance|port`). Его читают: сидер (`etcd-seed`), `Makefile` (через `-include
.env`) и, после `make instances`, оператор. `docker compose` списки разворачивать не умеет,
поэтому 8 сервисов в `docker-compose.yml` описаны явно через общий anchor `x-service` (одинаковый
образ, лимит памяти 512m, healthcheck на readiness), а порты 18081–18088 и сегменты пути заданы
по одному на каждый блок. Порты в кортеже `.env` должны совпадать с портами в compose — расхождение
видно через `make instances` (самоконтроль).

Маршрутизация ручных правок: `I=service-a-group-1-1` адресует один инстанс (из кортежа достаются
service/group/instance и порт), `S=service-a` — все четыре инстанса сервиса, `G=group-1` — все
инстансы группы. Список инстансов в Makefile не дублируется: он читается из `.env`.

`POOL_NAME` каждого инстанса = имени инстанса: иначе view `pool_sessions` сольёт все восемь пулов
в одну строку (application_name был бы одинаковым).

### 7. nginx: шаблон с envsubst

`nginx/lb.conf.template` отдаёт upstream из `server ${BACKEND_N};` (envsubst официального образа),
`proxy_next_upstream error timeout http_502 http_503`, `max_fails=1 fail_timeout=5s`, плюс
`location /healthz { return 200; }` — за него `make up` и дергает балансировщик. Граница
балансировки по сервису: `lb-a` (host 8080) → 4 инстанса `service-a`, `lb-b` (host 8081) → 4
инстанса `service-b`. Отказы на неготовых инстансах nginx открытой редакции не видит заранее —
лечится `proxy_next_upstream` (503 от фильтра гейта) и `max_fails` (под смоченный инстанс трафик
перестаёт идти).

### 8. Нагрузчик: `STATUS_TARGET`

Отчёт нагрузчика брал `/api/pool` с `TARGET`. При балансировке `TARGET` — это nginx, и состояние
пула в репорте мигает между инстансами группы. Добавляется `STATUS_TARGET` (дефолт = `TARGET`),
чтобы отчёт стабильно показывал состояние одного выбранного инстанса.

## Risks / Trade-offs

- **8 JVM без лимитов разнесут хост** → `mem_limit: 512m` на каждый сервис.
- **Open-source nginx не знает о неготовности заранее** → `proxy_next_upstream http_503` +
  `max_fails=1 fail_timeout=5s`; часть запросов до срабатывания может получить 503 с первого
  предплеча; это ограничение документируется.
- **Имена сегментов дублируются между `.env`, compose и nginx-шаблоном** → канонический список в
  `.env` (один источник), `make instances` показывает фактический расклад по пути/порту;
  несовпадение кортежа в `.env` и блока в compose видно, а не молчаливо.
- **Падение при пустой группе/инстансе может удивить локальный запуск без etcd** → режим
  единственный: `ETCD_ENABLED=false`; документируется в README и operations.
- **Watch-поток блокируется на eager fill и дренаже** (существующий инвариант) — не меняется;
  гейт добавляет только одну публикацию события готовности.
- **Старые ключи `make clean` удаляет вместе с томом** → миграции нет, это осознанная ломка,
  документируется.

## Migration Plan

1. `git`-коммит изменений; старые ключи в etcd-томе остаются, но не читаются (путь другой) —
   сервисы их не увидят.
2. `make clean && make up` — том etcd пересоздаётся, сидер раскладывает ключи по восьми путям.
3. Откат: `git revert`, `make clean && make up`.

Стенд не переживает частичный перенос: сервис новой сборки с новым путём и старый том совместимы
только после пересида (`make clean`), поэтому шаг 2 обязателен.

## Open Questions

Нет. Спорные решения (гейт открывается при полученном, но отклонённом конфиге; падение при пустом
сегменте вместо дефолтов; ломка старых ключей без миграции) были согласованы в планировании и
зафиксированы в спеках.
