# Design

## Context

Текущая архитектура сервиса предусматривает, что единственным источником конфигурации пула является etcd. При `pool.etcd.enabled=true`:
- `EtcdPoolConfigSource` строит пути, запускает три потока (`etcd-config-watch`, `etcd-registration`, `etcd-drain-publication`)
- `EtcdConfigWorker` получает снимок ключей и watch с `revision+1`, применяет конфигурацию через `ManagedPool.apply()`
- `InstanceRegistration` создаёт узел регистрации с TTL
- `UnreleasedShrinkPublisher` публикует неосвобождённое сжатие

При отключённом etcd (`pool.etcd.enabled=false`) необходимо, чтобы пул инициализировался статически из `application.yaml` (`pool.db.*`). Важно сохранить полную обратную совместимость: поведение etcd-режима не меняется.

См. `proposal.md` - Why.

## Goals / Non-Goals

**Goals:**
- Добавить статический режим работы без зависимости от etcd
- При `enabled=false` не подключаться к etcd и не запускать его потоки
- Инициализировать `ManagedPool` статической конфигурацией сразу при старте
- Корректно формировать readiness/health при статическом режиме
- Сохранить все существующие инварианты для etcd-режима

**Non-Goals:**
- Динамическое переключение между режимами во время работы приложения
- Поддержка частично статической конфигурации (только full static или full etcd)
- Изменение формата ключей etcd

## Decisions

### Decision 1: Инициализация пула в статическом режиме
**Что:** При `pool.etcd.enabled=false` сразу после создания `ManagedPool` применить начальную конфигурацию из `DbProperties`.

**Почему:** В текущей реализации пул создаётся через `PoolBeansConfiguration`, но получает размер только от `apply()` из `EtcdConfigWorker`. В статическом режиме нет воркера, поэтому нужен явный путь инициализации.

**Альтернативы:**
- Создавать HikariDataSource сразу в конструкторе `ManagedPool` с статическими значениями - но это ломает существующую логику `apply()` (которая умеет пересоздавать пул при изменении конфигурации и делать дренаж)
- Вынести создание пула наружу - избыточное изменение

**Решение:** Добавить в `ManagedPool` метод `applyInitial(DbProperties)` или вызывать `apply()` с `PoolSize` из статических свойств. При этом сохранить текущий механизм (apply с валидацией, recreate при изменении размера).

### Decision 2: Поведение EtcdPoolConfigSource при enabled=false
**Что:** В `EtcdPoolConfigSource` при `properties.isEnabled()==false`:
- Не строить пути для etcd
- Не создавать и не запускать `worker`, `registration`, `publisher`
- `start()` просто логирует и возвращается
- `isTrafficAllowed()` возвращает `true`
- `notReadyReason()`/`notReadyCause()` возвращают `null` (или специальное значение, не влияющее на readiness)

**Почему:** Минимальное изменение. Уже есть проверка `isEnabled()` в `start()`, `isTrafficAllowed()`. Нужно убедиться, что health/readiness компоненты корректно интерпретируют disabled-состояние.

**Решение:** Сохранить текущую структуру, но гарантировать, что при disabled ни один из etcd-потоков не стартует. Также `path()` может возвращать `null` - это уже реализовано.

### Decision 3: Readiness и health при статическом режиме
**Что:**
- `TrafficGateFilter` использует `source.isTrafficAllowed()` - при disabled вернёт `true`. Ок.
- `PoolReadinessState` зависит от состояния пула и источника etcd. При `enabled=false` etcd-состояние не должно делать readiness DOWN.
- `EtcdConfigHealthIndicator` (если есть) должен возвращать UP/не критичное состояние при `enabled=false`.

**Почему:** Readiness должен отражать готовность сервиса принимать трафик. В статическом режиме критерием готовности является успешная инициализация пула из статических настроек.

**Решение:** Проверить реализацию `PoolReadinessState` и `EtcdConfigHealthIndicator`. Скорее всего, нужно добавить проверку `etcdSource.isEnabled()` - если отключён, то etcd-компонент readiness не влияет на результат.

### Decision 4: Валидация статической конфигурации
**Что:** `DbProperties` уже валидируется (`validate()`) при старте через `@ConfigurationProperties`/валидацию. При применении статической конфигурации в `ManagedPool` также использовать те же правила нормализации (`PoolSize.normalize()`).

**Почему:** Единообразие валидации. Как в etcd-режиме применяем нормализованный размер, так и в статическом - те же правила.

**Решение:** Использовать `DbProperties.toHikariConfig(size)` и `PoolSize` с теми же нормализующими правилами. Статическая конфигурация из `application.yaml` должна проходить ту же валидацию диапазонов.

## Risks / Trade-offs

- [Risk] Изменение ключевого архитектурного допущения (только etcd) → влияет на инварианты
  - **Mitigation:** Явно разделить режимы, не смешивать их. При `enabled=false` etcd-компоненты полностью неактивны. Инварианты для etcd-режима не трогаем.

- [Risk] Двойной путь инициализации пула (через apply из etcd vs сразу из статики)
  - **Mitigation:** Оба пути используют один и тот же механизм `apply()` в `ManagedPool` с одинаковой логикой валидации, дренажа, recreate. Это минимизирует расхождения.

- [Risk] Readiness/health могут некорректно трактовать disabled-состояние
  - **Mitigation:** Тщательно проверить `PoolReadinessState`, `TrafficGateFilter`, health indicators. При `enabled=false` etcd-связанные статусы должны игнорироваться.

- [Risk] Тесты, предполагающие etcd-режим по умолчанию
  - **Mitigation:** Новые тесты для статического режима. Существующие тесты не должны ломаться - по умолчанию `enabled=true` сохраняется.
