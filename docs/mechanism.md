# Механизм: от `etcdctl put` до нового числа коннектов

Документ описывает весь путь изменения конфигурации и все решения, которые на этом пути
принимаются. Ссылки на строки — на текущее состояние кода, при правках могут сдвинуться.

## Путь целиком

```
make set-max-connections SIZE=100 S=service-a
     │  etcdctl put /config/services/service-a/maxConnections 100
     ▼
провизёр делит бюджет между живыми инстансами сервиса (сумма долей = 100)
     │  etcdctl put .../instances/service-a-group-1-1/hikari/maximumPoolSize 25
     ▼
jetcd: событие watch (WatchResponse с батчем событий)
     │  EtcdPoolConfigSource.onEvent()            etcd/EtcdPoolConfigSource.java
     │    keys.put(key, value) или keys.remove(key) — полное состояние пути в памяти
     ▼
EtcdKeys.parse(keys, path())                     etcd/EtcdKeys.java:45
     │    ключи → HikariSettings; нечитаемое значение → в problems, остальное применяется
     ▼
.settings().resolve(defaults)                      pool/HikariSettings.java:46
     │    null → локальный дефолт из application.yml
     ▼
ManagedPool.apply(desired, reason)                 pool/ManagedPool.java:70  (synchronized)
     │
     ├─ normalize()                                pool/HikariSettings.java:69
     │    вне диапазона → InvalidSettingsException → REJECTED, пул не тронут
     │    мягкие проблемы → warning + починка
     │
     ├─ sameTarget() == false (jdbcUrl/креды/имя) → create() + drain()   → RECREATED
     │
     ├─ diff() пуст                                → ничего не делать     → UNCHANGED
     │
     └─ applyOnLivePool()                          pool/ManagedPool.java:112
          максимум/минимум/таймауты через HikariConfigMXBean             → RESIZED
```

## Путь конфигурации

Путь строится сервисом из сегментов (`EtcdKeyPath.build`), а не приходит строкой извне:

```
{ETCD_ROOT}/services/{service}/groups/{group}/instances/{instance}/hikari/
```

- `root` — `ETCD_ROOT`, дефолт `/config`;
- `service` — `SERVICE_NAME`, фолбэк `spring.application.name`;
- `group` — `ETCD_GROUP`, фолбэк `POD_NAMESPACE`;
- `instance` — `ETCD_INSTANCE`, фолбэк `POD_NAME`.

Сегменты проверяются на пустоту и на отсутствие `/`; при `pool.etcd.enabled=true` пустой или
битый сегмент прекращает запуск с именем проблемного сегмента. Выключенный источник
(`ETCD_ENABLED=false`) путь не собирает и ничего не проверяет.

`EtcdPoolConfigSource` хранит собранный путь в константе конструктора и использует его во всех
операциях: снимок, watch, shortKey, статус. Провижер (`provisioner/`) собирает путь по тем же
правилам, поэтому расхождение «провижер пишет в другой путь, чем читает сервис» исключено по
построению.

## Регистрация инстанса в etcd

Ключи конфигурации читает и применяет конфиг-воркер; сам себя в хранилище инстанс отмечает
отдельно — узлом регистрации, на уровень выше `hikari/`:

```
{root}/services/{service}/groups/{group}/instances/{instance}   ← узел регистрации (имя = инстанс)
{root}/services/{service}/groups/{group}/instances/{instance}/hikari/{ключ}   ← конфигурация
```

Узел создаётся на старте при включённом источнике (`EtcdPoolConfigSource.registrationLoop()`)
по схеме «аренда»: `Lease.grant(ttl)` → `put(узел, пустое значение, lease_id)` → keepalive каждые
`ttl/3`. TTL по умолчанию 15с (`pool.etcd.registration-ttl`, env `ETCD_REGISTRATION_TTL`),
keepalive — `keepAliveOnce` в своём цикле. Всё это — в отдельном daemon-потоке
`etcd-registration`: keepalive не должен блокировать `etcd-config-watch` (тот занят снимком,
apply, eager fill и дренажом).

Жизненный цикл узла:

| событие | что с узлом |
|---|---|
| старт инстанса | появляется (grant + put на аренде) |
| штатная остановка | исчезает немедленно: `revoke(lease_id)` в `stop()` до закрытия клиента; если отзыв не успел (обрыв) — по TTL |
| падение процесса | исчезает сам по истечении TTL аренды (keepalive молчит) |
| обрыв etcd | аренда истекает, узел пропадает; при возврате etcd цикл с backoff'ом перерегистрирует инстанс |
| `ETCD_ENABLED=false` | регистрация не запускается вовсе — путь не собирается, как и у конфиг-источника |

Ключевое свойство: узел лежит **вне префикса `hikari/`**, поэтому конфиг-воркер его не замечает —
снимок и watch используют префикс `{instance}/hikari/`, узел не попадает ни в снимок, ни в
события, не порождает «неизвестный ключ» и не дёргает гейт. Готовность и трафик регистрация не
меняет: «зарегистрирован, но не готов» — нормальное состояние. Значение узла пока пустое
(заполнение — отдельная задача).

## Провижирование конфигурации

Конфигурацию в пути инстанса раскладывает отдельный сервис — провизор
(`provisioner/`, `ConfigProvisioner`). Он наблюдает за деревом `{root}/services/`, а не за одним
инстансом, и держит инвариант: **ключи конфигурации инстанса существуют тогда и только тогда,
когда существует его узел регистрации и узел получил долю сервисного бюджета**.

Провизор запускается **двумя репликами**, работает по одной на сервис. Кто ведёт какой сервис —
решают выборы лидера (раздел «Выборы лидера» ниже); фолловер простоя ждёт и не трогает
конфигурацию. Каждая реплика держит свой воркер на поддерево сервиса, которым в данный момент
руководит (`ProvisioningWorker`): сверка (`reconcile`) + watch с `revision + 1` на префиксе
`{root}/services/{service}/`.

Оба потока событий приводят к одному и тому же — **пересчёту всего сервиса**: доли считаются по
живым узлам целиком, поэтому изменение одного узла меняет доли всех.

| событие | что делает провизор |
|---|---|
| инстанс зарегистрировался (PUT узла) | пересчёт сервиса: новому узлу достаётся доля, доли остальных пересчитываются |
| инстанс исчез (штатная остановка, краш, истёк TTL) | удаление префикса `hikari/` инстанса + пересчёт сервиса |
| изменился `{service}/maxConnections` или `{service}/minConnections` | пересчёт сервиса |
| лидер сервиса упал / потерял аренду (см. «Выборы лидера») | фолловер перехватывает: полная сверка поддерева — раздача долей, очистка всего, что конфигурацией не обеспечено |
| сервис полностью исчез из дерева | выборы за него завершаются: свой ключ кампании удаляется, воркер останавливается |
| изменение ключа `hikari/*`, кроме `maximumPoolSize` | игнорируется — правка оператора живёт, пока жив узел |

Окна между снимком и подпиской нет — тот же аргумент `revision + 1`. Любой обрыв etcd возвращает
воркер к полной сверке с backoff'ом: пропущенные при обрыве события догоняет свежий снимок.

## Распределение сервисного бюджета

Размер пула инстанса — не самостоятельная настройка, а **доля сервисного бюджета**. Бюджет лежит
в etcd, поэтому оператор меняет его на живом стенде без правки конфигурации и перезапуска:

```
{root}/services/{service}/maxConnections   ← бюджет N, сумма долей сервиса
{root}/services/{service}/minConnections   ← минимальная доля m
```

**Почему это дело провизора, а не инстанса.** Инстанс видит только свой префикс
`.../{instance}/hikari/` и не знает ни про бюджет, ни про число соседей. Делить на его стороне
значило бы расширить его watch на всё поддерево сервиса — N watch-потоков вместо одного и
зависимость гейта трафика от чужих ключей. Провизёр поддерево уже держит.

**Жизненный цикл ключей.** Оба ключа создаются при появлении первого узла сервиса тем же
put-if-absent, что и стартовые ключи инстанса: дефолт из конфигурации провизора
(`PROV_MAX_CONNECTIONS` = 100, `PROV_MIN_CONNECTIONS` = 1) вступает в силу только если ключа нет,
поэтому правка оператора не перетирается. В отличие от инстантных ключей, сервисные **не удаляются
при исчезновении последнего узла**: rolling update даёт окно, когда живых узлов нет вовсе, и удаление
ключа сбросило бы операторский бюджет на дефолт.

**Формула.** Для N, минимума m и n живых узлов:

```
serve = min(n, N div m)          сколько инстансов обслуживают трафик
base  = N div serve              базовая доля
доля_i = min(base + (i < N mod serve ? 1 : 0), 200)
```

Остаток достаётся первым инстансам в порядке сортировки по полному ключу узла, поэтому доли не
«дрожат» на ±1 при пересчёте с одним и тем же составом. Сумма долей равна N — потолок защищает базу
(`max_connections` у postgres) от перерасхода. Ключевое свойство: если `n × m ≤ N`, то
`N div n ≥ m` и обычный равномерный сплит сам даёт каждому не меньше минимума — отдельной ветки для
«нормального режима» нет, минимум включается сам собой при нехватке бюджета.

**Случаи отказа (fail-closed).** Провизёр в таких случаях не меняет ничего и пишет WARN с числами:
`N < m`; `m` выше верхней границы доли; нечисловое значение сервисного ключа. Опечатка в etcd не
должна обнулять работающий сервис.

**Избыток.** Инстанс, которому не досталась доля, теряет конфигурацию целиком — и получает 503 на
`/api/work` и `readiness: DOWN`, то есть ровно то же состояние, что «ещё не провижен». Значение `0`
здесь не годится: сервис отклонил бы конфиг целиком (`POOL_SIZE_MIN = 1`), инстанс продолжал бы
работать на старом размере и светить `REJECTED`.

**Управляемый ключ.** `maximumPoolSize` — единственный ключ, который провизёр перезаписывает.
Условие txn инвертировано: `If(значение == доля)` → обходная ветка пуста, записи при равенстве не
происходит вовсе, иначе выполняется ветка `Else` и ключ пишется; отсутствующий ключ — тот же случай
(сравнение значения с несуществующим ключом в etcd никогда не проходит, поэтому `Else` и создаёт
ключ). Это один поход в etcd, а две реплики в окне перехвата лидерства пишут одно и то же (записи
идемпотентны). `connectionTimeoutMs` и остальные ключи остаются put-if-absent — ручные правки
оператора переживают перезапуск инстанса.

Следствие для ручных правок: `maximumPoolSize` в etcd живёт **до ближайшего пересчёта** (изменение
бюджета, изменение состава сервиса, рестарт провизёра, обрыв etcd). `make set-size`,
`set-service-size`, `set-group-size` — временные оверайды для показа, а не способ задать размер
пула. Остальные ключи в etcd живут **пока жив узел инстанса**: остановленный инстанс теряет
конфигурацию целиком (вместе с ручными правками) и при следующем старте получает значения заново.
При полном останове стенда (`docker compose down`) провизор останавливается вместе со всеми —
успеет ли он увидеть `DELETE` узлов, зависит от порядка остановки; `make up` в любом случае
поднимает стенд корректно: ключи живых узлов провизор либо сохраняет (они ещё в etcd), либо
провижит заново.

Порядок старта в compose не важен: инстансы не ждут подготовки конфигурации — провизор сам
нагоняет её по факту регистрации узла. Окно «зарегистрирован, но ещё не провижен» закрывает гейт
трафика (раздел ниже).

## Выборы лидера

«Работает один» — это не конфигурация, а соглашение на общем ключевом пространстве etcd.
Каждая реплика ведёт свою аренду (одну на процесс) и кампанию по каждому живому сервису:

```
{root}/provisioner/leader/{service}/<hex аренды реплики>   ← ключ кампании
```

Ключ кампании пишется атомарным txn «ключа нет → put» и привязан к аренде реплики. **Лидер —
ключ с наименьшим `create_revision`** (старейший из живых в префиксе сервиса): строкового порядка
тут нет — `hex аренды` не упорядочен по времени создания. Значение ключа — имя реплики
(`PROV_NAME`), по нему удобно смотреть `make leader`.

Набор сервисов реплика выводит сама из узлов регистрации дерева `{root}/services/` (чистая
функция `InstanceKey.liveServices`: сегмент `{service}` ключей-узлов; ключи конфигурации, обрывки
путей и всё вне `services/` не считаются). Списка сервисов в конфигурации нет — провизор по-прежнему
не требует список инстансов.

Три собственных потока реплики:

| поток | что делает |
|---|---|
| `provisioner-lease` | одна аренда на реплику: `grant(TTL)` + keepalive каждые TTL/3; сбой keepalive → аренда отзывается, воркеры все остановлены, повтор с backoff 1→30с |
| `config-provisioner-election` | поллинг дерева сервисов ~1с: для каждого живого сервиса — txn «ключа нет → put» своего ключа кампании, лидер — ключ с наименьшим `create_revision` префикса (без блокирующих ожиданий); ушедшему из дерева сервису — resign своего ключа |
| `provision-worker-<service>` | сверка + watch поддерева сервиса; стартует и останавливается лидерством |

Ключи выборов лежат **вне** `{root}/services/`, поэтому в снимок и watch воркера не попадают
(никаких «неизвестных ключей»), а `liveServices` их не учитывает.

### Переходы ролей

| событие | что происходит |
|---|---|
| сервис появился в дереве (первый узел) | первая же кампания выигрывает её ключ — реплика становится лидером, воркер стартует с полной сверки |
| реплика-лидер упала (SIGKILL) | keepalive молчит, аренда истекает по TTL (`PROV_LEADER_TTL`, 10с), ключ кампании исчезает; фолловер на ближайшем поллинге (~1с) видит себя лидером и перехватывает сервис с полной сверки |
| штатный `stop` лидера | аренда отзывается до закрытия клиента (`revoke`) — ключ кампании исчезает сразу, фолловер перехватывает без ожидания TTL |
| потеря аренды (обрыв etcd дольше TTL/3) | keepalive-сторож останавливает воркеры немедленно; после возврата etcd — новый grant, новые выборы |
| сервис исчез из дерева (последний узел удалён) | выборы за него завершаются: реплика удаляет свой ключ кампании (resign), воркер останавливается |
| рестарт реплики | новый ключ = новый (бо́льший) `create_revision` — реплика стартует фолловером; предпочтительного лидера нет |

### Окно перехвата и «два писателя»

Перехват при крахе лидера занимает **TTL + ~1с**: ключ живёт, пока жива аренда (последний успешный
keepalive был TTL/3 назад, значит до TTL ещё пара keepalive-интервалов), плюс поллинг фолловера. В
этом окне упавший лидер формально ещё «ведёт» сервис (его ключ — старейший), но фактически пишет
только в состоянии живого etcd. Записи провижинга идемпотентны (txn «ключа нет → put» и `del`),
поэтому даже краткое окно «двух писателей» при перехвате безопасно — fencing не нужен.

Симметрия ролей: стартовавший фолловер ничего не пишет в `hikari/*`, но держит памяти столько же,
сколько лидер (та же аренда, те же поллинги). Ограничение прежнее: **один watch-поток на воркер
сервиса**, он же применяет события (eager fill и дренаж тут не участвуют — это домен пула).

## Готовность к трафику (гейт конфигурации)

Пока в пути нет ни одного распознанного ключа (`EtcdKeys.ALL`), инстанс **не готов принимать
трафик**: `/api/work` отвечает 503 (фильтр `TrafficGateFilter`), `/api/pool` и `/api/config`
работают, `/api/config` отдаёт `notReadyReason`. Живость (`liveness`) от etcd не зависит —
процесс жив и докатывает конфигурацию с backoff'ом.

Гейт открывается в `updateReadiness()` после `apply()`: первый снимок или событие, принёсшее
распознанный ключ, публикует `AvailabilityChangeEvent<ReadinessState.ACCEPTING_TRAFFIC>` и
логирует открытие. Там же гейт закрывается, когда распознанных ключей не осталось (провижер
снял конфигурацию — например, инстанс потерял долю бюджета): публикуется
`REFUSING_TRAFFIC`, логируется закрытие; при возврате ключей трафик открывается снова. Закрытие
происходит только по реальным событиям удаления и снимкам при живом etcd — обрыв etcd после
применения конфигурации трафик не останавливает (событий в этом случае не приходит; согласуется
с правилом «обрыв не влияет на пул»). Отклонённая при проверке конфигурация (REJECTED) гейт не
удерживает — значение из хранилища получено.

Пустой снимок до открытия гейта логирует предупреждение с путём один раз за прогон и оставляет
`notReadyReason`: «конфигурация не получена: в пути … нет распознанных ключей». При недоступном
etcd причина другая: «конфигурация не получена: etcd недоступен (…)» — это отдельное поле, не
перекрывающее `lastError`.

Всё это выполняется в одном потоке — `etcd-config-watch` (платформенный daemon-поток,
`EtcdPoolConfigSource#start()`). Метод `apply()` синхронизирован, поэтому два события,
пришедшие подряд, никогда не применятся одновременно.

## Снимок + watch

Периодического опроса etcd нет вообще: конфигурация приезжает событиями. При старте
`EtcdPoolConfigSource:119-141`:

```java
long revision = snapshot(c);   // get по пути инстанса, isPrefix=true
watch(c, revision + 1);       // подписка со следующей ревизии
```

Ключевой момент — `revision + 1`. Ревизия берётся из ответа снимка, поэтому если ключ
поменялся в промежутке между `get` и `watch`, это изменение придёт первым же событием.
Окна «потерянного обновления» не существует.

`snapshot()` (`:160`) полностью перезатирает `keys` свежим содержимым, ставит `connected=true`,
чистит `lastError` и сразу вызывает `apply("etcd-снапшот@rev")`. То есть после любого
переподключения конфиг применяется заново целиком — без дырок и без «частичного» состояния.

`onEvent()` (`:213`) накапливает батч: `PUT` → `keys.put`, `DELETE` → `keys.remove`. Удаление
ключа — не ошибка, а «вернуться к дефолту». Пустые батчи (от etcd прилетают как прогресс-сообщения)
игнорируются, чтобы не дёргать apply.

## Обрывы: три уровня

| что случилось | поведение |
|---|---|
| compaction, рестарт etcd, `onCompleted` | `finished.countDown()` → `watch()` возвращается → новый снимок + новый watch |
| etcd недоступен, таймаут `get` (`call-timeout`, 5с) | `connected=false`, `lastError` заполняется, сон с backoff'ом |
| etcd мигнул на пару секунд | backoff сбрасывается на начальное значение (1с) сразу после первого успешного прохода цикла (`:127`) |

Backoff растёт вдвое от `retry-initial-backoff` (1с) до `retry-max-backoff` (30с). Клиент при
этом не пересоздаётся: `client()` (`:143`) ленивый и под `synchronized`, один `Client` на весь
жизненный цикл. Пересоздавать его пришлось бы ещё и синхронизировать с in-flight watch.

Итог: обрыв связи с etcd не влияет на пул. Он продолжает работать на последнем применённом
конфиге и докатывает изменения, когда etcd вернётся. Сервис при этом не падает и на старте.

## Порядок сеттеров при изменении на живом пуле

`applyOnLivePool()` (`ManagedPool.java:112`) — единственное место, где меняется живой пул.

```java
if (shrinking) {
    setMinimumIdle(mx, ...);   // сначала меньший
    setMaximumPoolSize(mx, ...);
} else {
    setMaximumPoolSize(mx, ...);
    setMinimumIdle(mx, ...);
}
```

**Почему порядок именно такой.** `HikariConfigMXBean` проверяет `minimumIdle <= maximumPoolSize`
в обоих сеттерах. При уменьшении пула со значениями `max=30, minIdle=30` сначала нужно опустить
`minimumIdle` — иначе `setMaximumPoolSize(3)` упал бы с `minimumIdle > maximumPoolSize`, и весь
конфиг (включая таймауты, которые вполне валидны) не применился бы.

Дальше таймауты применяются через `setQuietly` (`:161`): каждый сеттер обёрнут в try/catch,
значение, которое не удалось применить, не роняет остальные — в лог уходит ошибка по этому
одному полю, пул продолжает работать.

**Почему после shrink нужен `softEvictConnections`.** Новый лимит применяется сразу, а вот
лишние idle-соединения живут до следующего прохода HouseKeeper (~30 секунд). В этот промежуток
`/api/pool` показывал бы `total=30` при `maximumPoolSize=3`. `softEvictConnections()` (`:140`)
вытесняет всё сверх `minimumIdle` немедленно, и `total` становится равен `minimumIdle` в тот же
момент.

## eagerFill: почему соединения надо одновременно держать

`eagerFill()` (`ManagedPool.java:179`) — демо-помощь: после увеличения пула сразу открыть нужное
число коннектов, иначе рост виден только под нагрузкой или через ~30 секунд HouseKeeper.

Тонкость, на которой легко ошибиться: соединения нужно **одновременно удерживать**. Если взять
коннект и сразу вернуть, HikariCP отдаст то же самое idle-соединение, и `total` не вырастет.
Поэтому все соединения набираются в список `held` и только в `finally` возвращаются:

```java
while (runtime().total() < target.maximumPoolSize() && System.nanoTime() < deadline) {
    held.add(ds.getConnection());
}
// ... возврат всех разом
```

Дедлайн — 2 секунды (`EAGER_FILL_TIMEOUT`). Он нужен, чтобы насыщенный нагрузкой пул не
подержал watch-поток: `pool.db.eager-fill-on-resize=false` (в `application.yml` это
`POOL_EAGER_FILL`) полностью отключает добивку, и коннекты добираются по мере надобности.

## Пересоздание пула и дренаж

`jdbcUrl`, `username`, `password`, `poolName` через MBean не меняются — определяется это сравнением
`sameTarget()` (`HikariSettings.java:115`). Тогда `create()` (`:212`) собирает новый
`HikariDataSource`, переключает `AtomicReference` на него и закрывает старый.

Проблема: `HikariDataSource.close()` закрывает и активные соединения, запросы в полёте падают
с `08006`. Поэтому `drain()` (`:266`) сначала вытесняет idle через `softEvictConnections()`,
потом ждёт до `pool.db.drain-on-recreate-timeout` (3с), пока активные соединения доработают:

```java
pool.softEvictConnections();
while (pool.getActiveConnections() > 0 && System.nanoTime() < deadline) {
    Thread.sleep(20);
}
```

Что не доработало за 3с — закрывается принудительно, клиенты получат ошибку. Это осознанный
компромисс: повесить переключение навсегда из-за одного долгого запроса хуже.

Переключение происходит через `AtomicReference`, поэтому `JdbcTemplate`, который держит ссылку
на `ManagedPool` (а не на конкретный `HikariDataSource`), продолжает работать без изменений.
Вот ради этого `ManagedPool` и реализует `DataSource` сам, а не отдаёт наружу `HikariDataSource`.

## Валидация

Два уровня, оба в `HikariSettings.normalize()` (`:69`).

**Жёсткий** — `InvalidSettingsException`, конфиг отклоняется целиком, пул остаётся на последнем
рабочем значении:

| поле | диапазон |
|---|---|
| `maximumPoolSize` | 1..200 |
| `minimumIdle` | 0..200 |
| `connectionTimeoutMs` | 250..600000 |
| `idleTimeoutMs` | 0 (выключен) или 10000..3600000 |
| `maxLifetimeMs` | 0 (выключен) или 30000..3600000 |
| `validationTimeoutMs` | 250..60000 |
| `leakDetectionThresholdMs` | 0 (выключен) или 2000..600000 |
| `jdbcUrl` | обязан начинаться с `jdbc:` |
| `username`, `poolName` | обязательны |
| `password` | обязателен, но может быть пустой строкой (вход без пароля) |

**Мягкий** — warning в лог, значение чинится, конфиг применяется:

- `minimumIdle > maximumPoolSize` → `minimumIdle` понижается до `maximumPoolSize`
  (важно: `make set-min-idle SIZE=8`, а потом `make set-size SIZE=3` не уронит конфиг);
- `idleTimeout > 0 && minimumIdle == maximumPoolSize` → предупреждение, что таймаут не применится;
- `leakDetectionThresholdMs >= connectionTimeoutMs` → предупреждение о ложных срабатываниях.

Почему одно и то же нарушение трактуется по-разному: `minimumIdle > max` — это следствие
нормализации (не задан `minimumIdle`, а `maximumPoolSize` уменьшили), чинить безопасно. А
`maximumPoolSize=0` — осмысленное «хочу ноль коннектов», которое технически невозможно, и
молча подменять его на 1 было бы враньём.

Предупреждения показываются только когда конфиг реально изменился (`ManagedPool.java:98`),
иначе они сыпались бы на каждый `put` того же значения.

## Плохое значение vs плохой конфиг

Два разных уровня деградации, и это осознанное решение:

| ситуация | что происходит |
|---|---|
| значение не число (`banana`) | игнорируется **только этот ключ**, в настройках остаётся `null` → возьмётся дефолт; остальные ключи применяются; причина попадает в `etcd.problems` в `/api/pool` |
| значение вне диапазона (`0`) | отклоняется **весь конфиг целиком**, потому что изменить именно это значение нельзя, а оставить его как есть — значит нарушить инвариант |

Результат: опечатка в одном ключе не блокирует правку соседних, но бессмысленное значение
размеров не применяется молча. Событие `put` с тем же значением, которое уже применено,
проходит как `UNCHANGED` — ни лога, ни apply.

## Исходы применения

`ManagedPool.Outcome` (`:381`) — что в итоге произошло:

| outcome | когда | видно |
|---|---|---|
| `CREATED` | первый пул в процессе | `HikariCP '<имя инстанса>' создан: ...` |
| `RESIZED` | настройки изменились, пул тот же | `обновлён на лету: maximumPoolSize: 10 -> 25` + строка eager fill при росте |
| `RECREATED` | сменилась цель (jdbcUrl/креды/имя) | `пересоздан (сменилась цель: jdbcUrl/креды/имя)`, перед этим строки про дренаж |
| `UNCHANGED` | diff пуст | ничего, только debug |
| `REJECTED` | `normalize()` бросил исключение | `конфиг отклонён (...), остаёмся на предыдущих значениях: ...` + причина в `etcd.lastError` |

Результат последнего применения виден в `/api/pool` → `etcd.lastOutcome`, счётчик — в
`etcd.applyCount`, счётчики ресайзов и пересозданий — в `pool.resizeCount` / `pool.recreationCount`.

## Неочевидное про первый apply

На старте `lastOutcome` почти всегда `RESIZED`, хотя никто ничего руками не менял. Это нормально:
локальный дефолт `connectionTimeoutMs` в `application.yml` — 30000, а config-provisioner кладёт 3000.
Первое применение честно приводит пул к etcd-значению. Смотреть надо на `pool.lastChangeReason`
— он покажет, откуда пришло изменение (`etcd-снапшот@5`, `etcd@7 [maximumPoolSize=put]` и т.п.).
