# Глоссарий

Термины домена так, как они используются в README, `docs/` и `openspec/`. Определения — контракт
поведения, а не привязка к классам: если реализацию можно поменять, не меняя смысла, в глоссарии
этого нет. Канонические разделы: [mechanism.md](mechanism.md) (путь изменения),
[operations.md](operations.md) (эксплуатация), [api.md](api.md) (HTTP), [experiments.md](experiments.md)
(замеры). Спецификации — в `openspec/specs/`.

## Роли и сущности флота

**Инстанс (instance)** — один процесс сервиса со своим пулом соединений. Сегмент пути
`{root}/services/{service}/groups/{group}/instances/{instance}/`, имя инстанса — из окружения
(`ETCD_INSTANCE` → `POD_NAME` → `HOSTNAME`, в контейнере короткий hex-ID). `POOL_NAME` = имя
инстанса и `application_name` пула в postgres, поэтому уникален на весь стенд.

**Сервис (service)** — именованная группа инстансов одного приложения (`service-a`, `service-b`).
У сервиса свои бюджет, база, точка входа балансировщика и своя реплика-лидер провижёра. Сегмент
пути — `SERVICE_NAME`.

**Группа (group)** — подмножество инстансов сервиса (`group-1`, `group-2`). Группа — **глобальный
флот**: маркер `{root}/groups/{group}/active` общий для всех сервисов, но бюджет каждого сервиса
считается свой. Сегмент пути — `ETCD_GROUP`.

**Флот (fleet)** — совокупность инстансов. *Активный флот* — инстансы групп с активным маркером,
*неактивный* — с выключенным. Слово «флот» в метриках (`provision_fleet_*`) — величины сервиса
целиком, а не одного узла.

**Тёплый флот** — неактивные инстансы при `R ≥ 1`: получают конфигурацию, держат пул ровно `R` и
обслуживают трафик. **Холодный флот** — при `R = 0`: конфигурации нет, пула нет, 503 и
`readiness: DOWN`.

**Инстанс без доли** — живой узел, которому не досталось доли бюджета (активный бюджет не тянет
минимум). Состояние то же, что у холодного узла: пула нет, `/api/work` = 503, `readiness: DOWN`.
Это не ошибка, а закрытый гейт трафика.

**Узел регистрации** — ключ `{root}/services/{service}/groups/{group}/instances/{instance}`, который
инстанс создаёт на старте на аренде etcd. Лежит **вне** префикса `hikari/`, поэтому конфиг-воркер
его не видит и гейт от него не зависит. Исчезает при остановке (штатно — `revoke`, при падении — по
TTL).

**Нагрузчик (loadgen)** — отдельное приложение (`loadgen-a`/`loadgen-b`), гоняющее трафик через
балансировщик. Выводит только отчёт о прогоне (rps, перцентили, ошибки); состояние пула и базы
снимает наблюдение, а не он.

**Балансировщик (Traefik)** — один процесс с двумя точками входа: `web-a` (`:8080`) обслуживает
только `service-a`, `web-b` (`:8081`) — только `service-b`. Состав бэкендов читает из docker-событий,
неготовый инстанс исключает опросом готовности (~1с).

**Точка входа (entrypoint)** — именованный маршрут балансировщика на сервис (`web-a`/`web-b`).
Границу по сервису держит привязка маршрута к точке входа, а не отдельный процесс.

## Бюджет и распределение

**Бюджет активного флота `N`** — ключ `{root}/services/{service}/activeMaxConnections`. Верхний
потолок суммы соединений активного флота; резерв неактивных вычитается из него. По умолчанию
`PROV_ACTIVE_MAX_CONNECTIONS` = 100.

**Минимальная активная доля `m`** — ключ `.../activeMinConnections`. Активный узел получает долю,
только если она не меньше `m`; иначе он остаётся без доли. По умолчанию `PROV_ACTIVE_MIN_CONNECTIONS`
= 1.

**Резерв неактивного флота `R`** — ключ `.../inactiveMaxConnections`. Размер пула каждого
неактивного узла; `0` = холод. По умолчанию `PROV_INACTIVE_MAX_CONNECTIONS` = 1.

**Доля (share)** — часть бюджета, причитающаяся одному активному узлу; провижёр записывает её в
управляемый ключ `maximumPoolSize`. Доли не «дрожат» при повторном пересчёте с тем же составом:
остаток получают первые по сортировке полного ключа узла.

**Управляемый ключ** — `maximumPoolSize`. Единственный ключ, который провижёр перезаписывает при
каждом пересчёте (условие txn инвертировано: при равенстве записи нет). Ручная правка живёт до
ближайшего пересчёта. Остальные ключи инстанса — put-if-absent и переживают ручные правки, пока жив
узел.

**Публикация неосвобождённого сжатия, долг** — ключ `{instance}/unreleasedConnections`, равный
`max(0, удерживаемое − maximumPoolSize)`. Инстанс пишет его рядом с узлом регистрации, по той же
аренде. Долг — это то же число с точки зрения провижёра: сколько узел держит **сверх** потолка.

**Оценка занятости** — «потолок + долг» по узлу; сумма по флоту. Если публикации нет или она
относится к прежнему потолку (`mod_revision` не новее), берётся **худший случай** — узел держит свой
текущий потолок.

**Худший случай** — оценка, при которой узел считается удерживающим весь свой потолок. Ошибка
односторонняя: флот простаивает, но не выходит за `N`.

**Свободное место для роста** — `max(0, N − сумма занятости)`. Выдаётся один раз на сервис, в
порядке сортировки полного ключа: растущий забирает всё, что освободилось, остальные ждут
фактического освобождения.

**Приказ** — размер, который провижёр пишет узлу: `min(доля, потолок + рост)`. Нулевой приказ не
пишется вовсе (0 из etcd сервис отклоняет).

**Зависшее сжатие** — узел с **подтверждённой** публикацией, значение которой не уменьшается дольше
порога (~30с). Узлы без публикации зависшими не считаются: иначе ими выглядел бы весь флот на
штатном перезапуске.

**Fail-closed** — при отказе распределения (`N < m`, `m > PROV_MAX_SHARE`, `R` вне
`{0} ∪ [1..200]`, `R×k > N`, активные есть и `N′ < m`, не-число) провижёр **ничего не меняет** и
пишет WARN с числами. Опечатка в etcd не должна обнулить живой сервис.

**Символы формулы.** `k` — число неактивных узлов сервиса; `n_акт` — число активных;
`N′ = N − R×k` — бюджет активных после резерва; `serve = min(n_акт, N′ div m)` — сколько активных
обслуживают; `base = N′ div serve`; доля = `min(base + (первым N′ mod serve ? 1 : 0),
PROV_MAX_SHARE)`. Сумма активных долей + резерв неактивных = `N` (доли выше границы усекаются, тогда
сумма меньше `N` намеренно).

## Жизненный цикл пула

**Гейт трафика (гейт конфигурации)** — инстанс не принимает трафик, пока в его пути нет ни одного
распознанного ключа. Гейт открывает первый распознанный ключ и закрывается, когда распознанных
ключей не осталось (провижёр снял конфигурацию); неготовый инстанс остаётся наблюдаемым. Живость от
гейта не зависит.

**Применение (apply)** — пересчёт желаемого состояния по снимку/событию и приведение к нему живого
пула. `apply()` синхронизирован: два события не применяются одновременно.

**Ресайз (resize), рост и сжатие (grow/shrink)** — изменение размера живого пула. При уменьшении
`minimumIdle` ставится первым, затем `maximumPoolSize`; при увеличении — наоборот. После сжатия
вызывается `softEvictConnections()`, иначе лишние idle висят до HouseKeeper (~30с).

**Дренаж** — перед закрытием пула (`softEvictConnections()` и ожидание до
`drain-on-recreate-timeout`, 3с) дать активным соединениям доработать. Без дренажа запросы в полёте
падают с `08006`. Дренаж идёт **до** отзыва аренды узла регистрации.

**Пересоздание (recreate)** — создание нового пула, когда пула нет, а пришла ненулевая доля (снятие
конфигурации и её возврат). Переключение — через `AtomicReference`, поэтому потребители не
пересоздаются.

**Поколение пула (generation)** — счётчик, растущий при каждом пересоздании (`pool_generation`).
Состояние пула публикуется из `runtime()`, а не из SPI: SPI-адаптер отдаёт только события, иначе
гейджи привязались бы к первому поколению и после recreate показывали ноль.

**Eager fill** — добор соединений сразу после увеличения пула (`POOL_EAGER_FILL`, на стенде `true`).
Соединения удерживаются одновременно, иначе HikariCP вернёт то же idle-соединение и `total` не
вырастет; дедлайн ~2с, чтобы не задерживать watch-поток.

**Исход применения (outcome)** — `CREATED` (первый пул), `RESIZED` (размер изменился), `RECREATED`
(пул был закрыт), `CLOSED` (целевой размер 0), `UNCHANGED` (diff пуст), `REJECTED` (конфиг
отклонён — пул остаётся на последнем рабочем значении).

**Установившийся размер против целевого** — `maximumPoolSize` это потолок, `total` — сколько
соединений открыто сейчас; они расходятся при сжатии (долг) и недоборе (пул ещё не добит).

## Конфигурация и etcd

**Распознанный ключ** — ключ пути `hikari/` из закрытого перечня, который сервис умеет применить:
`maximumPoolSize`, `minimumIdle`. Всё остальное — «неизвестный ключ»: логируется один раз и
игнорируется. Не-число в одном ключе не мешает применить соседние.

**Размер из etcd против локальной конфигурации** — из etcd приходит **только размер**; цель
соединения и таймауты (`DB_URL`, `DB_USER`, `DB_PASSWORD`, `POOL_CONNECTION_TIMEOUT_MS` и прочие
`POOL_*`) заданы локально на процесс и меняются только перезапуском. Пароль в etcd не хранится.

**Путь конфигурации** — `{root}/services/{service}/groups/{group}/instances/{instance}/hikari/`,
собирается из сегментов, а не берётся строкой. Сервис и провижёр собирают его по одним правилам,
поэтому расхождение «пишет в другое место, чем читает» исключено по построению. При
`ETCD_ENABLED=true` пустые `group`/`instance` валят старт с именем сегмента.

**Снимок + watch, `revision + 1`** — при старте (и после любого обрыва) берётся снимок пути, а
подписка идёт с `revision + 1` ответа снимка. Окна потерянного обновления нет.

**Аренда (lease), TTL, keepalive** — узел регистрации и публикация долга живут на аренде etcd.
Узел: TTL `ETCD_REGISTRATION_TTL` (15с), keepalive каждые TTL/3 (5с), отдельный поток
`etcd-registration`. Штатная остановка — `revoke` узла сразу.

**Аренда выборов, `PROV_LEADER_TTL`** — своя аренда провижёра (10с), на которой держатся ключи
кампании. Потеря аренды (keepalive-сторож) немедленно останавливает воркеры сервисов.

**Backoff** — переподключение к etcd с паузой, растущей вдвое от `retry-initial` (1с) до
`retry-max` (30с). Обрыв etcd не влияет на пул: он работает на последнем применённом конфиге.

## Провижирование

**Провижёр (config-provisioner)** — сервис, раскладывающий конфигурацию. Держит инвариант: ключи
`hikari/` инстанса существуют тогда и только тогда, когда жив его узел регистрации **и** узел
получил долю бюджета. Запускается двумя репликами (`PROV_REPLICAS`), работает по одной на сервис.

**Лидер и фолловер** — на каждый сервис активна ровно одна реплика. Лидер — ключ с наименьшим
`create_revision` в `{root}/provisioner/leader/{service}/` (значение — имя реплики). Роли
симметричны, предпочтительного лидера нет, рестарт разворачивает роли — это норма.

**Выборы лидера** — поллинг ~1с: каждая реплика делает снимок дерева сервисов и кампанию (txn
«ключа нет → put») по каждому живому сервису. Набор сервисов выводится из живых узлов дерева, списка
в конфигурации нет. Окно перехвата при крахе лидера — TTL + ~1с поллинга; записи идемпотентны,
поэтому «два писателя» в окне безопасны.

**Сверка (reconcile)** — полный пересчёт сервиса по свежему снимку: раздача долей живым узлам,
очистка префиксов `hikari/` у исчезнувших узлов и осиротевших путей. Выполняется на старте, при
перехвате лидерства и после каждого обрыва etcd.

**Маркер активности группы** — ключ `{root}/groups/{group}/active` (глобальный для всех сервисов):
«false» в любом регистре выключает группу, отсутствие/мусор/«true» — активна. Читается **поллингом**
~1с, не событиями; обрыв etcd держит последнее известное состояние.

**Сервисные ключи бюджета** — `activeMaxConnections` (N), `activeMinConnections` (m),
`inactiveMaxConnections` (R). Создаются put-if-absent при первом узле сервиса и **переживают
опустение сервиса** (нужно для rolling update): ручная правка не перетирается, ключи удаляются
только руками.

**Осиротевший префикс** — ключи `hikari/` без живого узла регистрации; удаляются при сверке.

## Готовность и трафик

**Готовность (readiness)** — `/actuator/health/readiness` = `readinessState,db,poolEtcd`. Закрытый
гейт отдаёт DOWN с причиной в деталях. Именно сюда смотрят compose-healthcheck, `make up` и опрос
балансировщика.

**Живость (liveness)** — `/actuator/health/liveness` = только `ping`. От etcd и базы не зависит:
обрыв etcd не роняет процесс и не валит liveness.

**Причина неготовности (`NotReadyCause`)** — закрытый набор `no_config_keys` (в пути нет
распознанных ключей), `etcd_unavailable` (хранилище недоступно) и `none` (причины нет — гейт открыт
или источник выключен). Текст для человека выводится из кода, а не хранится рядом.

**503** — два разных случая: от гейта конфигурации (до входа в метод, без `durationMs`/`dbMs`/
`rows`) и от насыщения пула (конфигурация есть, готовность UP, все соединения заняты,
`durationMs ≈` таймауту ожидания). Наблюдение в обоих случаях работает.

## Наблюдение

**Дверь сигналов** — `otel-collector` (`:4318` приём OTLP, `:9464` её метрики). Единственная точка
приёма метрик, трасс и журналов приложений; раздаёт их по хранилищам, а сборщик забирает у неё
только метрики. Ограничитель памяти — **по одному на сигнал** (трассы → журналы → метрики
последними), иначе отказ во всех сигналах разом.

**Витрина** — Grafana (`:3000`), три панели, поставляются **только на чтение**. Правка в интерфейсе
перезаписывается при рестарте.

**Правило молчания** — по одному `absent()`-правилу на каждый инстанс из `docker compose ps`
(`prometheus/rules/instances.yml`, генерация `make silence-rules`). Ряд, по которому судят молчание, —
состояние пула: он есть у процесса всегда, поэтому инстанс без доли видим, а упавший — нет.

**Признаки (labels)** — общие задаёт окружение: `service`, `group`, `node` у инстанса, `replica` у
провижёра. Метку `instance` не заводят: она зарезервирована Prometheus за адресом цели. Признак
`pool` у приборов событий тоже не заводят: пул в процессе один.

**Событие механизма** — решение пути `put` → resize (применение конфига, пересоздание, записи
провижёра, выборы), попадающее в трассу общей долей `OTEL_TRACES_SAMPLING`, как и обслуживание
запросов: отдельного трассировщика «всегда» нет. Событие из фонового потока — самостоятельная
трасса; из потока запроса (ожидание соединения) — часть трассы этого запроса. Гарантия
применения — журнал, а не трасса.

**`pool_etcd_problems`** — журнал проблем источника за всё время процесса, **не очищается** при
исправлении значения. Текущее состояние смотрят в `pool` / `config`.

**Значения против состояния в метриках** — значений конфигурации в метриках нет: вместо них
числовые гейджи применённых величин, состояние из закрытого набора (`pool_config_state{state}`,
`pool_not_ready_reason{reason}`) и счётчики.

## Часто путают

| одно | другое | разница |
|---|---|---|
| бюджет `N` | потолок базы `POSTGRES_MAX_CONNECTIONS` (120) | механизм бюджет базы не проверяет; запас 20 меньше доли (25) и больше служебных сессий (7–9), поэтому превышение ловит база, а `psql` проходит |
| доля | `maximumPoolSize` | доля — это величина, которую провижёр кладёт в управляемый ключ; ручная правка ключа живёт до ближайшего пересчёта |
| оценка занятости | подтверждённое сжатие | оценка в худшем случае выше бюджета, и её максимум **не алертится**; сжатие считается только по подтверждённым публикациям |
| готовность (readiness) | живость (liveness) | readiness зависит от гейта и базы, liveness — только `ping` |
| узел регистрации | ключи конфигурации | узел вне `hikari/`, на готовность не влияет; ключи появляются/исчезают вместе с ним |
| неактивный флот | инстанс без доли | неактивный при `R ≥ 1` обслуживает трафик на резервном размере; без доли — 503 всегда |
| холодный флот (`R=0`) | ошибка конфигурации | холод — намеренное снятие конфигурации, а не сбой |
| `pool_config_state` | `pool_etcd_problems` | первое — текущее состояние apply, второе — накопленный журнал |
