# Эксплуатация: troubleshooting, переменные, локальный запуск, ограничения

## Prerequisites

| нужно | для чего | обязательно? |
|---|---|---|
| Docker + `make` | сам стенд | да |
| `curl` | healthcheck в `make up`, все `make`-цели обращения к API | да |
| `python3` | `make pool` (сводка `scripts/pool-all.py`) и `make work` (форматирование JSON) | да |
| `maven` | только `make test`; образ сервиса собирает maven внутри себя | нет |

Отсутствие `python3` — самая частая причина, почему `make up` падает на последнем шаге, когда
стенд уже поднят. Обойти можно, вызвав API напрямую: `curl -s localhost:18081/api/pool`.

## Troubleshooting

### `make up` завершился отказом: «ТАЙМАУТ: не готовы: …»

`make up` по умолчанию ждёт готовности всех 8 инстансов и обоих балансировщиков до 120 секунд
(`scripts/wait-ready.sh`) и **перечисляет, что не готово**, после чего завершается с кодом 1 и
подсказывает, что проверить. Не готовый инстанс почти всегда означает «конфигурация из etcd не
получена»:

```bash
make instances                    # правильный ли путь у каждого инстанса
docker compose ps                 # все ли сервисные контейнеры живы
docker compose logs config-provisioner-1 config-provisioner-2   # обеспечил ли провизор ключи зарегистрированных узлов
make pool I=service-a-group-1-1   # ready, path, notReadyReason конкретного инстанса
```

Инстансы от провизора не зависят (`depends_on` нет): провизор нагоняет конфигурацию сам, по
факту регистрации узла. Пока провизор не работает или не пересверялся — ключей нет, гейт закрыт.

Таймаут регулируется: `make up WAIT_S=300`.

### Инстанс `ready=DOWN`, причина «конфигурация не получена: … нет распознанных ключей»

В пути инстанса нет ни одного ключа из `EtcdKeys.ALL`. Причины: провизор ещё не обеспечил ключи
(сверьте `docker compose ps config-provisioner-1 config-provisioner-2` и
`docker compose logs config-provisioner-1 config-provisioner-2`;
провизор кладёт ключи по факту регистрации узла), путь не совпал (сервис смотрит в другой путь —
см. `path` в `/api/config`), ключи удалили (см. «Ключи инстанса исчезли из etcd» ниже), либо инстанс
в неактивной группе при нулевом резерве флота (`R=0` — холод, конфигурация не выдаётся намеренно).
Пока гейт закрыт, `/api/work` отвечает 503, а `/actuator/health/liveness` — UP: процесс жив.

### Инстанс `ready=DOWN`, причина «etcd недоступен»

etcd лежит до первого применения конфигурации: инстанс жив, но трафик не принимает. Когда etcd
вернётся, провизор пересверяется, ключи появятся, и инстанс **сам** станет готовым — рестарт не
нужен. Стоп-шаги:

```bash
docker compose ps etcd
docker compose logs --tail=50 service-a-group-1-1   # "etcd недоступен/ошибка watch (...) повтор через ..."
```

### Ключи инстанса исчезли из etcd (конфиг сброшен)

Это работа провизора (GC): префикс `hikari/` живёт, пока жив узел регистрации инстанса **и** узел
получает долю бюджета.

- Инстанс остановлен (`docker compose stop <i>`) или упал — провизор удалил весь его путь (включая
  ручные правки); при следующем старте инстанс получит долю бюджета и стартовые значения заново.
- Инстанс выпал из активного распределения: бюджет не тянет состав на минимум
  (`n_акт × m > activeMaxConnections − R×k`), и этому активному узлу не досталась доля.
  Конфигурация снята намеренно — иначе он продолжал бы обслуживать трафик вопреки потолку.
  Проверить: `make budget S=<сервис>` — строки «без доли (не обслуживает трафик)».
- Инстанс в неактивной группе при нулевом резерве (`R=0`): холодный флот — резерв нулевой, поэтому
  ключи сняты целиком. При `R ≥ 1` неактивный инстанс конфигурацию **получает** (пул ровно R) и
  продолжает обслуживать трафик — пропажи ключей не будет.
- Обрыв etcd дольше TTL регистрации: узлы исчезли по аренде, а после возврата и до
  перерегистрации узлов провизор мог счесть префиксы осиротевшими и удалить их. Конфиг
  восстановится при перерегистрации узлов; ручные правки в этом окне теряются — держите нужные
  значения в `.env` (`PROV_CONNECTION_TIMEOUT_MS`) или восстановите руками.

Проверить, кто удалил: `docker compose logs config-provisioner-1 config-provisioner-2` — строки
«очистка: удалено N ключей префикса …». Ключи **бюджета** (`{service}/activeMaxConnections`,
`{service}/activeMinConnections`, `{service}/inactiveMaxConnections`) при этом не удаляются никогда —
см. следующий раздел.

### Доли не равны бюджету / инстанс остался без доли

Смотрите `make budget [S=сервис]`: он печатает `N`, `m`, `R`, маркеры групп, живые инстансы, доли
и их сумму, а также помечает превышение бюджета и недобор с причиной. Частые причины расхождения:

- **Сумма меньше N, часть инстансов «без доли».** Активный бюджет не тянет состав на минимум:
  обслуживается `floor(N'/m)` активных инстансов (`N' = N − R×k`), остальные 503. Лечится
  увеличением `activeMaxConnections` или уменьшением `activeMinConnections` / `inactiveMaxConnections`.
- **Сумма меньше N, все инстансы с долями.** Доли усечены до `PROV_MAX_SHARE` (200) — бюджет
  слишком велик для числа инстансов. Сумма при этом меньше N намеренно: потолок важнее точности.
- **Сумма больше N.** Так быть не должно. Проверьте, не осталось ли ручных правок
  `maximumPoolSize` от `make set-size`, сделанных в обход бюджета, и не работают ли две реплики
  провизёра на одном сервисе (`make leader`).
- **Доли не меняются после правки.** Проверьте, что команда писала в ключ того сервиса, который
  выводит `make budget` (без `S=` он показывает все сервисы), и посмотрите логи провизёра —
  пересчёт пишет строку «пересчёт сервиса …: бюджет …, живых узлов …, обслуживается …».
- **`N < m`, `R` вне диапазона или `R×k > N`, нечисловой ключ.** Провизёр fail-closed: ничего не
  меняет, в логах WARN «распределение бюджета не выполнено» с числами. Приведите ключи к дефолту
  (`PROV_ACTIVE_MAX_CONNECTIONS`/`PROV_ACTIVE_MIN_CONNECTIONS`/`PROV_INACTIVE_MAX_CONNECTIONS`)
  или увеличьте бюджет.
- **Группа не сжалась / не разжалась.** Маркеры групп подхватываются поллингом ~1с — проверьте
  `make budget` (маркер «false» = неактивна, отсутствие/«true» = активна) и подождите пару секунд.
  Флот глобальный: маркер выключает группу во всех сервисах одновременно, но бюджет каждого
  сервиса пересчитывается свой.
- **Ручная правка `maximumPoolSize` «слетает».** Это ожидаемо: ключ управляемый. Правка живёт до
  ближайшего пересчёта — смены бюджета, изменения состава сервиса, рестарта провизёра или обрыва
  etcd. Для разового показа удобны `make set-size` / `set-service-size` / `set-group-size`.

### `minimumIdle` больше, чем `total`

`make pool I=…` показывает `minimumIdle=25` при `total=4`, и пул добирается медленно. Обычно это
значит, что недавно было сжатие **под нагрузкой**: соединения, занятые запросами, помечены к
вытеснению и закрываются при возврате, а новые открывает HouseKeeper небольшими порциями раз в
~30с. Добор занимает минуту-две, в неё флот держит меньше бюджета — это недобор, а не превышение.

Не помогает и строка лога `обновлён на лету: … | now: … total=0`: счётчик читается сразу после
`softEvictConnections()`, пока закрытия не завершились, и показывает 0 независимо от реального
состояния. Ориентироваться надо на `/api/pool` и на `make fleet-sessions`.

Сюда же относится осцилляция «доля туда-сюда» после `kill -9` инстанса: пока его узел висит до
истечения аренды, провижёр считает его живым, доли делятся между тремя (`33/33/34`), а после
возвращения инстанса делятся между четырьмя (`25×4`). Обе волны проходят без превышения N.

### Инстанс остановлен, а его узел ещё видно в etcd

Так и должно быть. При остановке инстанс сначала освобождает соединения (дренаж), и только потом
снимает регистрацию. Пока дренаж не закончился, узел и его публикация `unreleasedConnections`
живятся, и место считается занятым — ровно настолько, насколько честно отчитывается инстанс. Если
снять регистрацию раньше, место освободилось бы повторно: получившие его доли инстансы выросли бы
пока останавливающийся ещё держит свои соединения, и сумма флота превысила бы N.

```bash
make registrations                 # живые узлы и аренды
docker compose logs --tail=30 service-a-group-1-1   # «освобождаем соединения перед остановкой»
```

| симптом | что означает |
|---|---|
| узел пропал сразу, соединения ещё в `pg_stat_activity` | регистрация снята до дренажа — порядок нарушен, место освобождено дважды |
| `WARN` о принудительном закрытии соединений по таймауту | дренаж не уложился в `drain-on-recreate-timeout`; место освободится принудительно, узел снимется после |
| после `kill -9` узел висит до истечения аренды | так и задумано: соединения умерли вместе с процессом, окно в безопасную сторону (недобор) |

### Лидер не выбран / перехват не работает

Проверить, кто ведёт каждый сервис: `make leader` (лидер — ключ с наименьшим `create_revision`
в префиксе `{root}/provisioner/leader/{service}/`, значение ключа — имя реплики). Признаки
проблемы и что делать:

- **Префикс пуст — лидеров нет.** Провизор не выиграл выборы: смотрите логи обеих реплик. У
  штатной реплики в любом состоянии должна жить аренда («аренда выборов получена lease=N»), иначе
  подозревайте `PROV_LEADER_TTL`/`PROV_CALL_TIMEOUT` или недоступность etcd. Расклад по логам:
  `docker compose logs --tail=100 config-provisioner-1 config-provisioner-2`.
- **На сервис два лидера (оба пишут).** В нормальной работе невозможно: в префиксе сервиса всегда
  один старейший ключ. «Оба пишут» на практике означает, что задержка перехвата дольше ожидаемой —
  уцелевший лидер продолжает действовать до истечения своей аренды даже после краха второго узла
  записи. Записи провижинга идемпотентны (txn «ключа нет → put»), поэтому пользоваться обоими
  лидерами безопасно в пределах окна перехвата.
- **Перехват дольше `PROV_LEADER_TTL`.** Типичные причины: keepalive ещё жив (обрыв был короче
  TTL/3), либо фолловер сам потерял аренду (`onLeaseLost` в логах) и ждёт новой. Перезапустите
  фолловера и проверьте `make leader`.
- **После рестарта реплики роли развернулись.** Это норма: новый ключ получает бо́льший
  `create_revision` и стартует фолловером. Предпочтительного лидера нет.

### `make pool` падает на `python3 -m json.tool` / не находится

`make pool` в сводном режиме зовёт `python3 scripts/pool-all.py` — нужен `python3`.
Детально один инстанс: `make pool I=service-a-group-1-1`. Сырой JSON: `curl -s localhost:18081/api/pool`.

### В логах `конфиг отклонён (...), остаёмся на предыдущих значениях`

Значение вне допустимого диапазона, конфиг целиком не применён. Точная причина — в этом же
сообщении и в `etcd.lastError`. Полные диапазоны: [mechanism.md](mechanism.md#валидация). Частые
случаи: `maximumPoolSize=0` из etcd (отклоняется до проверки, отдельной причиной про провизора —
0 здесь означает «снять пул», а пулом управляет провизор) или >200, `connectionTimeoutMs` < 250.
Отклонение не закрывает гейт: значение из хранилища получено, трафик открыт, пул на последних
рабочих значениях.

### `etcd.problems` не пуст, хотя конфиг выглядит правильным

Этот словарь **не очищается**, когда значение чинят: он копится за всё время работы процесса.
Проверено на стенде: после `put maximumPoolSize=banana` и последующего `put maximumPoolSize=12`
запись про `banana` осталась. Смотрите `pool.maximumPoolSize` и `config` — они отражают текущее
состояние. `problems` читается как «что-то когда-то было плохо», а не «прямо сейчас плохо».
Обнуляется только рестартом сервиса.

### `etcd.connected = false` при работающем пуле

etcd недоступен, watch докарачивается с backoff'ом. Пул при этом продолжает работать на последнем
применённом конфиге — проверьте, что `pool.total` ненулевой, клиенты не должны падать.
`etcd.lastError` покажет причину (`TimeoutException` на недоступный etcd, `EtcdException` при
обрыве соединения, текст причин при `REJECTED`).

Две тонкости по времени: первые ~2 секунды после падения etcd флаг ещё `true` (обрыв приходит
асинхронно), а после подъёма восстановление занимает до ~8 секунд из-за backoff'а.

### Нагрузчик показывает растущий `err`, хотя сервис живой

Почти всегда это накопленные ошибки от перезапуска сервиса вручную
(`docker compose up --force-recreate service-a-group-1-1`): нагрузчик продолжает долбить, пока
сеть переподнимается, и получает connection refused. На чистом прогоне `err=0`. Различить можно
по времени: реальные ошибки из-за насыщения пула растут только под нагрузкой и сопровождаются
`waiting > 0`. Балансировщик при этом частично гасит такие окна: `proxy_next_upstream` переводит
запрос на живой инстанс.

### `pg: n/a (...)` в отчёте нагрузчика

`/api/pool` не смог посчитать сессии postgres, потому что пул насыщен (`active` = `total`).
Это ожидаемое поведение: интроспекция не должна занимать последний свободный коннект.
Считать сессии напрямую: `make sessions`.

### Не могу запустить на порту 8080 / 5432 / 2379

Порты балансировщиков (`LB_A_PORT`/`LB_B_PORT`) и инфраструктуры настраиваются в `.env`.
Порты инстансов 18081–18088 привязаны к кортежам `ETCD_INSTANCES` — менять их нужно синхронно с
`docker-compose.yml` (см. «Про ETCD_INSTANCES» ниже).

## Переменные окружения

Берутся из `.env` (скопируйте `.env.example`), у всех есть дефолты в `docker-compose.yml`
и в `Makefile`. Ключевой момент: **канонический список инстансов живёт в `.env`
(`ETCD_INSTANCES`), его читают compose и Makefile** — не дублируйте его в Makefile руками.

### etcd

| переменная | дефолт | куда |
|---|---|---|
| `ETCD_PORT` / `ETCD_PEER_PORT` | `2379` / `2380` | порты на хосте |
| `ETCD_ROOT` | `/config` | корень ключей; путь инстанса: `{root}/services/{service}/groups/{group}/instances/{instance}/hikari/` |
| `ETCD_INSTANCES` | 8 кортежей `service\|group\|instance\|hostPort` | канонический список инстансов (см. ниже) |

### провизор (config-provisioner)

Провижер запускается двумя репликами (`config-provisioner-1`, `config-provisioner-2`), работает
по одному на сервис: лидер выбирается узлами `{root}/provisioner/leader/{service}/`, набор сервисов
реплика выводит сама из узлов регистрации. Кто ведёт какой сервис: `make leader`.

| переменная | дефолт | примечание |
|---|---|---|
| `PROV_ETCD_ENDPOINTS` | `http://etcd:2379` | endpoints etcd для провизора |
| `PROV_ETCD_ROOT` | `${ETCD_ROOT}` `/config` | корень ключей — тот же, что у сервисов |
| `PROV_NAME` | hostname | имя реплики — значение лидер-ключа; в compose задано явно (`provisioner-1`/`-2`), не дублируй в `.env` |
| `PROV_LEADER_TTL` | `10s` | TTL аренды выборов: после краха лидера запасной перехватывает сервис в пределах TTL |
| `PROV_ACTIVE_MAX_CONNECTIONS` | `100` | бюджет активного флота N, если ключа `{root}/services/{service}/activeMaxConnections` нет (кладётся put-if-absent) |
| `PROV_ACTIVE_MIN_CONNECTIONS` | `1` | минимальная активная доля m, если ключа `{root}/services/{service}/activeMinConnections` нет |
| `PROV_INACTIVE_MAX_CONNECTIONS` | `1` | резерв неактивного флота R, если ключа `{root}/services/{service}/inactiveMaxConnections` нет; 0 = холод (неактивным узлам конфигурации нет) |
| `PROV_MAX_SHARE` | `200` | верхняя граница доли; зеркалит верхнюю границу размера пула у сервиса, доли выше неё усекаются |
| `PROV_CONNECTION_TIMEOUT_MS` | `3000` | стартовый `connectionTimeoutMs` (put-if-absent, ручные правки переживают) |
| `PROV_CALL_TIMEOUT` | `5s` | таймаут запросов к etcd |
| `PROV_RETRY_INITIAL` / `PROV_RETRY_MAX` | `1s` / `30s` | границы backoff'а переподключения |

### сервисы (по инстансу)

Каждый инстанс получает свои сегменты пути. Фолбэки — «как в кубах»: `POD_NAMESPACE`/`POD_NAME`.

| переменная | дефолт | примечание |
|---|---|---|
| `SERVICE_NAME` | `spring.application.name` (`pool-service`) | сегмент `service` |
| `ETCD_GROUP` | `POD_NAMESPACE` | сегмент `group`, обязателен при `ETCD_ENABLED=true` |
| `ETCD_INSTANCE` | `POD_NAME` | сегмент `instance`, обязателен при `ETCD_ENABLED=true` |
| `POOL_NAME` | `POOL_NAME` | `application_name` в postgres; в стенде = имя инстанса, иначе `pool_sessions` склеит пулы |
| `POOL_EAGER_FILL` | `true` | добивать пул сразу после расширения (в проде обычно `false`) |
| `POOL_DRAIN_TIMEOUT` | `3s` | сколько ждать активные соединения при пересоздании/закрытии пула |

Локального размера пула больше нет: `pool.db.maximum-pool-size` зашит нулём в `application.yml`
(env-переменной `POOL_MAX_SIZE` не существует). Пул появляется только из конфигурации etcd:
первый принятый снимок создаёт его на своей доле, целевой ноль (инстанс без доли, холодный флот
`R=0`) закрывает его с дренажом.

Порты инстансов на хосте 18081–18088 заданы статически в `docker-compose.yml`; последний элемент
каждого кортежа `ETCD_INSTANCES` обязан совпадать с соответствующим `ports:` блока.

### балансировщики

| переменная | дефолт | примечание |
|---|---|---|
| `LB_A_PORT` / `LB_B_PORT` | `8080` / `8081` | `lb-a` → service-a, `lb-b` → service-b |

### нагрузчик

| переменная | дефолт | примечание |
|---|---|---|
| `TARGET` | `http://lb-a` | куда долбить (через балансировщик) |
| `STATUS_TARGET` | `http://service-a-group-1-1:8080` | откуда брать сводку пула: стабильный инстанс, иначе отчёт мигает между инстансами группы |
| `WORKERS` | `4` | число виртуальных потоков |
| `WORK_MS` | `25` | сколько держать коннект в `pg_sleep` |
| `THINK_MS` | `0` | пауза между запросами |
| `REPORT_MS` | `2000` | период отчёта |
| `DURATION_S` | `0` | `0` = крутится до `docker compose stop loadgen` |

### Важно про `ETCD_INSTANCES`

Список задаётся **один раз** в `.env` и подхватывается оттуда compose (через `$ETCD_INSTANCES`) и
Makefile (`-include .env`). Фолбэк-дефолт продублирован в `docker-compose.yml` и `Makefile` на
случай отсутствующего `.env` — не редактируйте его, правит `.env`.

Расхождение между кортежами и блоками `service-*` в `docker-compose.yml` видно, а не молчаливо:
`make instances` печатает фактический расклад (имя, порт, путь) по каждому инстансу, а
`make pool` показывает, кто реально отвечает. Расклад «правильное место»: Makefile адресуется по
`ETCD_INSTANCES`, сервисы адресуются по сегментам `SERVICE_NAME`/`ETCD_GROUP`/`ETCD_INSTANCE`,
провизору список не нужен вовсе — он пишет ключи в путь любого зарегистрированного узла.

### Прочие настройки, которых нет в `.env`

| переменная | дефолт | примечание |
|---|---|---|
| `ETCD_ENABLED` | `true` | `false` — пула нет (локальный максимум жёстко 0), etcd не опрашивается, путь не собирается, гейта нет |
| `ETCD_CALL_TIMEOUT` | `5s` | таймаут запросов к etcd |
| `ETCD_RETRY_INITIAL` / `ETCD_RETRY_MAX` | `1s` / `30s` | границы backoff'а переподключения |
| `ETCD_REGISTRATION_TTL` | `15s` | TTL аренды узла регистрации инстанса; keepalive идёт каждые TTL/3 (5с) |
| `POOL_CONNECTION_TIMEOUT_MS` и прочие `POOL_*` | см. `application.yml` | локальные дефолты пула; etcd перекрывает |

## Готовность к трафику

Инстанс не принимает трафик, пока не получил конфигурацию из etcd (снимок с хотя бы одним
распознанным ключом: `maximumPoolSize`, `minimumIdle`, `connectionTimeoutMs`, …). Пока гейт
закрыт: `/api/work` = 503 (фильтр `TrafficGateFilter`), `/actuator/health/readiness` = DOWN,
`/actuator/health/liveness` = UP, `/api/config` отдаёт `notReadyReason`. Гейт закрывается, когда распознанных ключей не осталось
(провижер снял конфигурацию — инстанс без доли бюджета или в холодном флоте `R=0`) и открывается
снова при возврате ключей: обрыв etcd после применения конфигурации трафик не останавливает,
события при недоступном хранилище не приходят вовсе.

Неактивный флот — особый случай: при `R ≥ 1` инстанс получает конфигурацию (пул ровно R) и
продолжает обслуживать трафик на резервном размере; при `R = 0` — как инстанс без доли: гейт
закрыт, 503, готовность DOWN.

Проверить всех сразу: `make pool` (колонка `ready`). Один инстанс:
`curl -s localhost:18081/actuator/health/readiness | python3 -m json.tool` и
`curl -s localhost:18081/api/config | python3 -m json.tool`.

## Регистрация инстансов

При включённом источнике каждый инстанс на старте создаёт в etcd узел со своим именем — на
уровень выше ключей конфигурации:

```
/config/services/{service}/groups/{group}/instances/{instance}
```

Узел держится арендой (TTL, дефолт `ETCD_REGISTRATION_TTL=15s`) и исчезает при остановке:
штатной — немедленно, при падении процесса — по истечении TTL. Узел лежит вне префикса `hikari/`,
поэтому на готовность и гейт трафика не влияет; в `/api/config` он не показывается. Конфигурация
инстанса привязана к узлу: стартовые ключи кладёт провизор в момент появления узла, а при его
исчезновении весь префикс `hikari/` удаляется (см. [mechanism.md](mechanism.md#провижирование-конфигурации)).
Смотреть:

```bash
make registrations            # живые узлы: имя инстанса = последний сегмент ключа
make config                   # ключи конфигурации (hikari/...) отдельно от узла
docker compose stop service-a-group-1-1 && make registrations   # узел исчез сразу
```

При `ETCD_ENABLED=false` регистрации нет. Тонкость времени: после `kill -9` узел ещё ~TTL
виден — это свойство аренды, а не сбой.

## Локальный запуск без compose

Сервис — обычное Spring Boot-приложение, ему нужны только postgres и etcd по сети. Пустой
сегмент `group`/`instance` при включённом etcd — отказ на старте, поэтому задайте их явно:

```bash
# 1. поднять только БД и etcd
docker compose up -d postgres etcd

# 2. собрать сервис
cd service && mvn -B package

# 3. запустить с сегментами пути (внутри compose имена сервисов, а не localhost)
java -jar target/pool-service-*.jar \
  --pool.db.jdbc-url=jdbc:postgresql://localhost:5432/demo \
  --pool.etcd.endpoints=http://localhost:2379 \
  --pool.etcd.group=group-1 --pool.etcd.instance=local-1
```

Либо через переменные окружения: `DB_URL`, `DB_USER`, `DB_PASSWORD`, `ETCD_ENDPOINTS`,
`ETCD_GROUP`, `ETCD_INSTANCE`. Не забудьте: локальный инстанс (вне стенда) увидит только ключи
под своим путём, а провизируются ключи по факту регистрации узла в etcd — для отдельно
запущенного сервиса узла не будет, поэтому стартовые ключи ему придётся положить руками:
`docker compose run --rm --no-deps etcdctl put "/config/services/.../instances/local-1/hikari/maximumPoolSize" 10`.

Нагрузчик тоже запускается локально, без образа:

```bash
cd loadgen && javac LoadGen.java
TARGET=http://localhost:8080 STATUS_TARGET=http://localhost:18081 WORKERS=8 WORK_MS=50 DURATION_S=30 java LoadGen
```

### Режим без etcd

```bash
ETCD_ENABLED=false java -jar service/target/pool-service-*.jar
```

Сервис поднимется без обращения к etcd, путь не собирается (пустые сегменты не проверяются), ключи
в etcd на него не повлияют, гейта нет (фильтр пропускает все запросы). Но локальный размер пула
теперь жёстко 0 — пула нет вообще: `etcd.enabled=false`, `etcd.applyCount=0`, `pool.closed=true`,
`pool.maximumPoolSize=0`, а `/api/work` завершается ошибкой «пул закрыт». Этот режим годен для
проверки наблюдаемости и старта без etcd, а не для обслуживания запросов: размер пула задаётся
только через etcd. Проверка, что etcd действительно выключен: `etcd.applyCount=0` и `pool.closed`.

## Как убедиться, что правка доехала

Быстрая последовательность для проверки, что watch работает:

```bash
curl -s localhost:18081/api/pool | python3 -m json.tool   # запомнить etcd.revision инстанса
make set-active-max-connections SIZE=120 S=service-a
make budget S=service-a                                     # доли по сервису и их сумма
curl -s localhost:18081/api/pool | python3 -m json.tool   # revision выросла, maximumPoolSize — доля
docker compose logs --tail=5 service-a-group-1-1          # строка "обновлён на лету: ..."
```

Три признака, что всё применилось: `etcd.revision` выросла, `pool.maximumPoolSize` совпадает с
**долей** из `make budget`, `pool.lastChangeReason` содержит `etcd@<ревизия> [maximumPoolSize=put]`.

Если `etcd.revision` выросла, а `pool.maximumPoolSize` нет — правка не доехала, смотрите
`etcd.lastOutcome` и `etcd.lastError`. Если не выросла и ревизия — сервис не видит etcd вообще,
смотрите `etcd.connected`. Правка бюджета затрагивает все инстансы сервиса, а разные сервисы
изолированы: рост ревизии инстанса service-b не значит, что инстанс service-a увидел ключ.

## Потолок бюджета: как проверить, что флот в него уложился

Сумма долей в etcd равна N всегда, но реальные соединения в переходе ведут себя иначе: сжатому
инстансу приказали меньше, а он ещё держит соединения. Поэтому «сумма долей = N» ничего не
говорит о том, держит ли флот N прямо сейчас.

```bash
make fleet-sessions        # потолки, публикации, «худший случай» и OK/ПРЕВЫШЕНИЕ по сервису
make pool I=service-a-group-1-1   # unreleasedConnections — долг этого инстанса
```

`make fleet-sessions` печатает по каждому инстансу потолок, опубликованный долг и оценку «потолок +
долг», сумму по флоту и сравнение с `N`:

```
  service-a/group-1/service-a-group-1-1       49     0         49             49
  сумма потолков: 200   по отчёту: 200   худший случай (его видит провижёр): 200
  service-a: по отчёту 100, худший случай 100, бюджет N=100 → OK
```

Столбец «худший случай» — это то, что видит провижёр, если публикации нет или она от прежнего
потолка. Пока он не превышает N, место флоту не выдаётся и превышения не будет. **ПРЕВЫШЕНИЕ в этой
таблице — всегда баг**, а не «инстанс ещё не отчитался»: отчёт запаздывает, но его отсутствие
только придерживает рост.

`unreleasedConnections` в `/api/pool` — то же число, что инстанс публикует. Ненулевое значение при
`total` больше `maximumPoolSize` — идёт дренаж после сжатия, это норма. Ноль при `total` **меньше**
`maximumPoolSize` долгом не является: пул просто не добит, место под него свободно.

Проверить переход целиком (пик по флоту, а не только установившийся режим) — сэмплером на 10 Гц,
он ловит сотни миллисекунд перехода:

```bash
docker compose exec -T postgres /tmp/measure-fleet.sh 25 'service-a%' 0.1
```

Скрипты лежат в `scripts/` (`measure-fleet.sh` — сумма по флоту, `measure-pools.sh` — разбивка по
инстансам) и копируются в контейнер postgres через `docker compose cp`.

### Признаки пробитого потолка в логах провижёра

Строка пересчёта печатает всё, из чего считается решение:

```
пересчёт сервиса service-a: N=100, m=1, R=1, активных 4, неактивных (k) 0, обслуживается 4,
избыток 0, изменено размеров 2 (из них рост 2), очищено префиксов 0, ждут места 0,
потолки 52, долги 0, занято 52, свободно роста 48
```

`свободно роста` — место, которое флот реально не занимает. Если при переходе оно скачет от 0 к
десяткам и обратно, место выдаётся растущим раньше, чем сжимающие освободили своё. Долгий
`WARN ... застрял с неосвобождённым сжатием` (30с без движения) означает, что инстанс не отпускает
соединения: смотрите его `threadsAwaitingConnection` и `unreleasedConnections`.

**Сумма может быть меньше N — и это правильно.** Пока сжатый инстанс не отпустил соединения, место
не перераспределяется: флот недоборит, но не выходит за N. Размен односторонний, и цена от него
измеримая — в переходе сумма может падать в разы (52 при N=100 на деактивации группы) и
возвращаться к N по мере освобождения. Во вторую сторону (в сумме выше N) читать нечего: так не
бывает, и если видите — это баг либо ручная правка `maximumPoolSize` в обход провижёра.

**`max_connections` на стенде — 300, а не 200.** Сумма флота на стенде ровно 200, и пик перехода
упирался в потолок postgres: соединения просто не создавались, превышение становилось
невидимым. Проверять переход надо на потолке флота, а не на потолке базы.

## Ограничения

Что в этом прототипе не сделано и что придётся доделать до прода.

### Секреты и доступ

- **Пароль лежит в etcd открытым текстом.** Для боя это отдельный секрет: KMS, шифрование или
  хранение вне etcd с доставкой по своему каналу.
- **Нет TLS и аутентификации к etcd.** Сейчас `endpoints: http://etcd:2379`, сертификатов нет.
  В кластере это значит, что конфиг может менять кто угодно с сетью.
- **Нет ACL на путь.** Любой клиент с доступом к etcd пишет любой ключ. Стоит завести отдельного
  пользователя etcd только на `ETCD_ROOT` и выдавать доступ по сегментам.

### Масштабирование

- **Один путь — один инстанс.** Конфиг пишется под каждый инстанс отдельно (`I=`/`S=`/`G=` в
  Makefile — это ручная группировка, а не репликация конфига). Если захочется «один конфиг на
  группу», нужен отдельный механизм распространения.
- **8 JVM на один хост.** Стенд — это демо-машина: `mem_limit: 512m` на инстанс
  (`-XX:MaxRAMPercentage=70`), но 8 подов + postgres + etcd + nginx всё равно заметно едят память.
  На продакшен это переносится как Deployment/StatefulSet с `POD_NAME`/`POD_NAMESPACE`, а не как
  compose на одной машине.
- **Пул только один на процесс.** Несколько независимых пулов (к разным БД, с разными профилями)
  не поддержаны: один `ManagedPool`, один `EtcdPoolConfigSource`, один путь.

### Балансировка

- **nginx открытой редакции не знает о неготовности заранее.** Active health-чеков нет: неготовый
  инстанс выпадает из ротации только через `proxy_next_upstream` (503 от гейта) и
  `max_fails=1 fail_timeout=5s`. До первого 503 часть запросов может попасть на неготовый под —
  это компромисс против Nginx Plus / njs-скрипта с пробами.

### Блокировки

- **Watch-поток один и он же применяет конфиг.** `eagerFill` держит его до 2 секунд, дренаж при
  пересоздании — до 3 секунд (`POOL_DRAIN_TIMEOUT`). В это время события etcd не обрабатываются.
  Для пути из ~10 ключей это незаметно, для сотни ключей, где важна свежесть, может быть уже
  значимо. Масштабируется плохо: обработка не параллелится и не отбрасывается.
- **`apply()` синхронизирован** (`ManagedPool.java:70`). Это гарантирует отсутствие гонок, но и
  означает, что два больших изменения применяются последовательно.

### Провижер

- **Лидер выбирается по сервису, а не глобально.** Каждый сервис ведёт ровно одна реплика,
  перехват — по TTL аренды выборов (`PROV_LEADER_TTL`, 10с). Задержки и «двух писателей» см. в
  troubleshooting «лидер не выбран / перехват не работает». Проверить, кто ведёт:
  `make leader`.
- **Размер пула не настраивается поинстансно, он доля бюджета.** `maximumPoolSize` — управляемый
  ключ: провижёр перезаписывает его при пересчёте, поэтому `make set-size` живёт только до
  ближайшего пересчёта (смена бюджета, изменение состава, рестарт провижёра, обрыв etcd).
  `connectionTimeoutMs` и прочие ключи — обычные put-if-absent, ручные правки переживают.
- **Изменение состава сервиса меняет доли всех.** Падение одного инстанса пересчитывает пул
  остальных: это каскад ресайзов, но записи идемпотентны, при равенстве значения записи нет.
- **Сервисные ключи бюджета живут дольше инстантов.** `{root}/services/{service}/activeMaxConnections`,
  `.../activeMinConnections` и `.../inactiveMaxConnections` создаются при первом узле и не удаляются
  при опустении сервиса — этого требует rolling update с окном без живых узлов. Инстантные ключи,
  наоборот, умирают вместе с узлом.
- **Отказ в распределении fail-closed.** `N < m`, `m` выше `PROV_MAX_SHARE`, `R` вне диапазона
  `{0} ∪ [1..200]`, `R×k > N`, `N − R×k < m` при наличии активных узлов, нечисловой сервисный
  ключ: провижёр ничего не меняет и пишет WARN с числами. Последнее применённое состояние
  продолжает работать.
- **Маркеры групп — это поллинг, а не события.** Группа `{root}/groups/{group}/active` читается
  отдельным потоком воркера ~1с; изменение пересчитывает только сервисы, содержащие узлы группы
  (проверено на стенде: флип маркера применяется в течение ~1с). Обрыв etcd между проходами держит
  последний известный набор маркеров.
- **Холодный флот без пула.** Локального размера пула больше нет: инстанс без доли (в том числе
  неактивный при `R=0`) не имеет пула вовсе (`pool.closed=true`, `maximumPoolSize=0`) и открыть
  соединения к базе не может. Тёплый флот (`R ≥ 1`) держит пул ровно R и обслуживает трафик.
- **GC удаляет весь префикс при исчезновении узла**, включая ручные правки (см. troubleshooting
  «Ключи инстанса исчезли из etcd»). При обрыве etcd дольше TTL регистрации возможна краткая
  потеря конфигурации до перерегистрации узлов.

### Наблюдаемость

- **Нет метрик в prometheus-формате.** `management.endpoints` экспортирует `metrics`, но приборов
  для пула там нет. Нужен Micrometer-регистратор поверх `HikariPoolMXBean`: размер пула, active,
  idle, ожидающие потоки, время получения коннекта. В проде без этого никак — заметить
  деградацию по логам невозможно.
- **Нет алертов.** Автоматической реакции на `REJECTED`, на `connected=false`, на закрытый гейт
  или на рост `threadsAwaitingConnection` нет.
- **`/api/pool` считает сессии postgres, занимая коннект пула.** При насыщенном пуле поле
  возвращает `error`. Для прода это надо уводить на отдельное соединение.

### Прочее

- **`etcd.problems` не очищается** при исправлении значения (см. troubleshooting). Нужен либо
  сброс по событию, либо чтение как «журнал за всё время».
- **`withPrevKV(true)` в watch** — jetcd десериализует предыдущие значения всех событий, а код их
  не читает. Для пути из ~10 ключей бесплатно; при росте пути начнёт нагружать канал событий.
- **Валидации против `max_connections` у postgres нет.** Бюджет `PROV_ACTIVE_MAX_CONNECTIONS` задаёт
  сумму долей, но потолок базы он проверяет только тем, что провижёр пишет доли, а не их сумму
  «поверх» лимита. Если сумма долей всех сервисов стенда превысит `max_connections` postgres
  (дефолт стенда — 200, два сервиса по 100 впритык), сессии будут отклоняться под нагрузкой;
  при точном равенстве бюджетов лимиту (100+100=200) слотов не остаётся даже для админ-psql —
  наблюдалось на стенде при rolling-прогоне.
  Считать: `make budget` по каждому сервису и складывать.
- **`minimumIdle` по умолчанию следует за `maximumPoolSize`**, то есть в стенде пул держит
  максимум соединений всегда. Это удобно для демо и обычно неверно для прода: лишние коннекты
  съедают лимит postgres, а при `eager-fill-on-resize=true` ещё и открываются сразу.
- **Секьюрити нет никакой.** Не авторизация, не rate limiting, не TLS на HTTP-стороне сервиса —
  `/api/work` доступен кому угодно, кто дотянулся до порта.
- **JUnit-тесты покрывают только чистые функции** (валидация, разбор ключей, путь). `ManagedPool`
  и watch-цикл не покрыты: для них нужен либо Testcontainers, либо интеграционные тесты с
  поднятым etcd. Проверка путей гейта — на живом стенде.
