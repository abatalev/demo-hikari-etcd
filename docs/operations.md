# Эксплуатация: troubleshooting, переменные, локальный запуск, ограничения

## Prerequisites

| нужно | для чего | обязательно? |
|---|---|---|
| Docker + `make` | сам стенд | да |
| `curl` | healthcheck в `make up`, все `make`-цели обращения к API | да |
| `python3` | `make pool` и `make work` форматируют JSON через `python3 -m json.tool` | да |
| `maven` | только `make test`; образ сервиса собирает maven внутри себя | нет |

Отсутствие `python3` — самая частая причина, почему `make up` падает на последнем шаге, когда
стенд уже поднят. Обойти можно, вызвав API напрямую: `curl -s localhost:8080/api/pool`.

## Troubleshooting

### `make up` висит и не показывает состояние пула

Цель ждёт `http://localhost:8080/actuator/health` в цикле (`Makefile:25`) и не имеет таймаута.
Если сервис не поднялся, ждать можно вечно. Смотреть причину:

```bash
docker compose ps
docker compose logs --tail=100 service
```

Сервис может висеть на старте, если etcd-seed не завершился: в `docker-compose.yml:82` стоит
`condition: service_completed_successfully`. Проверить `docker compose logs etcd-seed`.

### `make pool` падает на `python3 -m json.tool`

Нет `python3` в системе. Либо поставьте, либо смотрите сырой JSON: `curl -s localhost:8080/api/pool`.

### В логах `конфиг отклонён (...), остаёмся на предыдущих значениях`

Значение вне допустимого диапазона, конфиг целиком не применён. Точная причина — в этом же сообщении
и в `etcd.lastError`. Полные диапазоны: [mechanism.md](mechanism.md#валидация). Частые случаи:
`maximumPoolSize=0` или >200, `connectionTimeoutMs` < 250.

### `etcd.problems` не пуст, хотя конфиг выглядит правильным

Этот словарь **не очищается**, когда значение чинят: он копится за всё время работы процесса.
Проверено на стенде: после `put maximumPoolSize=banana` и последующего `put maximumPoolSize=12`
запись про `banana` осталась. Смотрите `pool.maximumPoolSize` и `config` — они отражают текущее
состояние. `problems` читается как «что-то когда-то было плохо», а не «прямо сейчас плохо».
Обнуляется только рестартом сервиса.

### `etcd.connected = false`

etcd недоступен, watch докарачивается с backoff'ом. Пул при этом продолжает работать на последнем
применённом конфиге — проверьте, что `pool.total` ненулевой, клиенты не должны падать.
`etcd.lastError` покажет причину (`TimeoutException` на недоступный etcd, `EtcdException` при обрыве
соединения, текст причин при `REJECTED`).

Две тонкости по времени: первые ~2 секунды после падения etcd флаг ещё `true` (обрыв приходит
асинхронно), а после подъёма восстановление занимает до ~8 секунд из-за backoff'а.

### Нагрузчик показывает растущий `err`, хотя сервис живой

Почти всегда это накопленные ошибки от перезапуска сервиса вручную
(`docker compose up --force-recreate service`): нагрузчик продолжает долбить, пока сеть переподнимается,
и получает connection refused. На чистом прогоне `err=0`. Различить можно по времени: реальные
ошибки из-за насыщения пула растут только под нагрузкой и сопровождаются `waiting > 0`.

### `pg: n/a (...)` в отчёте нагрузчика

`/api/pool` не смог посчитать сессии postgres, потому что пул насыщен (`active` = `total`).
Это ожидаемое поведение: интроспекция не должна занимать последний свободный коннект.
Считать сессии напрямую: `make sessions`.

### `make stress` не возвращается

`DURATION_S` по умолчанию равен 0 (бесконечный прогон) в `Makefile:8`, и подстановка
`$(or $(DURATION_S),20)` в `Makefile:52` не срабатывает — `DURATION_S` уже определён. Указывайте
значение явно: `WORKERS=32 WORK_MS=200 DURATION_S=20 make stress`.

### Не могу запустить на порту 8080 / 5432 / 2379

Проброс портов настраивается в `.env`, см. ниже. Для полностью локального запуска без compose
см. следующий раздел.

## Переменные окружения

Берутся из `.env` (скопируйте `.env.example`), у всех есть дефолты в `docker-compose.yml`.

### postgres

| переменная | дефолт | куда |
|---|---|---|
| `POSTGRES_DB` | `demo` | имя БД |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | `app` / `app` | креды |
| `POSTGRES_PORT` | `5432` | порт на хосте |

### etcd

| переменная | дефолт | куда |
|---|---|---|
| `ETCD_PORT` / `ETCD_PEER_PORT` | `2379` / `2380` | порты на хосте |
| `ETCD_PREFIX` | `/config/pool-service/hikari/` | префикс ключей: читает etcd-seed, сидер и сервис |
| `SEED_MAX_POOL_SIZE` | `10` | что etcd-seed положит в `maximumPoolSize`, если ключа ещё нет |

### сервис

| переменная | дефолт | примечание |
|---|---|---|
| `SERVICE_PORT` | `8080` | порт на хосте |
| `POOL_MAX_SIZE` | `10` | локальный дефолт; etcd всё равно перекрывает своим значением |
| `POOL_EAGER_FILL` | `true` | добивать пул сразу после расширения (в проде обычно `false`) |
| `POOL_DRAIN_TIMEOUT` | `3s` | сколько ждать активные соединения при пересоздании пула |

### нагрузчик

| переменная | дефолт | примечание |
|---|---|---|
| `WORKERS` | `4` | число виртуальных потоков |
| `WORK_MS` | `25` | сколько держать коннект в `pg_sleep` |
| `THINK_MS` | `0` | пауза между запросами, для моделирования не насыщенного клиента |
| `REPORT_MS` | `2000` | период отчёта |
| `DURATION_S` | `0` | `0` = крутится до `docker compose stop loadgen` |

### Важно про `ETCD_PREFIX`

Префикс задаётся в трёх местах, и они должны совпадать:

1. `ETCD_PREFIX` в `.env` — используется в `docker-compose.yml` для etcd-seed и сервиса;
2. `POOL_PREFIX` в окружении etcd-seed — производная от первого пункта;
3. **`PREFIX` в `Makefile:3`** — отдельная переменная make, `.env` она не читает.

Если поменять префикс в `.env` и забыть про Makefile, `make set-size` напишет ключ в старый
префикс, а сервис его не увидит: правка пройдёт «в молоко» без ошибки. Для ручной работы с
нестандартным префиксом передавайте префикс явно:

```bash
make set-size SIZE=20 PREFIX=/my/prefix/
```

### Прочие настройки, которых нет в `.env`

Они есть в `application.yml` и настраиваются через переменные окружения, но в `.env.example`
не вынесены, потому что стенду не нужны:

| переменная | дефолт | примечание |
|---|---|---|
| `ETCD_ENABLED` | `true` | `false` — пул живёт на локальных дефолтах, etcd не опрашивается вообще |
| `ETCD_CALL_TIMEOUT` | `5s` | таймаут запросов к etcd |
| `ETCD_RETRY_INITIAL` / `ETCD_RETRY_MAX` | `1s` / `30s` | границы backoff'а переподключения |
| `POOL_CONNECTION_TIMEOUT_MS` и прочие `POOL_*` | см. `application.yml` | локальные дефолты пула; etcd перекрывает |

## Локальный запуск без compose

Сервис — обычное Spring Boot-приложение, ему нужны только postgres и etcd по сети.

```bash
# 1. поднять только БД и etcd
docker compose up -d postgres etcd

# 2. собрать сервис
cd service && mvn -B package

# 3. запустить, указав etcd на хост (внутри compose это имя сервиса, а не localhost)
java -jar target/pool-service-*.jar \
  --pool.db.jdbc-url=jdbc:postgresql://localhost:5432/demo \
  --pool.etcd.endpoints=http://localhost:2379
```

Либо через переменные окружения — `DB_URL`, `DB_USER`, `DB_PASSWORD`, `ETCD_ENDPOINTS`.

Нагрузчик тоже запускается локально, без образа:

```bash
cd loadgen && javac LoadGen.java
TARGET=http://localhost:8080 WORKERS=8 WORK_MS=50 DURATION_S=30 java LoadGen
```

### Режим без etcd

```bash
ETCD_ENABLED=false java -jar service/target/pool-service-*.jar
```

Сервис поднимется на локальных дефолтах из `application.yml`, к etcd не пойдёт, ключи в etcd
на него не повлияют. Полезно, чтобы проверить пул без инфраструктуры. Проверено: поднимается
за ~3 секунды, `total=10`, `etcd.enabled=false`, `etcd.applyCount=0`, `connectionTimeoutMs=30000`
(локальный дефолт, а не 3000 из etcd-seed) — по этой разнице удобно убеждаться, что etcd
действительно выключен.

## Как убедиться, что правка доехала

Быстрая последовательность для проверки, что watch работает:

```bash
curl -s localhost:8080/api/pool | python3 -m json.tool   # запомнить etcd.revision
make set-size SIZE=20
curl -s localhost:8080/api/pool | python3 -m json.tool   # revision выросла, maximumPoolSize стал 20
docker compose logs --tail=5 service                     # строка "обновлён на лету: ..."
```

Три признака, что всё применилось: `etcd.revision` выросла, `pool.maximumPoolSize` совпадает с
записанным значением, `pool.lastChangeReason` содержит `etcd@<ревизия> [maximumPoolSize=put]`.

Если `etcd.revision` выросла, а `pool.maximumPoolSize` нет — правка не доехала, смотрите
`etcd.lastOutcome` и `etcd.lastError`. Если не выросла и ревизия — сервис не видит etcd вообще,
смотрите `etcd.connected`.

## Ограничения

Что в этом прототипе не сделано и что придётся доделать до прода.

### Секреты и доступ

- **Пароль лежит в etcd открытым текстом.** Для боя это отдельный секрет: KMS, шифрование или
  хранение вне etcd с доставкой по своему каналу.
- **Нет TLS и аутентификации к etcd.** Сейчас `endpoints: http://etcd:2379`, сертификатов нет.
  В кластере это значит, что конфиг может менять кто угодно с сетью.
- **Нет ACL на префикс.** Любой клиент с доступом к etcd пишет любой ключ. Стоит завести отдельный
  пользователя etcd только на `/config/pool-service/`.

### Масштабирование

- **Один инстанс на конфиг.** Несколько реплик применят один и тот же ключ к нескольким пулам —
  это, скорее всего, не то, что нужно. Нет per-instance префиксов и распределения.
- **Пул только один на процесс.** Несколько независимых пулов (к разным БД, с разными профилями)
  не поддержаны: один `ManagedPool`, один `EtcdPoolConfigSource`, один префикс.

### Блокировки

- **Watch-поток один и он же применяет конфиг.** `eagerFill` держит его до 2 секунд, дренаж при
  пересоздании — до 3 секунд (`POOL_DRAIN_TIMEOUT`). В это время события etcd не обрабатываются.
  Для префикса из ~10 ключей это незаметно, для сотни ключей, где важна свежесть, может быть уже
  значимо. Масштабируется плохо: обработка не параллелится и не отбрасывается.
- **`apply()` синхронизирован** (`ManagedPool.java:70`). Это гарантирует отсутствие гонок, но и
  означает, что два больших изменения применяются последовательно.

### Наблюдаемость

- **Нет метрик в prometheus-формате.** `management.endpoints` экспортирует `metrics`, но приборов
  для пула там нет. Нужен Micrometer-регистратор поверх `HikariPoolMXBean`: размер пула, active,
  idle, ожидающие потоки, время получения коннекта. В проде без этого никак — заметить
  деградацию по логам невозможно.
- **Нет алертов.** Автоматической реакции на `REJECTED`, на `connected=false` или на рост
  `threadsAwaitingConnection` нет.
- **`/api/pool` считает сессии postgres, занимая коннект пула.** При насыщенном пуле поле
  возвращает `error`. Для прода это надо уводить на отдельное соединение.

### Прочее

- **`etcd.problems` не очищается** при исправлении значения (см. troubleshooting). Нужен либо
  сброс по событию, либо чтение как «журнал за всё время».
- **`withPrevKV(true)` в `EtcdPoolConfigSource.java:189`** — jetcd десериализует предыдущие значения
  всех событий, а код их не читает. Для префикса из ~10 ключей бесплатно; при росте префикса
  начнёт нагружать канал событий.
- **Нет валидации против `max_connections`.** Можно положить `maximumPoolSize=200` при
  `max_connections=100` и получить ошибки под нагрузке. В стенде `max_connections` поднят до 200.
- **Нет сравнения с лимитом на нескольких пулах.** Один пул — одна проверка.
- **`minimumIdle` по умолчанию следует за `maximumPoolSize`**, то есть в стенде пул держит
  максимум соединений всегда. Это удобно для демо и обычно неверно для прода: лишние коннекты
  съедают лимит postgres, а при `eager-fill-on-resize=true` ещё и открываются сразу.
- **Секьюрити нет никакой.** Не авторизация, не rate limiting, не TLS на HTTP-стороне сервиса —
  `/api/work` доступен кому угодно, кто дотянулся до порта.
- **JUnit-тесты покрывают только чистые функции** (валидация, разбор ключей). `ManagedPool`
  и watch-цикл не покрыты: для них нужен либо Testcontainers, либо интеграционные тесты с
  поднятым etcd.
